## 1. Зачем это нужно (для человека)

RKB — база краеведческих книг о Кёнигсберге/Калининградской области. Человек задаёт обычный вопрос по-русски («Кто основал Кёнигсбергский университет и когда?», «Что вспоминал Вихерт о детстве?»). Он получает один короткий ответ с источниками. Ответ строит модель-клиент (ChatGPT-коннектор или dot для Slack) по результатам `search` → `fetch` нашего MCP. Если нужного фрагмента нет среди результатов поиска, хорошего ответа не будет, как бы ни была умна модель.

Книги на русском и немецком, и их становится больше. Сейчас импортируется немецкий «Lexikon der Stadt Königsberg» Альбинуса, ждут ещё пять немецких книг. Типичный тяжёлый случай: **русский вопрос, ответ в немецкой книге**. Другие трудные случаи: короткие факты (строка хронологии, подпись к иллюстрации), исторические названия мест (Кёнигсберг/Königsberg/Калининград, Твангсте, Кнайпхоф), имена, даты.

Владелец считает, что нынешний поиск **деградировал** по сравнению с реализацией начала–середины октября. Тогда было больше веток и больше результатов, но качество мерили мало. Сейчас мы правим ранжирование догадками на живой системе. Нужно серьёзное исследование: как это делают правильно, что у нас было, чего не хватает, и минимальный путь к хорошему поиску.

## 2. Что известно сейчас (проверено RKB-Ответы 26.10, проверь сам)

### 2.1. Текущий путь поиска фрагментов книг (Kaggle, PostgreSQL 17 + pgvector 0.8.2, BGE-M3 1024)
- `src/regional_knowledge/kaggle_search.py` — `_search`: две ветки, лексика (`rkb_v4.lexical_candidates`, до 100 кандидатов) и dense BGE (`rkb_v4.dense_candidates`, HNSW cosine, `hnsw.ef_search=100`, `iterative_scan=strict_order`, до 100). Склейка RRF k=60 с равными весами (строки ~217–221), затем hydrate top-K.
- `sql/kaggle/001_search.sql`, `003_search_scope.sql`: таблица `passage_search` (язык ru/de/simple, `tsvector` по `regconfig` строки, `vector(1024)`), индексы **GIN** (lexemes) и **HNSW** (embedding). `websearch_to_tsquery` по трём конфигурациям (russian/german/simple). Ранжирование лексики — `ts_rank_cd` без нормализации длины и **без IDF** (особенность PostgreSQL: корпусную статистику ранжирование не учитывает).
- **Числа результатов:** по умолчанию 3, максимум 5. `kaggle_protocol.py:82` (`evidence_limit … le=5 = 3`), `kaggle_public_backend.py:425` (`limit=3`), проверка `1 <= top_k <= 5` (`kaggle_search.py:112-114`), SQL hydrate `candidate_ids[1:5]` (`001_search.sql:92`, `003_search_scope.sql:65`), приёмочный контракт `Literal[3]` (`kaggle_acceptance_contracts.py:28`), Slack-бот `[:3]` (`expert_slack_search_reply.py:40`). Ни в ТЗ, ни в документации обоснования «3» не найдено.
- **Что видит модель:** `search` отдаёт только `id`, название книги, `urn:` — без страницы и без фрагмента текста. Три результата из одной книги выглядят одинаково, поэтому модель не может выбрать, что читать через `fetch`.
- **Алиасы:** MCP-инструмент `search` объявляет параметр `aliases`, но Kaggle-путь его **отклоняет** (`kaggle_public_backend.py:687-689`, `unsupported_target_search_option`). При импорте сущности и алиасы сохраняются (`sql/kaggle/011_geo_identity_manifest.sql`: `source_entity_aliases`, `source_entity_mentions`), но в поиске фрагментов не используются.
- Нет `pg_trgm`, нет BM25/IDF, нет sparse- или multi-vector-ветки BGE-M3, нет реранкера, нет соседнего контекста фрагмента.

### 2.2. Что требует ТЗ (`docs/prompts/rkb-scalable-kaggle-implementation-20261019.md`, §4.2–4.3)
- **Три** параллельные ветки: dense, GIN lexical, **exact alias/entity matches** (до 50 хитов), затем RRF/fusion и один batched hydrate top-K. Сейчас реализованы только две.
- Алиасы: «B-tree normalized alias + language/time/identity; exact alias branch; при доказанной нужде fuzzy names — pg_trgm».
- «PG `ts_rank_cd` не равен SQLite BM25: качество измеряется, прежние веса не переносятся как тождественные». «Языковая настройка не выдаётся за перевод RU→DE — эту задачу прежде всего выполняет dense branch. Проверять captions/names/footnotes и language slices отдельно». «Common-term FTS… проверять по actual buffers/rows/time».
- Задержка: тёплый backend p95 ≤ 1000 мс, публичный MCP p95 ≤ 1500 мс, предел 2000 мс.

### 2.3. История проекта (до переноса на Kaggle 19–20.10)

Ветки: BGE dense, E5 dense, lexical (`simple`), **ветка точных алиасов** (`exact_current_alias` / `exact_historical_alias`, phrase match). Результатов по умолчанию **8** (`match_count=8`), до 20. RRF k=60 с диагностикой рангов каждой ветки (`ranking_signals`).

### 2.4. Живые наблюдения 26.10 (банк вопросов RKB-Ответы, issue #499)
До 26.10 ~08:30 UTC лексика требовала все слова вопроса, и на естественных вопросах эта ветка почти всегда была пуста. Фактически работал один dense:
- русский вопрос по немецкому Вихерту — нужная книга в top-3 (4 вопроса: 2 «да», 2 «частично»);
- вопрос по маленькой книге «Тевтонский орден» — ответ первым;
- «Кто основал Кёнигсбергский университет и в каком году его открыли?» — ответа нет в top-3, хотя в книге есть строка «1544 17 августа основание университета (Альбертины)» (Гаузе, с. 141). Короткий запрос «основание университета» находит её первой.

PR 500 (миграция `sql/kaggle/039_lexical_any_term.sql`) сделал лексику «любое слово» (OR для ru/de). После установки:
- **все** проверенные русские вопросы по Вихерту и по «Тевтонскому ордену» потеряли нужную книгу: top-3 целиком из большой русской книги Гаузе;
- коронация Фридриха I (с. 141) выпала из top-3;
- Альбертина по-прежнему не находится;
- время поиска стало 0,4 с вместо 0,7–1,8 с.

Гипотеза RKB-Ответы (проверить):
1. OR на частых словах даёт 100 кандидатов из самой большой книги, а `ts_rank_cd` не учитывает редкость слов.
2. RRF с равными весами награждает присутствие в обеих ветках, поэтому средний фрагмент Гаузе обходит лучший dense-only фрагмент немецкой или маленькой книги.
3. «основал» и «основание», вероятно, дают разные основы в snowball russian.
4. Короткая строка хронологии сохранена без контекста.

Сейчас готовится откат 039 (миграция 040). Это возврат к прежнему состоянию, а не решение.

## 3. Вопросы исследования

Отвечай по каждому пункту: вывод, доказательства (ссылки file:line, отчёты, внешние источники), неопределённость.

1. **Инвентаризация.** Таблица «нужно / было (до 19.10) / требует ТЗ / есть сейчас» для каждого вида поиска и индекса: dense ANN, полнотекст, BM25/IDF, алиасы и сущности, fuzzy (pg_trgm), sparse и multi-vector BGE-M3, реранкер, соседний контекст, фильтры по книге и языку, число результатов, что видит модель в выдаче. Что деградировало и почему (по git-истории и PR), а что сознательно упрощено и правильно.
2. **Как правильно делают гибридный поиск в PostgreSQL** (pgvector + FTS) в 2025–2026:
   - способы склейки: RRF, его k и глубина списков, взвешенный RRF, нормализованная линейная склейка, convex combination;
   - когда лексическая ветка помогает, а когда шумит;
   - как получить IDF/BM25 в PG без нового сервиса: что умеют `pg_search`/ParadeDB, VectorChord-bm25, pg_textsearch и подобные расширения, какая у них совместимость с PG17 и Kaggle, чем это обходится; или как сделать IDF своими средствами (`ts_stat`, словарь частот);
   - как ограничить вклад частых слов (минимальное покрытие, редкие термы, `ts_rank_cd` normalization flags).
3. **Многоязычный поиск RU→DE** на BGE-M3: dense-only против гибрида; sparse/lexical weights BGE-M3 и ColBERT (multi-vector) в pgvector; двуязычный запрос, когда клиент сам переводит запрос; перевод фрагментов при импорте; алиасы исторических названий. Какие методы реально работают и сколько стоят по задержке. Оцени выводы `rkb-crosslanguage-search-decision-20261023.md`.
4. **Сколько результатов и в каком виде отдавать модели-клиенту.** Практика RAG и deep-research коннекторов: top-K для чтения моделью, сниппеты и локаторы в выдаче, recall@K против precision@3, стоимость лишних `fetch`. Формат ChatGPT MCP-коннектора (`search`/`fetch`): какие поля допустимы в результате `search` (title, url, text/snippet, metadata) — по официальной документации OpenAI. Конкретная рекомендация K и формата выдачи для RKB.
5. **Чанкинг и короткие факты.** Contextual retrieval (Anthropic, 2024), parent–child, «small-to-big», соседние фрагменты, контекстные заголовки чанков (книга, глава, страница). Как не терять строки хронологии, подписи иллюстраций и записи лексиконов, не раздувая импорт. Что из этого можно сделать при импорте (у нас модель сама нарезает фрагменты по смыслу, ~256 BGE-токенов).
6. **Реранкинг.** Cross-encoder (например, bge-reranker-v2-m3) на top-20/50 внутри Kaggle (CPU/GPU): даёт ли он выигрыш при наших объёмах, укладывается ли в бюджет 1000/1500 мс, какие есть альтернативы подешевле.
7. **Методика оценки.** Как правильно построить эталон (gold set) и офлайн-сравнение вариантов на копии базы (восстановленный Saved Dataset снимок), а не на живой системе: метрики (Hit@3/@10, MRR, candidate recall@100, срезы RU→DE, короткие факты, отрицательные вопросы), размер выборки, честные знаменатели. Как повторно использовать прежний эталон из 32 семейств.
8. **Минимальный путь.** Упорядоченный список 3–6 изменений: что дать первым, ожидаемый эффект, добавка к p50/p95 задержки, объём кода, риск. Для каждого — один различающий офлайн-тест, по которому его принимать. Учитывай запреты сложности ниже: предпочитай вычитание и уже существующие механизмы, например уже сохраняемые алиасы.

## 4. Широкий внешний поиск — обязательно
Ищи и цитируй со ссылками (отмечая дату и уровень доверия):
- официальная документация: PostgreSQL FTS (ranking, normalization, dictionaries, snowball russian/german), pgvector (HNSW, iterative scan, halfvec, sparsevec), ParadeDB/pg_search, VectorChord / VectorChord-bm25, pg_trgm, OpenAI MCP connectors (search/fetch schema), BGE-M3 и bge-reranker model cards;

## 6. Границы
- Не менять код, SQL, live, Kaggle, прод-БД, не сливать PR. Слияние — RKB-Opus, live — Шкипер.
- Не предлагать новый поисковый сервис, отдельный search engine, второй registry, «LLM внутри бэкенда» и синхронный перевод на каждый запрос без измеренного выигрыша. ## Как писать в Slack (владелец читает и личные треды, и общий)
Пиши для живого человека, на продуктовом языке, как короткую сводку:
- первая строка — итог одной фразой (что изменилось для продукта / вердикт);
- дальше 2–5 пунктов: **тема** — что происходит простыми словами — кого/чего ждём — следующий шаг;
- никаких хешей, SHA, job_id, run id, длинных путей и file:line в тексте для владельца; PR — номером («PR 436»), окно/исполнитель — именем;
- технические детали (file:line, HEAD, CI) — только в комментарий к PR или одной строкой исполнителю, которому они нужны для работы;
- без «Существующие гарантии §1/§2», без перечня того, чего ты НЕ делал (не трогал merge/live — это и так правило);
- коротко: сообщение владельцу ≤ 8 строк.
Пример хорошего отчёта:
> **Бритва (codex):** PR 439 — можно сливать, лишнего не нашёл.
> • **PR 438 (курсор)** — убрать два лишних шага, автор уже исправляет.
> • **PR 400** — против заморозки: +273 строки ради новой таблицы; не сливать до стабильного поиска.

## Запреты сложности (вставлять дословно в промпты окон и исполнителей)
- Цель — продуктовый результат, а не процесс. Каждое добавление должно назвать реальный сбой, который оно предотвращает; иначе не добавлять.
- Не добавлять: новые сервисы, БД, MCP, очереди, гейты, предусловия, сверки SHA/хэшей, «доказательства», фазы, ремонтные ветки, режимы восстановления, ручные шаги. Не дублировать гарантии инструментов (транзакции PG, git, systemd, TLS, неизменяемые версии).
- Предпочитать вычитание: PR на критическом пути должен уменьшать число условий и строк.
- «Неизвестный исход» не повод останавливать всё: ошибка до COMMIT = не применено; проверить по журналу и идти дальше.
- Не давить на скорость в обход ревью сложности. Не делать фичи параллельно нестабильному ядру.
- Не плодить окна: продолжать существующее по той же теме; закрывать вкладку после результата.
