## 2. Исходное упоминание и отложенная GEO-работа

Нормальный `book_ingest(start → book_pages → stage)` в одном модельном проходе сохраняет дословное `exact_source_spelling`, тип/контекст места, `entity_id` и accepted `passage_id/chunk_id` + физическую страницу/регион. `source_poi_hypotheses` хранит POI-факты книги независимо от наличия Story. `source_entity_references`/aliases сохраняют точные явные ссылки, а не backend name matching.

**После фактического accepted text/graph apply** производный `geo_request` для принятого `poi_ref`/mention ставит/пробуждает intent по стабильному source+revision+mention+policy key. Pending/rejected stage, сырое OCR, vector-only shortlist и чужой private source **не** eligible. Withdrawal или superseded revision лишает старый intent права на новую мутацию, но не удаляет старые receipts. Geo enrichment не блокирует ни одну принятую страницу, обычный `search/fetch`, последующее `finalize` или сохранённый Story. Дополнительный graph/owner link приходит **позже**, без reimport/re-embed.

Модель (ChatGPT/dot) по **существующему** разрешённому расписанию получает не более пяти доступных claims, проверяет реальные Wikipedia/Wikidata/OSM/иные источники, сопоставляет тип здания/площадь/остров, эпоху, источник, соседний контекст и внешние ID. `poi_registry(search)` лишь даёт shortlist; модель выбирает существующий POI через `select` или отдельно мотивирует `create` candidate. Имя, расстояние и совпадение Wikidata-слова сами по себе не сливают RKB entity/Street Story POI и не создают точных координат.

## 3. MVP: вычисляемая очередь и одна GEO-проекция (решение Opus)

**Opus 1792775176.034429 заменил исходный план переноса четырёх SQLite-таблиц и семи GEO-инструментов.** Перечень старого API и таблиц в §§1–2 — инвентаризация legacy, а не объем реализации MVP. Никаких новых GEO intents/aliases/attempts/receipts, lease/fence, stage→apply, worker или планировщика. Модель использует существующий механизм расписания.

**Динамический запрос `geo_queue(limit)`:** bounded, максимум 5, выборка из уже существующих `rkb_v4.source_entity_mentions`, связанной `source_entity_ids(kind='poi_ref')` и принятых `source_graph_receipts`. Отобрать только актуальные дословные упоминания **без GEO-link** (нет записи `geo_links` для той же пары `(source_id,mention_id)` и нет ранее явно связанного current canonical POI ref). Проверить `sources.accepted`, `NOT withdrawn`, `active_revision`, `source_visibility`, actor/audience ACL, текущую привязку passage/page/region. JOIN/`NOT EXISTS` по обоим полям `source_entity_mentions.source_id=geo_links.source_id` и `source_entity_mentions.mention_id=geo_links.mention_id`, стабильная пагинация по `(source_id,mention_id)`, никакого persisted backlog, экспорта чужого private source, поиска по похожему имени или обязательного повторного book pass. Accepted source становится доступным для обычного `search/fetch` независимо от GEO.

**Единственная будущая таблица:** `geo_links(source_id, mention_id, status candidate|unresolved|ambiguous, poi_ref, url, checked_at, reason)` с `PRIMARY KEY (source_id,mention_id)`. Это только проекция проверенного решения по *существующему* source mention, не новая RKB place identity и не второй Street Story registry. `candidate` требует current owner-confirmed `poi_ref`; `unresolved/ambiguous` не содержат POI ID. `url` и `checked_at` — реально просмотренный внешний источник и момент проверки **отдельно** от immutable книжного chunk/page/region proof; не выдумывать URL, дату события либо координаты. В PR353 SQL не создаётся.

**Только два будущих целевых MCP-инструмента:** `geo_queue(limit)` (authorized read) и `geo_resolve(source_id,mention_id,status,poi_ref,url,checked_at,reason,operation_key)` (ровно **одна существующая ordered accepted command** через нынешние `TargetServiceStartup` / `ControlSpool` / `AcceptedSourceDispatch` / `kaggle_apply.py` / `rkb_v4.applied_ops`). Внешний `poi_registry(search/get/select/create)` остается текущим, решение принимает модель, owner POI подтверждает Street Story; PG хранит link через existing mention→entity relationship, не редактируя accepted source graph/Story. Нет новых WSS frames, credential, общего name matching или second IAM.

**Техническая ID/ACL граница (Opus 1792776042.134149):** [SQL011](../../sql/kaggle/011_geo_identity_manifest.sql) задаёт `source_entity_mentions PRIMARY KEY (source_id,mention_id)`. `geo_links` использует **такую же пару** и source-scoped JOIN по `source_id` **и** `mention_id`, без требования глобально уникального `mention_id`. `geo_queue` выдаёт оба ID, а `geo_resolve` принимает оба; никакого поиска «ровно одного source» по одному `mention_id`, произвольного JOIN, угадывания `source_id` или новой identity scheme. Для каждого read/write точную пару сопоставить с current eligible `source_entity_mentions`, её `entity_id` и `source_entity_ids(kind='poi_ref')`, затем с source/graph accepted receipt, active revision, withdrawal, passage/page/region и actor/role/audience/source_visibility ACL. Отсутствующая, чужая, withdrawn или stale пара → deny/fail closed **без** POI mutation и утечки private source; одинаковые `mention_id` в разных `source_id` не конфликтуют. Составной PK гарантирует лишь одну строку проекции **на source mention**, не сериализует внешние POI effects либо разные `operation_key`.

**Идемпотентность и история — отдельно.** На RKB стороне действует текущий `operation_key`, exact command/hash, PG accepted outcome/receipt и UNKNOWN readback/replay. У Street Story отдельный существующий owner `idempotency_key` и owner receipt; при потерянном ответе не выполнять повторный POI create с новым ключом. Составной PK проекции не обеспечивает атомарную двухсервисную операцию и не является ACK/Saved.

Все legacy SQLite `rkb_geo_intents/aliases/attempts/receipts/watermarks`, старые lease/outcomes/accepted bytes, backups, immutable PG `geo_manifest_*` и подтверждённые Street Story identities **остаются неизменными вне MVP**. `geo_links` представляет только решения по новым accepted PG mentions и **не мигрирует, не перекрывает, не удаляет и не реконструирует** историю старой очереди. Она остается доступной в историческом owner/recovery контуре; не считать отсутствие строки в новой projection потерей старой записи. Reanchor старого GEO proof — отдельный GEO-only шаг PR158 по edition/SHA/page/region; пока `legacy_unanchored`.

## 4. Web URL + дата отдельно от книжной цитаты (конкретный контрактный gap)

[`entity_graph.py::ResearchSource`](../../src/regional_knowledge/entity_graph.py) уже имеет `url/note`, в то время как `GraphEvidence` сохраняет **book** `chunk_id/page_id/region_id`. В [`geo_resolution.py::GeoProposal`](../../src/regional_knowledge/geo_resolution.py) разрешены лишь `status/reason/canonical_poi_ref/relation/layer_ref/geometry_ref`: URL и дата посещения **отсутствуют**. Поэтому future narrow source PR должен дописать только *версионированное поле существующего geo proposal/attempt/receipt* с bounded external evidence: `url` + фактическая `checked_at_utc` + note/утверждённый external ID, а `source_published_at`/historical epoch только когда известны. Не создавать ещё один provenance registry и не изменять старые accepted JSON. Отдельное время проверки веб-страницы **не** является датой события, названием 1910 года, датой книги или доказательством координат. Никаких реальных веб-вызовов в данном PR.

**Неполное существующее перечисление статусов:** `GeoProposal.status` = `candidate|unresolved|ambiguous|outside_coverage|rejected`; отдельного `not_found` нет. Если поиск не дал подходящего POI, оставить `unresolved` + конкретные проверенные URL/date/coverage и reason «не найдено среди проверенных источников», а не глобальное «объекта нет». Несколько совпадений → `ambiguous` (не select); непокрытая территория/эпоха → `outside_coverage`; owner outage/partial/read unavailable → retry/pending **не** `not_found`.

## 5. MVP: статусы, ACL, retries и граница внешнего эффекта

- `geo_queue(limit<=5)` — current actor-authorized bounded read accepted `poi_ref` source mentions без связанного GEO результата по паре `(source_id,mention_id)` (source-scoped `NOT EXISTS geo_links`), **без** persisted `intents`, leases/claims, `geo_status`/`geo_receipt`, stage/apply и отдельного poller. Очередь — запрос к действующим данным, не второе хранилище; одна страница ответа не доказывает полноту книги.
- `geo_resolve` — единственный будущий write с обязательной парой `(source_id,mention_id)`, `status∈{candidate,unresolved,ambiguous}`, nullable `poi_ref`, реальным web `url+checked_at`, `reason` и стабильным `operation_key`. `candidate` — уже owner-confirmed POI/candidate (не принятая историческая геометрия); `unresolved` — недостаточно подтверждений в **просмотренном покрытии**, а не абсолютное `not_found`; `ambiguous` — 2+ кандидатов без выбора по имени. Network outage/partial/search unavailable не выдавать за отрицательное историческое доказательство.
- **До read и write**: current OAuth actor/role/audience, accepted source/graph receipt, eligible `source_visibility`, active revision/withdrawal, exact passage/page/region и source-scoped JOIN `source_entity_mentions` по обоим `(source_id,mention_id)` с проверкой `entity_id/kind='poi_ref'`. Неавторизованная, отсутствующая, withdrawn, stale или неeligible пара → deny/unknown, **без** POI mutation; не искать глобально уникальный source по одному `mention_id`. Уже записанный `geo_links` не может открывать чужие private fragments/Case, оригиналы и scan proof.
- **Одна строка не означает одну внешнюю операцию:** `geo_links PRIMARY KEY (source_id,mention_id)` допускает одну projection row на пару, не мешая совпадающим `mention_id` у разных sources, но не является mutex для Street Story `create` либо универсальной idempotency. Тот же RKB `operation_key`/payload hash → восстановить accepted result, другой payload под ключом → conflict. Street Story `poi_registry` использует свой owner `idempotency_key`+receipt/readback; при timeout сначала доказать эффект и только затем использовать прежний exact key, не выпускать новый POI. Конкурирующие разные решения отклонять как explicit conflict, без silent overwrite.
- **URL/date ≠ книга:** web URL и `checked_at` — отдельная проверенная справка, не буквальная фраза Гаузе, не время исторического события, не доказательство координат. Современный физический POI принадлежит Street Story; точная историческая геометрия — Cartography. `coordinates=null` честнее вымышленной pin.
- **История не исчезает:** legacy `rkb_geo_*`, прежние `leased/staged/retry_exhausted` и receipts/backups неизменны и *вне* двухинструментного MVP; `geo_links` не пересоздаёт эту машинерию и не переписывает прошлое. После новых исследований намеренное новое решение возможно только в рамках existing ordered command/authority, не автоматическим recheck/scheduler. Normal source import и `poi_context` не ждут GEO; приёмка G1/G5 остается **NOT RUN**.

## 7. Будущие минимальные пакеты MVP — не implementation PR353

1. **GEO-A read:** существующий native authorized PG read получает `geo_queue(limit<=5)` из принятых `source_entity_mentions` + `source_entity_ids(kind='poi_ref')`, current revision/ACL/source graph receipt, `NOT EXISTS geo_links` c JOIN по обоим `(source_id,mention_id)`. Нет материальной очереди или lease. Read возвращает source-scoped пару, а не один глобальный `mention_id`; чужая, отсутствующая либо ineligible пара недоступна. Без новой identity scheme.
2. **GEO-A write:** одна additive versioned PG таблица `geo_links(source_id,mention_id,status,poi_ref,url,checked_at,reason)` с `PRIMARY KEY (source_id,mention_id)` и один `geo_resolve(source_id,mention_id,...,operation_key)` через *существующий* accepted ordered command/`operation_key`/PG result; owner POI подтверждён, source/revision/ACL current. Никаких GEO `claim/stage/apply`, attempts/lease/fence, второго ledger/transport/сервиса. Если current route/ACL/owner-receipt binding несовместим, **STOP** конкретного source-пакета и решение Opus/Контур, не новый обход.
3. **GEO-B POI owner:** модель использует тот же `poi_registry(search/get/select/create)`, owner stable key+receipt в Street Story, связывает доказанный POI с существующим RKB `(source_id,mention_id)→entity_id` через `geo_resolve`. Не автосливать одинаковые названия и не повторять внешнее create после UNKNOWN. Источник физической POI identity остаётся Street Story.
4. **GEO-B reverse read:** существующий `poi_context`/Street Story knowledge endpoint, current source `source_graph_fetch/fetch/story_get` с actor ACL, реальные Gause passages и *Saved* stories. §6 и сценарии **G1/G5** §8 остаются без изменений и **NOT RUN**. Не объявлять read-role баг из §6 исправленным.
5. **Legacy вне MVP:** SQLite `rkb_geo_intents/aliases/attempts/receipts/watermarks` и их backups, old accepted GEO payloads/PG manifest/receipts сохранить дословно. Новая `geo_links` проекция их не реплицирует и не стирает; будущий GEO-only reanchor требует отдельного review PR158. Устаревшие G2/G6/G7 §8 и §§1–2 описывают legacy полный workflow (lease/`geo_status`/receipt) для provenance, но **не гейт этого двухинструментного MVP**; другие разделы не редактируются по точной границе задания.

Нет GEO-C, нового геокодера/ranker/gazetteer, scheduler, массового backfill, PG/provider/POI effect, SQL/code в текущем docs PR. Opus+Контур review, Шкипер sole будущий runtime.
