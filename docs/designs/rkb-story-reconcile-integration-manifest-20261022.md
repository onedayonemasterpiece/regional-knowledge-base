## Exact proposed native contract

`ExactCommand.kind=domain_command`, `route=story.reconcile.v1`, `ids={actor_id,source_id,peer_source_id}` with canonical UUIDs, `person_id=actor_id`; `expected_revisions={progress_version,step_index}` with canonical nonnegative integer strings. Handler functions `rkb_v4.check_story_reconcile_v1(bytea,jsonb,jsonb,text)` and `rkb_v4.apply_story_reconcile_v1(bytea,jsonb,jsonb,text)` with **definition SHA256 pinned by the runtime owner**, not caller input. Fixed dependency semantics: `DependencySpec(route,'public_source',frozenset({'source_id','peer_source_id'}),'shared',False)`, with **both** sources rechecked. The proposed `Revisions` tuple is `('rkb-v4-sql001-016-v1','rkb-v4-story-reconcile-v1','rkb-python-apply-v1')`; it is a candidate until the SQL013–015 chain and exact native binary are reviewed.

The first `stage` uses the stable **parent** `story-reconcile:<sha256>` operation key, canonical `intent_bytes` and their SHA256. Each further accepted transition has a deterministic **different** `story-reconcile-progress:<sha256(actor,parent,action,version,step)>` key, with the same immutable original parent/request/intent digests. A retry retains the original sequence/request_id/command bytes from the existing journal; no new domain result is inferred from an expired local spool. SQL PG cursor advances only after `apply_accepted` checks exact accepted seal, current writer, function definitions and native check preconditions, then commits `rkb_v4.applied_ops` with one outcome.

`begin` sets attempted under expected progress version/step. `advance` checks that the *same actor's* native Case operation for exactly this step is `applied` and that its typed `CaseCreate` or `EvidenceAdd` command equals the immutable model comparison; `reject` requires a distinct exact actor-bound Case `applied_ops.status=rejected_precondition`, not an arbitrary client boolean. `finish` requires exact `step_count`, no attempted step, and makes only this comparison complete. **Neither finish nor source-pass `state=complete` implies all cross-book comparisons complete**. Case ID is a subject-matter selection by the model or existing Case backend, not a pair fingerprint.

The SQL effect can modify **only** the two reconciliation tables; it never edits `source_regions`, `story_assertion_versions`, original documents, model/human variants, contributions or Case tables. A trigger initializes independent reconciliation state `open` for old/new accepted source frontiers, including source-pass `complete`. First source/peer identity, active content revision, eligibility, original SHA, exact quote/offset/page/region and withdrawal are checked against existing PG source tables. The Case effect is solely the existing `KaggleCasesBackend.disagreement_edit(create|add_evidence|operation_status)`.

### Reader and durable outcome

`read_story_reconciliation_v1(parent text,actor uuid)` returns exactly the current actor's immutable intent and PG progress state, only while both source snapshots and current Case ACL (when applicable) remain usable. `PgReconciliationSourceReader` is separate and requires an independently versioned reconciliation cursor; it fails closed if absent. `NativeAcceptedReconcileStore.get()` also verifies the **last progress command** against the existing `RecoveryJournal.remote_outcome()` and exact canonical command bytes/remote `rkb.applied-outcome.v1` before reissuing a state after lost ACK/raw Dev GC. With Dataset, `remote_outcome` must prove checkpoint coverage; a PG-only row is not a durable user-visible success. Missing/mismatched native read, journal, checkpoint, or authority => typed pending/error, never silent Saved.

**Narrow SQL016 grants:** only the selected `(source_id,revision,frontier_id,state)` columns of `source_research_frontier` plus SELECT on the two new reconciliation tables and EXECUTE on exact reconciliation read helpers to `rkb_reader`; no grant of private originals/Case draft tables, no `GRANT ALL`. The writer gets SELECT/INSERT/UPDATE only on the new tables and EXECUTE on its new fixed native functions. Database role changes and definition pin registration require the current owner; this leaf does not execute grants in the running database.
