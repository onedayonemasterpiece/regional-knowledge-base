# РКБ · «Читать первоисточник»: глава/статья в PDF, затем озвучка

**Решение владельца, уточнено 26.10.2026. Статус: продуктовый контракт; реализация не выполнена.**
P0 — точный авторский текст в удобно читаемом PDF. P1 — озвучка. Только существующие клиенты **MCP и Slack**. Никаких новых пользовательских экранов, редакторов, настроек типографики, «переходов между PDF и аудио» и P2.

## 1. Сценарий

- Пользователь задал вопрос РКБ, получил ответ с цитатами и обращается к модели: «Дай статью, откуда цитата 2» либо «Сделай PDF по цитатам 1, 3 и 4». Модель, вызывающая MCP, разрешает ссылки на реальные источники. **Это диалог, не визуальный multi-select интерфейс.**
- Для каждой выбранной цитаты система определяет **уже установленную при импорте** логическую единицу: статью, главу, раздел, если книга действительно так устроена. Несколько цитат одной главы не создают повторный файл.
- **P0:** для каждой уникальной единицы генерируется один PDF (без выдуманного сборника нескольких книг). Модель сообщает статус асинхронной операции и получает файл по готовности. На прогретом Kaggle PDF должен готовиться быстро, конкретное SLA — только после замеров.
- **P1:** по отдельной команде пользователя этот же точный текст озвучивается. PDF не ждёт аудио; у аудио свой статус, возможна длительная очередь.

Не требуется отдельный каталог скачанного, профиль оформления, плеер, навигация между форматами или Web/PWA UI.

## 2. Закрытая группа и права

РКБ — **не публичный сервис**. Пользователи входят в ограниченную группу; вопросы договоров с правообладателями решаются **вне системы**. Внутри этой функции **не создавать новый механизм проверки авторских прав, отдельные статусы лицензий по каждой главе, per-source reproduction grants, юридическую экспертизу или экран согласования прав**.

Использовать существующую аутентификацию и допуск участников к сервису/операции. Уровни (demo, professional, краевед, преподаватель) могут впоследствии определять, кому включена функция, но не образуют отдельный legal-rights workflow и не блокируют P0 до определения тарифных квот. Остаются действующими уже существующие технические ограничения: исключённые/отозванные источники не выдаются, оригинальный PDF/DjVu не становится доступным как побочный эффект текстового экспорта, чужие приватные объекты не раскрываются. Общий Slack-канал не подменяет личную авторизацию, если выдача адресована конкретному пользователю.

Исходная договорная политика **не должна внедряться как программная задержка** для выдачи принятого текста закрытым пользователям. Этот документ не изменяет другие действующие контракты `docs/rights.md` для изображения/скана/полного оригинала.

## 3. Границы глав и статей устанавливаются **на импорте**

**Единственный семантический определитель — модель, которая уже читает книгу по MCP в ходе `book_ingest`.** При чтении страницы/пакета она одновременно определяет структуру: произведение, главу/статью/раздел, заголовок, начало и конец, продолжения на следующей странице. **Не** запускать вторую модель, не подавать поисковые чанки модели заново при PDF-запросе и не угадывать «10–20 страниц» по цитате.

Минимальный набор сохраняемых связей в принятом source graph:
- идентификатор логической единицы и её тип (`chapter`, `article`, `section`), исходное название, связь с конкретным изданием/`source_id` и accepted revision;
- **точные якоря начала и конца** в порядке исходного чтения (physical page + region/span, включая границу внутри страницы), а не только диапазон страниц;
- состояние `open` пока следующая граница/конец источника не подтверждены, `complete` после появления фактического замыкающего контекста.

Постраничный импорт остаётся постепенным. В конце пакета логическая единица может оставаться открытой; это **не останавливает приёмку страницы и обычный поиск**. Закрыть главу можно при подтверждённом начале следующей или в конце книги. Если граница неоднозначна, модель фиксирует это во время импорта, не записывает произвольную. Для старых импортов без структуры — исправление в обычном owner-only `reprocess`/`stage` при работе с книгой, а не модельный анализ по требованию читателя. Использовать уже имеющийся article scope/ID; **не** вести параллельную базу разделов.

Структурные единицы имеют иной смысл, чем семантические BGE-пассажи. Чанки нужны для поиска цитат, но текст экспорта собирается из **полного принятого исходного материала**: source regions/spans в исходном порядке, вместе с заголовками, примечаниями и сносками. Недостающий непрочитанный/непринятый текст или незакрытая граница → `unit_not_ready`, без неполного PDF. Наличие найденной цитаты не доказывает готовности всего раздела.

Связанные контракты: [импорт](../ingestion.md), [source-backed passages](../operations/source-backed-semantic-passages.md), [article scope](../operations/article-search-scope.md).

## 4. P0 · фиксированный книжный шаблон PDF

Файл — **новая вёрстка точного текста автора**, а не фотокопия исходных страниц и не пересказ. Один качественный стандартный шаблон, без пользовательских настроек:
- A4, читаемый шрифт с русскими/немецкими глифами, основное начертание ~11–12 pt; нормальные поля, межстрочный интервал около 1.3, **красная строка** каждого обычного абзаца, аккуратные переносы и правила одиночных строк;
- заголовки и иерархия, реальные сноски/примечания, списки, таблицы (если структура поддержана); если значимый элемент нельзя точно отобразить — явное предупреждение/ошибка, не молчаливый пропуск;
- исходный порядок, пунктуация, орфография и символы автора сохраняются; **нельзя** редактировать, дописывать, обобщать, переводить или склеивать найденные BGE chunks вместо исходного текста;
- PDF с выделяемым и копируемым текстом, Unicode/ToUnicode, внедрённым разрешённым шрифтом. Проверять реальное отображение и экспорт текста.

**Первая страница:** автор/авторы, книга/сборник/журнал, заголовок главы/статьи, выходные данные издания, исходные страницы; **ISBN, ISSN, УДК, ББК, DOI — только если поля имеются в проверенных метаданных**, без вычисления и догадок. Отсутствующих идентификаторов не придумывать. Подпись: «Материал подготовлен сервисом „База знаний региона Калининградская область“ на основе указанного первоисточника. Текст автора сохранён; вёрстка выполнена сервисом». Новая нумерация страниц PDF не выдаётся за исходную.

Иллюстрации статьи/главы (решение владельца 29.10.2026, заменяет прежнее исключение): если в единице есть принятые иллюстрации (`accepted_chunk_link` / illustration refs страниц единицы), они входят в PDF на своём месте в тексте, с исходной подписью и указанием исходной страницы. Изображения берутся в Kaggle из уже принятых иллюстраций, без нового хранилища. Факсимильная вёрстка по-прежнему не входит. Проверять обложку/первую страницу, вёрстку нескольких физических страниц, сноски и немецкую типографику.

### 4.1. Оформление v2 (замечания владельца 29.10.2026 по первому живому PDF)

Первый PDF (Albinus, «Hoffmann, Ernst Theodor Amadeus») устроен так: титульная страница и затем текст статьи. Владелец требует:

1. **Заголовок статьи/главы над её текстом** — так, как он напечатан в источнике; на титульной странице заголовок крупно, отдельно от автора книги.
2. **Аннотация на титульной странице — по-русски, 1–2 абзаца** (по объёму статьи). Помечена как краткое изложение, подготовленное сервисом; не цитата автора.
3. **После текста автора — полный автоматический перевод на русский**, если оригинал не на русском. Отдельный раздел с пометкой «Автоматический перевод; авторитетен оригинал выше». Оригинал остаётся первым и неизменным.
4. **Колонтитулы вместо «Страница PDF N»**: слово «PDF» убрать. Верхний колонтитул — заголовок статьи · автор · книга; нижний — номер страницы. Номер страницы файла не выдаётся за печатный.
5. **Идентификаторы**: ISBN, ISSN, УДК, ББК, DOI — показывать, если они есть в проверенных метаданных. Чтобы они там были, читатель при импорте заносит их с выходной/титульной страницы через `metadata.catalog_update`, как автора и год. Не вычислять и не угадывать.
6. **Вёрстка для чтения человеком**: иерархия заголовков, отступы, красная строка, межабзацные интервалы, выделение заголовочного слова словарной статьи, аккуратная немецкая и русская типографика (§4).

**Кто пишет аннотацию и перевод.** Это новый текст, а не текст автора, поэтому правило §4 «нельзя переводить» относится только к тексту автора: он остаётся дословным. Аннотацию и перевод пишет модель на стороне клиента — та же, что формирует ответы ([режимы ответа §4](../product/rkb-answer-modes-20261024.md)). Она передаёт их в `source_unit_export` как поля, и Kaggle только верстает. LLM внутри Kaggle не добавляется. Без этих полей PDF собирается, как сейчас, без пустых разделов.

## 5. MCP, Kaggle и передача PDF

**Один существующий путь:** модель в MCP/Slack → RKB MCP → Kaggle с принятыми source regions/структурой → PDF renderer **в Kaggle** → **файл напрямую из Kaggle клиенту/модели**, по аналогии с поддержанными механизмами передачи файлов/картинок. DevCoveer выполняет контрольную операцию и возвращает краткий статус/reference; **не проксирует PDF-байты, не сохраняет второй корпус и не создаёт промежуточное файловое хранилище**.

Сейчас картинки RKB доступны как фактический `ImageContent` MCP, а входящие оригиналы используют `openai/fileParams` и direct transfer. **PDF — иной бинарный тип**, поэтому при реализации проверить, какой реальный MCP file/resource/ссылочный механизм умеют соответствующие клиенты и как передать файл **прямо из Kaggle**, не заявляя, что текущая image-схема уже автоматически поддерживает PDF. Одной текстовой ссылки недостаточно, если конкретная вызывающая модель не умеет по ней получить документ.

Минимальная логика существующей оркестрации (наименования **проектные**, не опубликованные методы):
```text
source_unit_export(start, citation_refs | accepted_unit_refs, format="pdf")
  -> operation_ref, queued | preparing | ready | failed
source_unit_export(status, operation_ref) -> status + готовый artifact_ref
source_unit_export(get, operation_ref) -> клиент получает фактический PDF из Kaggle
```
Обычные source/revision/actor-refs, одна операция на одинаковый запрос, безопасное продолжение после разрыва связи. Не проектировать ещё один scheduler, брокер, IAM, REST/PWA и новый формат хранения. PDF render выполняется вне критического пути поиска, не мешает warm search p95. Нет готового source text/unit → сообщить причину, не запускать дополнительное исследование книги при export.

## 6. P1 · озвучка и временное хранение

Исходный текст **тот же, что идёт в PDF**, но аудио — отдельное явное действие. Исследовать повторное использование уже реализованной `wonderful-lections` схемы Qwen3-TTS (Kaggle, batch synthesis, durable job/progress, MP3 readback), прежде чем писать новый TTS-сервис:
- [Qwen Kaggle provider](https://github.com/onedayonemasterpiece/wonderful-lections/blob/main/src/presentation/kaggle-scenario-audio-provider.mjs)
- [Случаи отказа longform](https://github.com/onedayonemasterpiece/wonderful-lections/blob/main/docs/reports/incidents/INC-2026-10-05-scenario-audio-longform.md) — реальные длительные задания падали; надо учитывать process isolation, повторное использование chunks, Kaggle 429 и сохранение фактического run.

При необходимости синтез выполняется в **отдельном Kaggle**, чтобы не затрагивать RKB PostgreSQL/BGE. Сравнить на одинаковом RU/DE тексте скорость/качество Qwen3-TTS и быстрого TTS/Live маршрута, особенно длительность запуска Kaggle, скорость на минуту аудио, ошибки имён/топонимов, полноту исходного текста. Конкретный движок для тарифа выбирать после измерений; «безлимитная Qwen» не означает безлимитных вычислительных ресурсов Kaggle.

**Хранение стандартное:** сохранённые аудиофрагменты и итоговый файл в **обычном приватном версионируемом Kaggle Dataset**, чтобы восстановление не заставляло генерировать их повторно. Использовать стандартные операции Kaggle: добавили в очередную версию, повторно использовали готовое, удалили по принятому правилу хранения через дни/недели. Не создавать самостоятельную файловую БД, media-service, систему биллинга, отдельный cache backend или многоуровневую схему GC. Нужен лишь минимальный manifest, связывающий файл с исходным текстом/версией и голосом, и безопасное удаление неиспользуемых устаревших версий.

Результат аудио передаётся **из Kaggle модели/клиенту**, как PDF; Dev не скачивает MP3 себе для последующей пересылки. PDF не должен ждать озвучки и не зависит от доступности TTS Kaggle.

## 7. Непосредственная последовательность работ

1. **Импорт:** модель, уже читающая страницы, устанавливает точные логические boundaries главы/статьи и сохраняет их в принятом graph. Не тормозить принятие обычных страниц из-за открытой единицы.
2. **PDF:** deterministic read полного принятого авторского текста по unit anchors → один фиксированный формат в Kaggle → асинхронный статус → прямое получение PDF моделью. Включить библиографическую первую страницу и текстовые проверки.
3. **Аудио:** reuse Qwen-схемы Wonderful Lections, отдельный compute при необходимости, измерить Qwen/быстрый TTS, обычный Kaggle Dataset с ограниченной retention.
