## Findings

### Главный вердикт

Направление верное: canonical PostgreSQL+pgvector/BGE в Kaggle, маленький журнал на DevCoveer, один writer, readers по снапшотам. Но разделы 6–9 написаны как список свойств, а не как протокол. Из-за этого в них осталась лишняя церемония (фенсинг внутри эфемерного PG, отдельная подсистема авторизации для readers, открытые «выборы» watermark) и не закрыты три реальные дыры:

1. **Нефенсируемая публикация Dataset.**
2. **Размер журнала при импорте.** Без разделения данных на «авторитетные» и «производные» маленьким он не будет.
3. **Детерминированное покрытие пар источников при параллельных импортах.**

Кастомный event sourcing здесь избыточен. Достаточно **command log + снапшот с внутренним watermark**. Ниже он описан как конкретный протокол.

### P0

**P0-1. Фенсинг стоит не там (§6.3).** [проект]
- У каждого notebook свой локальный PG. Проверка эпохи «в каждой mutation» внутри PG ничего не защищает: зомби-writer портит только свою эфемерную копию.
- Опасны лишь выходы наружу:
  - receipts и resolved-mutations в журнал DevCoveer;
  - публикация снапшота;
  - внешние доставки.
- **Kaggle Dataset API не умеет CAS.** Зомби может создать новую версию Dataset, и «последняя версия Dataset» станет недостоверной.
- Исправление: источником истины для снапшота служит **указатель в DevCoveer**, который обновляется CAS по `writer_epoch`. Readers и restore берут версию только по этому указателю, а не «latest».
- Фраза «новый writer работает только после безопасной границы прежнего поколения» сводится к инкременту эпохи CAS-ом на DevCoveer. Ждать зомби не нужно, потому что все его выходы фенсятся.

**P0-2. Окно «Kaggle применил, журнал не знает» (§6.1 п.5) устраняется порядком операций, а не тестами.** [проект]
- Kaggle никогда не применяет то, чего ещё нет в журнале в resolved-виде.
- Последовательность для операции, требующей модели:
  1. Вычислить результат модели.
  2. Отправить `resolved_mutation(op_id, epoch, payload, model_outputs)`. DevCoveer принимает её CAS-ом с проверкой эпохи и **присваивает apply-seq**.
  3. Применить в PG строго по seq, записав `applied_ops(seq, op_id, payload_hash, outcome)` в той же транзакции.
  4. Отправить receipt.
- После этого «applied без receipt» не является неизвестным эффектом. Если PG потерян, операция переигрывается. Если PG жив, повтор отсекается по `applied_ops`.
- Unknown-состояние остаётся только у действительно внешних эффектов (§6.2).

**P0-3. Журнал не будет маленьким, пока не разделены классы данных (§6.4).** [проект] [не измерено]
- Embeddings: 1024×float32 = 4 КБ на чанк. Если писать в журнал «всё для восстановления», импорт книги раздувает его на мегабайты–гигабайты. HNSW дополнительно раздул бы WAL, поэтому физическая WAL-репликация на общий DevCoveer тоже не подходит.
- Правило:
  - **Авторитетные данные** (решения людей и модели, case-мутации, координаты stripe, активация ревизии) хранятся в журнале байт-в-байт. Они малы.
  - **Производные данные** (чанки, FTS, embeddings) хранятся как рецепт: `source_sha + parser_version + encoder_version(weights hash)`. Сам файл книги лежит один раз в content-addressed хранилище и удаляется по общему watermark.
  - Replay производных данных означает их пересчёт. Это допустимо, потому что ID чанков стабильны и выводятся из `source_sha` и locator, а не из векторов.
- Чтобы replay-хвост не включал тяжёлый re-embedding, **снапшот запускается событием «активирована ревизия»**, а не только по календарю.

**P0-4. Watermark должен вычисляться внутри снапшота (§7).** [проект]
- Внешний manifest может разойтись с содержимым снапшота.
- Если apply идёт строго по seq, без пропусков, и отклонённые операции тоже занимают seq с `outcome=rejected`, то watermark = `max(seq)` из `applied_ops`.
- Значение читается в той же транзакции дампа: `pg_dump --snapshot=<exported>` или чтение в той же сессии при физическом бэкапе.
- Проблема «max seen ≠ watermark» исчезает конструктивно.
- Требование: seq выдаётся счётчиком в транзакции DevCoveer, а не через AUTOINCREMENT с дырами.

**P0-5. Конфликт с защищённым `requirements.json`.** [код]
- Сейчас там зафиксированы Supabase vector-only capacity и quality gates.
- Без явной записи изменения требования владельцем реализация формально нарушит контракт. Quality gates (качество dense, латентность, массовый ingest) переносятся без изменений.

**P0-6. Миграция на PG ломает доказательства и guard'ы.** [код]
- `quote_proof.py` при `corpus=None` сразу возвращает `highlight_unavailable`. Proof и stripe упадут сразу после миграции.
- Disk guard в `source_archive.py` и `illustration_mirror.py` пропускается при `corpus=None`. Под PG эти guard'ы нужно привязать к реальному диску worker. Это новая проблема, а не повтор A0x.

### P1

**P1-1. Покрытие пар A/B должно быть детерминированным.** [проект]
- Правило: research pass ревизии R сравнивает R только с ревизиями X, у которых `activation_seq(X) < activation_seq(R)`, и читает состояние с watermark не ниже `activation_seq(R)`.
- Тогда каждая пара покрыта ровно один раз при любом порядке импорта и любой гонке.
- Таблица `coverage(revision, method_version, status)` даёт retro-scan без реимпорта: при новом `method_version` запускается повторный проход.
- Ключ дедупликации кейса: неупорядоченная пара точных якорей `(source_sha, page, span_hash)`. Формулировки модели в ключ не входят.
- Присоединение третьего источника к существующему кейсу оформляется как отдельная resolved-mutation с CAS по ревизии кейса.

**P1-2. Два прохода и два владельца завершения импорта.** [код]
- Сейчас `story_reconcile(next)` и disagreement scan делают отдельные полные проходы.
- Исправление: **один persisted research pass на ревизию**, у которого два потребителя (stories, cases).
- Единая машина состояний: `staged → active(search-ready) → research_pending → research_done`.
- Активация и постановка pass в очередь выполняются **одной операцией журнала**. Поиск не ждёт экспертной работы.

**P1-3. Авторизация readers переусложнена (§8).** [проект]
- Поиск публичный по принятым книгам, без per-book ownership. Значит, readers не нужны ни ACL, ни authorization epoch.
- Gateway на DevCoveer фильтрует выдачу по крошечному актуальному списку отозванных `source_revision` (с overfetch).
- Экспертные возможности (stripe, страница, оригинал) проверяет только gateway по identity из DevCoveer.
- Kaggle видит псевдонимные `actor_id`, OAuth туда не уходит. Это заодно уменьшает privacy-поверхность снапшотов.

**P1-4. Page→coords→stripe: доступ нельзя расширять снятием `owner=True`.** [код]
- `paint()` сейчас отдаёт всю страницу без маски.
- Требования к stripe:
  - Обрезку делает сервер. Наружу уходит только crop.
  - Координаты нормализованы к фиксированному page box с учётом rotation и CropBox≠MediaBox.
  - Stripe детерминирован по `(source_sha, pdf_page_index, renderer_version, dpi, bbox, padding/clamp)`, байты хешируются.
  - Координаты модели хранятся в журнале.
- Против «книги через полоски» нужны лимиты: максимальная доля страницы на один stripe и **кумулятивная квота покрытия на actor×source**.

**P1-5. Смена схемы или версии кода при непустом replay-хвосте.** [проект]
- Правило: схема меняется только после drain и снапшота при `watermark = head`.
- Записи журнала несут `schema/app` версию. Writer отказывается применять несовпадающие записи. Upcaster'ы не нужны.

**P1-6. Холодный старт reader/writer.** [не измерено]
- `pg_dump` при restore перестраивает HNSW. Это нормально на 2959 чанках, но на сотнях тысяч может съесть весь бюджет 3–5 минут.
- Предпочтительный формат: физический `pg_basebackup -Ft -X stream`. Manifest уже содержит версии PG/pgvector, совместимость контролируется.
- Query-embedding в readers можно считать на CPU, GPU оставить импортам. Это нужно замерить, и это главный рычаг экономии Kaggle-квоты.

**P1-7. Durable runtime: один, а не два.** [код]
- Inbox, generation, token и outbox из PR151 обобщаются до общего журнала: dialog-head, per-person справедливость, типы стадий.
- Параллельная ветка `feat/disagreement-journal` не должна заводить второй журнал или второй admission.
- BgeQueue и её launch reconciliation переиспользуются.

### P2

- **Готовность BGE считается по индексам, а не по работе.** [код] `bge_ready=2959` при остановленном worker и `lexical_only`. Метрика готовности должна быть `effective_retrieval_mode` плюс успешный probe-запрос.
- **Отдельная верификация снапшота лишняя.** Снапшот считается «опубликованным», когда свежий reader поднял его и прошёл checksum/counts/watermark-probe. Отдельный verify-job и отдельный ready-check тогда не нужны.
- **Две разные аренды смешаны.** Writer authority lease — это короткий heartbeat TTL с эпохой. Простой 30 минут — это idle policy. Документы не должны их смешивать.

## Edge cases

- **Пустой корпус, затем A.** Кейса нет, coverage(A) = done.
- **Затем B, противоречащий A.** Создаётся один кейс со ссылками на оба источника.
- **Обратный порядок B→A.** Тот же кейс, ключ симметричен.
- **Повтор B с тем же SHA.** No-op на уровне ревизии, дубля кейса нет.
- **A и B активированы почти одновременно.** Пару покрывает pass с большим `activation_seq`.
- **Та же книга, другой скан (другой SHA).** Это новая ревизия. Legacy-якорь переносится только после точной проверки цитаты на странице. Совпадение заголовка не годится.
- **Legacy-ссылки исторического слоя на E5-чанки.** Состояние `legacy_unanchored` (SHA/page/locator/bibliography). Автоматический reanchor запускается тем же research pass при появлении точного SHA. Границы чанков не используются.
- **Печатная страница ≠ индекс PDF.** Нужна таблица page labels. Библиография показывает печатные номера, stripe использует индекс PDF.
- **Развороты, повёрнутые страницы, CropBox со смещением.**
- **Зомби-writer.**
  - Публикует Dataset: игнорируется, указатель не изменился.
  - Шлёт receipt или resolved-mutation со старой эпохой: отклоняется.
  - Модель для одной операции вызвана дважды: это только стоимость.
- **Внешние доставки при неизвестном исходе.**
  - **Slack**: `operation_id` кладётся в metadata сообщения, сверка через readback истории.
  - **Telegram Bot API** не умеет читать историю бота и не поддерживает idempotency. Без readback нужна явная политика (см. выборы владельца).
  - Telegram и Slack отправляет только DevCoveer, никогда Kaggle.
- **Kaggle launch при неизвестном исходе.** Readback по slug или сессии. Один ключ потребности даёт не больше одного запуска.
- **Отзыв публичного кейса.** Tombstone с максимальной generation, сборка с меньшей generation отвергается. Last-good после отзыва не отдаётся, cache headers короткие. Отзыв источника каскадно снимает или помечает кейсы с его цитатами.
- **Единственная копия в Yandex.** Новая копия пишется под новым ключом, проверяется readback, только потом удаляется старая. На время замены нужен двойной объём.
- **Disk-full на DevCoveer во время загрузки книги.** Файл книги — это payload. Он сохраняется до ACK, иначе ACK не отправляется. Admission держит резерв (headroom).

## Recommendation

### Минимальный протокол (заменяет §6.1–6.3, §7 пп.5–6, §8 ACL)

1. **Intake** (DevCoveer, одна транзакция): `op_id`, idempotency key, payload или blob-ref. Затем ACK «принято». Тот же ключ с другим хешем — это конфликт.
2. **Resolve** (Kaggle writer): чтения и вызовы модели.
3. **Commit resolved** (DevCoveer): CAS(epoch) → `seq` + resolved payload. Только с этого момента изменение durable.
4. **Apply** (PG): строго по seq. `applied_ops` пишется в той же транзакции. Предусловия CAS детерминированы.
5. **Receipt** (DevCoveer): outbox → ответ «сохранено» или «конфликт».
6. **Snapshot** по триггерам: активация ревизии, хвост больше N байт или M операций, расписание.
   - Watermark берётся изнутри снапшота.
   - Порядок публикации: Dataset → readback → reader-probe → CAS-указатель в DevCoveer.
   - Отдельно копия в bucket с readback.
7. **Compaction**: удалять до `min(watermark проверенного Dataset, watermark проверенного bucket)` и только для операций без незакрытых outbox/unknown.
   - Если bucket еженедельный, журнал держит неделю авторитетных данных (это мало) и blob'ы книг (замерить).
   - При превышении порога принудительно делается копия в bucket.
8. **Writer lease**: короткий TTL, эпоха меняется CAS-ом. Idle 30 минут — отдельная политика.
9. **Readers**: только снапшоты по указателю, без репликации. Для read-after-write запрос несёт min watermark: ждём подходящий узел или маршрутизируем на writer.
10. **Очередь**: FIFO внутри диалога, DRR по verified-person между головами, work-conserving по типам ресурсов. Автоскейлинг по возрасту очереди с hysteresis, по реальной квоте и с учётом уже стартующих экземпляров.

### Что удалить или упростить, сохранив защиту

| Удалить или упростить | Чем сохраняется защита |
|---|---|
| Проверка эпохи внутри PG | Фенсинг на трёх границах DevCoveer |
| Открытый выбор механизма ACL для readers | Фильтр отозванного на gateway |
| Отдельный verify-job | Reader-probe |
| «Безопасная граница» прежнего writer | CAS эпохи |
| Gap-логика watermark | Строгий serial apply с отклонёнными seq |
| Второй журнал или второй scan-движок | PR151 плюс один research pass |

### Существенные выборы владельца

1. **Отказовый домен журнала.** Либо принять потерю диска DevCoveer как RPO = последняя копия в bucket, либо непрерывно реплицировать журнал в уже выбранный Yandex bucket (готовый инструмент вроде Litestream, без нового провайдера).
2. **Частота bucket**: неделя или сутки. От неё зависят размер журнала и compaction. Тариф ingress в Yandex нужно проверить.
3. **Неизвестный исход отправки в Telegram**: at-most-once (не повторять, пометить) или at-least-once (повтор с маркером «возможен дубль»).
4. **Экспертный доступ к страницам**: только stripe с лимитами или ещё страница или оригинал. Нужны точные пиксельные и кумулятивные лимиты.
5. **Запись изменения в `requirements.json`** с переносом quality gates.
6. *(Справочно, не замена.)* Корень сложности — canonical БД в эфемерном и недоступном извне compute. Managed PG сняла бы весь replay-протокол. Это решение только владельца, по умолчанию сохраняется Kaggle.

### Решающие приёмочные сценарии

1. **Kill writer.** Убить writer между Commit resolved и Apply, затем между Apply и Receipt. После restore и replay: ровно один эффект, верный watermark, один ответ.
2. **Два живых writer.** Два notebook одновременно, затем разделение сети на 10 минут и его восстановление. Указатель снапшота и журнал принимают только новую эпоху.
3. **Порядки импорта A/B.** A→B, B→A, B→B (тот же SHA), почти одновременная активация. Каждый раз ровно один кейс, coverage полный.
4. **Retro-scan.** Новый `method_version` перепроходит пары без реимпорта и сохраняет старые выводы с пометкой based-on stale.
5. **Restore снапшота на холодном reader.** Вычисленный watermark = `max(applied_ops.seq)`. Запрос с `min_watermark` выше ждёт или уходит на writer.
6. **Отзыв источника при старом снапшоте у reader.** Выдача отфильтрована сразу. Публичный кейс по нему не отдаётся, включая last-good. Устаревшая сборка не воскрешается.
7. **Stripe.** Повёрнутая страница и страница с CropBox. Байты stripe детерминированы между двумя запусками. Полная страница не уходит наружу. Срабатывает кумулятивная квота.
8. **Disk-full.** При заполненном диске DevCoveer ACK нет. Принятые операции не теряются. Compaction не удаляет операции с незакрытым unknown.
9. **Cold start.** Restore + replay + BGE probe не дольше 5 минут на целевом объёме (замерить). Один запрос не запускает два notebook.
10. **Готовность после PG-порта.** Proof и highlight работают без SQLite corpus. Disk guard срабатывает. `effective_retrieval_mode = bge` только при живом probe.

## Confidence

- **Средне-высокая** для протокольных выводов (фенсинг на границах, resolved-before-apply, watermark внутри снапшота, детерминированное покрытие пар). Они следуют из переданных фактов и не зависят от реализации.
- **Средняя** для оценок размера журнала, времени холодного старта, восстановления HNSW, CPU-эмбеддинга в readers и квот Kaggle. Это не замерено.
- **Ограничение**: про PR151 и ветку disagreement-journal я знаю только из краткого пересказа и не видел их текущего кода.
