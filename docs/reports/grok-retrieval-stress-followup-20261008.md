## Системные изменения

- Общая выдача и MCP `search` и `knowledge_search` принимают опциональные `document_ids` (1–20 UUID). Scope валидируется и применяется внутри авторизованного SQLite-корпуса **перед** lexical и pgvector-вызовами; недоступная/выключенная книга не превращается в неявный global search. Обычный поиск без scope не меняется.
- Для буквенно-цифровых literal identifiers новый `retrieval_policy=exact_identifier`; остальной естественный RU/DE/LA текст и графовые алиасы остаются на BGE.
- `latency_ms` теперь измеряется **после** continuation-expansion в обычном `search` и **после** hydration в `search_evidence`. Поля предназначены для воспроизводимого публичного мониторинга; внутренние timings по-прежнему не экспортируются.
- Continuation по контракту может вставить соседа только для двух лучших исходных результатов, поэтому источник соседей теперь обрабатывается **только для этих двух**, а не для всего top-8. Правила отбора и защиты рангов не изменены.

## Проверка

Репродуцируемый read-only harness:
`scripts/benchmarks/live_retrieval_followup.py`:
16 исторических положительных запросов, 2 negative identifier, 3 scoped
и один unauthorized-scope. Положительные требуют BGE `ready` и
правильный top-1 документ; прочие проверяют отсутствие ложных
идентификаторов и непрерывность ACL. У harness есть `--strict`:
warm backend p95 <=1000 ms, hard max <=2000 ms; оба условия обязательны,
не понижаются ради релиза.

Локальный прогон на рабочем коде: **качество — PASS по всем проверкам**.
Первый замер: backend p50 **607,9 ms**, p95 **1225,54 ms**, max **1500,4 ms**.
Второй контрольный прогон при высокой нагрузке: p50 **832,5 ms**,
p95 **1675,36 ms**, max **1865,8 ms**. Попытка распараллелить readiness
и запрос не дала доказуемого улучшения и была **откачена**. p95 acceptance
**не пройден**; это явно остаётся release blocker, а не «зелёный» продукт.

Диагностика хоста в период медленного прогона:
RAM 3,56 GB, `MemAvailable` около 0,70 GB,
swap 4,29 GB из которых свободно около 0,77 GB,
system load около 4,5–5. На небольшом сервере продолжают работать
необязательный E5-сервис и локальная BGE query-sidecar.
Доступ к управлению E5 через `owned_service_action` был отказан
(`worktree_denied`); действиями в обход отказа сервис не остановлен.

## Следующий release gate

1. Восстановить запас RAM/swap и снизить конкуренцию CPU в штатном
   авторизованном operator/deployment plane; E5 диагностический и может быть
   отключён, но только через разрешённую операцию.
2. Повторить `--strict` на тёплом production-like сервере, затем замерить
   **публичный MCP p95 <=1500 ms** с сетевой/transport частью.
3. Проверить recall Hit@5/10 и RU→DE на frozen held-out после нового
   ранжирования и расширения корпуса; отдельно калибровать ложные негативы
   вместо необоснованного cosine floor.
4. Только после критериев из `docs/mass-ingestion-readiness.md` заявлять
   массовую готовность (100k/100 книг и capacity headroom).

**Результат этого этапа:** исправления поиска и диагностический harness готовы;
quality gate пройден, latency gate — нет. Production rollout до
устранения проблемы ресурсов нельзя маркировать как acceptance.
