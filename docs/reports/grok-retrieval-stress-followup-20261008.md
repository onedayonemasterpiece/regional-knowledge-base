A (немецкоязычный, active rev 2) и B (русскоязычный, active rev 4).

Это проверка извлечения/находимости, **не подтверждение нагрузочной
готовности массового корпуса**. Базовая production-ревизия до этой задачи:

## Системные изменения

- Общая выдача и MCP `search` и `knowledge_search` принимают опциональные `document_ids` (1–20 UUID). Scope валидируется и применяется внутри авторизованного SQLite-корпуса **перед** lexical и pgvector-вызовами; недоступная/выключенная книга не превращается в неявный global search. Обычный поиск без scope не меняется.
- Для буквенно-цифровых literal identifiers новый `retrieval_policy=exact_identifier`; остальной естественный RU/DE/LA текст и графовые алиасы остаются на BGE.
- `latency_ms` теперь измеряется **после** continuation-expansion в обычном `search` и **после** hydration в `search_evidence`. Поля предназначены для воспроизводимого публичного мониторинга; внутренние timings по-прежнему не экспортируются.
- Continuation по контракту может вставить соседа только для двух лучших исходных результатов, поэтому источник соседей теперь обрабатывается **только для этих двух**, а не для всего top-8. Правила отбора и защиты рангов не изменены.

## Проверка

Репродуцируемый read-only harness:
`scripts/benchmarks/live_retrieval_followup.py --cases /path/to/private-fixture.json --concurrency 1 --strict`.
Исторические вопросы, идентификаторы документов и репрезентативные
scoped-запросы лежат в приватной fixture за пределами публичного Git.
Фиксированный контрольный набор содержит 16 исторических положительных запросов,
2 negative identifier, 3 scoped и один unauthorized-scope. Положительные требуют BGE `ready` и
правильный top-1 документ; прочие проверяют отсутствие ложных
идентификаторов и непрерывность ACL. У harness есть `--strict`:
warm backend p95 <=1000 ms, hard max <=2000 ms; оба условия обязательны,
не понижаются ради релиза.

**Исторический блокер на сервере до увеличения RAM:** качество — PASS,
но первый замер backend p50 **607,9 ms**, p95 **1225,54 ms**, max **1500,4 ms**;
второй при высокой нагрузке p50 **832,5 ms**, p95 **1675,36 ms**,
max **1865,8 ms**. Попытка распараллелить readiness и запрос не дала
доказуемого улучшения и была **откачена**. Эти два старых прогона не
проходили latency gate; результаты намеренно сохранены для сравнения.

Диагностика хоста **до** увеличения RAM: 3,56 GB, `MemAvailable`
около 0,70 GB, swap 4,29 GB из которых свободно около 0,77 GB,
system load около 4,5–5. На небольшом сервере продолжают работать
необязательный E5-сервис и локальная BGE query-sidecar.
Доступ к управлению E5 через `owned_service_action` был отказан
(`worktree_denied`); действиями в обход отказа сервис не остановлен.

## Приёмка релиза и границы применимости

1. Увеличение RAM до ~7,8 GB подтверждено. vCPU осталось 2; при конкуренции
   с фоновыми разработчиками/агентами хвост задержек может возрастать.
   E5 остаётся необязательным, самовольного отключения сервиса не было.
2. Backend warm `--strict` успешно повторён дважды с concurrency=1 и
   отдельно с concurrency=2. Для concurrency=4 p95=1166,55 ms не проходит;
   повышенную параллельность нельзя объявлять испытанной.
3. После deploy необходима проверка **публичного MCP p95 <=1500 ms**
   с транспортом и hard <=2000 ms для hydrated evidence-search.
4. Отдельный frozen replay подтверждает BGE-only качество, но требует
   новой выборки при расширении корпуса. Не вводить произвольный
   similarity cutoff для сложных отрицательных вопросов.
5. Только после критериев из `docs/mass-ingestion-readiness.md` заявлять
   массовую готовность (100k/100 книг и capacity headroom).

**Обновлённый результат на сервере с 8 ГБ RAM (8 октября):** все 16
контрольных исторических запросов, exact negatives и scope/ACL прошли.
После первичного прогрева два отдельных строгих прогона прошли
при p95 **677,70 мс / 644,80 мс**, максимумах **959,4 / 757,3 мс**.
При **2 одновременных запросах** p95 **687,15 мс** (PASS);
при **4 одновременных** p95 **1166,55 мс** (FAIL backend p95,
но ответ не превышает hard 2 с). На этом двухъядерном сервере проверенный
production-like concurrency envelope — два одновременных поиска.
Hydrated Live-backend (до трёх доказательств) p95 **780,78 мс**
(PASS по предварительному backend-критерию; публичный MCP transport
проверяется после production-развёртывания).

Сохранённый BGE-only t256 dense replay на закрытой frozen fixture
(только агрегаты; inputs SHA в приватных артефактах): held-out
Hit@5 **87,50%**, Hit@10 **90,625%**,
RU→DE held-out Hit@10 **91,67%**. Результаты подтверждают исходный
BGE-only критерий, но не доказывают масштаб 100k/100 books.

До production-развёртывания необходимы зелёный CI на окончательном PR,
соответствие SHA всех сервисов, затем public MCP p95 ≤1500 мс и hard ≤2000 мс.
Не объявлять завершённой массовую готовность без отдельных capacity,
качества и параллельных проверок на большем корпусе.
