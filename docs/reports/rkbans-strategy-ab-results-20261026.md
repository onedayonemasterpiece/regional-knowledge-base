# RKB-Ответы · «Стратегии» — сравнительный опыт V0–V4 на RU↔DE

**26 октября 2026. Статус: диагностический клиентский A/B, не продуктовая приёмка и не основание автоматически возвращать PR 517.** Заказчик — RKB-Ответы (Claude). База методики — [ПМИ PR 519](https://github.com/onedayonemasterpiece/regional-knowledge-base/pull/519), варианты инструкций — [PR 515 §10](https://github.com/onedayonemasterpiece/regional-knowledge-base/pull/515). Этот документ и [question-only банк](../testing/fixtures/rkbans-strategy-ab-queries-20261026.json) — весь diff данного PR.

## 1. Вывод для продукта

На 10 русских вопросах к **немецким** книгам попадание заранее подтверждённого целевого passage в доступный пакет: **6/10** при одном русском запросе (V0), **9/10** при смешанной RU+DE строке (V1), **9/10** при двух отдельных RU и DE запросах (V2), **7/10** при двух русских перефразировках (V3), **8/10** у диагностического proxy V4 (с заранее известными anchors; не слепой adaptive-read эксперимент). По Вихерту в W01 не сработал ни один вариант; по Альбинусу DE-эквивалент восстановил A03, где повторный русский запрос даже с `document_ids` не помог.

Но **на независимом по времени, историческом RU→RU пилоте PR 519 V1 снизил полноту доказательств с 5/8 до 4/8**. На четырёх немецких вопросах к русскому переводу V1 также терял контекст. Следовательно, *правило «всегда склеивать RU+DE в один запрос» не принимать*. Предпочтительная **проверяемая гипотеза** — короткая инструкция: поиск на языке пользователя → прочитать → только при незакрытом пробеле адресно дочитать соседний текст, ограничить книгу или **отдельно** выполнить эквивалент на языке документа. Это рекомендация для дальнейшего испытания, не доказанный победитель A/B.

## 2. Что измерялось и чем ограничено

- Банк был зафиксирован в отдельной docs-ветке **до оцениваемых поисков**: 10 новых RU→DE, четыре DE→RU, четыре отрицательных; F01–F10 из [исходного банка PR519](../testing/fixtures/rkb-retrieval-strategy-queries-20261026.json) оставлены как регрессия. D01–D04 — переводы F01–F04: **не являются четырьмя дополнительными независимыми историческими фактами**.
- `book_find` и точные read-only `fetch(source_id, page_start, page_end)` подтвердили **принятый немецкий текст**: коллективный том *Ernst Wiechert* (1975), проверенные физические страницы 1–4; Robert Albinus, *Lexikon der Stadt Königsberg Pr. und Umgebung* (1988), проверенные физические страницы 7–10. Для DE→RU: русское издание Ф. Гаузе (1994), конкретные страницы 4–8. Наличие прочитанных страниц **не означает завершённый импорт книг**. Gold сопоставлен с фактически принятым passage, не с неподтверждёнными знаниями модели.
- Реальный MCP `search` возвращал **три** кандидата, `fetch` — текст/провенанс, `document_ids` передавался только при адресном V4. Поисковые вызовы — последовательные, P=1; без нового backend, reranker, изменения K или live. Наблюдаемый corpus state в завершённых сериях: data/projection **776/776**, `bge_lexical`. Во время исследования владелец отдельно перезапускал API; периоды warming и рестартного теста исключены из успешных quality наблюдений. Код/маршрут API до и после установки различались, поэтому latency сравнивается **описательно**, не причинно.
- **Существенное ограничение слепоты:** один исполнитель одновременно видел accepted anchors при подготовке источников и исполнял поиск. Это нарушает разделение ролей ПМИ §3. Более того, proxy V4 в RU→DE иногда решал остановиться по **наличию известного gold anchor в выдаче**, а не после честного независимого чтения. Это **не исполнение V4 по ПМИ §7**, а диагностическая оценка возможного второго действия. Исторические RU→RU оценки PR519 имели отдельного оценщика; новые RU→DE/DE→RU — нет. Все допустимые альтернативные supporting sets корпуса не размечены. Ни одну цифру V4 не выдавать за слепое A/B.
- В RU→DE выполнено **74** завершённых измеряемых search (10+10+20+20+14); DE→RU использовало **16 физических search** для четырёх вопросов с переиспользованием одного первого запроса между V0/V2/V3/V4; отрицательные — четыре поисковых вызова. Дополнительно были source/page reads, диагностический `document_ids` поиск для D04 и пре-флайт/ошибочные оболочки вызовов; точный сквозной total call ledger неполон, так что соответствие общему cap `≤120 search, ≤80 fetch` **не сертифицируем**. Инструментальные отказы/target_warming не кодировались как retrieval miss.
- Для RU→DE V2/V3 и продолженных proxy V4 показаны **полное объединение возвращённых списков** и ориентировочный offline RRF60 top-3 (совпадающие returned URL, ранги с единицы; `1/(60+rank)`). Состояние data/projection было одинаковым, но source/revision для каждого элемента при склейке **индивидуально не верифицировались** — это не строгий RRF по ПМИ §6 и **не серверный reranker**. Поскольку закрытый raw call trace PR519 нельзя извлечь из публичного репозитория, **`scripts/benchmarks/rkb_cascade_pilot_summary.py` для новой серии не запускался**; приведена непосредственно подсчитанная ограниченная матрица, а не фиктивный вывод анализатора.

## 3. Результаты по языковым стратам

**C@3** — доказательный набор в пределах реально возвращённого top-3; **union** — все уникальные кандидаты не более двух запросов; **RRF@3** — offline top-3 после RRF60. RU→DE оценивает *strict accepted anchor present*, что не равно независимой оценке полного ответа. RU→RU и DE→RU требуют сохранения всех связей/контекста и потому не обязаны совпадать с наличием одного якоря.

| Страта / показатель | V0 один исходный | V1 одна mixed строка | V2 RU+DE отдельно | V3 два того же языка | V4 адресный шаг |
|---|---:|---:|---:|---:|---:|
| **RU→RU**, PR519, complete evidence, n=8 | **5/8** | **4/8** | **5/8** | **5/8** | **5/8** |
| **RU→DE**, strict anchor, n=10: C@3 первого search | 6/10 | **9/10** | 6/10 | 6/10 | 6/10 |
| **RU→DE**, strict anchor: полный union | 6/10 | **9/10** | **9/10** | 7/10 | 8/10 |
| **RU→DE**, strict anchor: RRF@3 | 6/10 | **9/10** | **9/10** | 7/10 | 8/10 |
| **DE→RU**, complete own evidence, n=4, union | 2/4 | 1/4 | 2/4 | 2/4 | 2/4 |
| **DE→RU**, RRF@3 | н/и | н/и | н/и | н/и | н/и |
| Исходные отрицательные вопросы: достаточное явное опровержение в V0 top-3 | 1/4 | н/и | н/и | н/и | н/и |

DE→RU: дополнительное точное чтение соседнего accepted chunk **после оценённых arms** разрешило указательное «из этих башен» для D03. Это **постфактум диагностика**, а не исполненный V4 и не улучшение RRF@3; к 2/4 её не прибавляли. D04 после первого немецкого поиска не нашёл связи «этот мост» с именем; отдельное **постфактум** чтение соседней страницы обнаружило связку. Этот успех также не прибавлен к результатам.

**Индивидуальные RU→DE семейства** (1 = точный принятый passage в union, 0 = не найден в возвращённых кандидатах):

| Семейство / книга | V0 | V1 | V2 | V3 | V4 | Что различает |
|---|---:|---:|---:|---:|---:|---|
| W01, Wiechert | 0 | 0 | 0 | 0 | 0 | Должность в Кёнигсберге; отдельный DE вернул книгу, не требуемый passage |
| W02, Wiechert | 1 | 1 | 1 | 1 | 1 | Университетские предметы |
| W03, Wiechert | 1 | 1 | 1 | 1 | 1 | Литературная премия и произведение |
| W04, Wiechert | 1 | 1 | 1 | 1 | 1 | Две даты выступлений |
| W05, Wiechert | 1 | 1 | 1 | 1 | 1 | Воспоминание о детстве |
| A01, Albinus | 0 | 1 | 1 | 0 | 1 | Имя художника; V4 `document_ids` помог |

**DE→RU (четыре немецкие формулировки по русскому Гаузе, диагностическое ручное чтение):** D01 — V0/V2/V3/V4 достаточны при **двух** связанных цитатах, V1 потерял предысторию письма; D02 — один passage содержит обе части, все варианты достаточны; D03 — наименование/форма/место башни найдены, но фраза «из этих башен» требует предыдущего passage; **после прогона** адресное чтение окружения закрыло связь, но это не оценённый V4; D04 — фрагмент «этот мост» без названия не доказывает, что речь о Кремербрюке, ни одно исполненное ограниченное поисковое плечо не вернуло пару. После завершения опыта точное чтение соседнего принятого текста нашло пару, что является **неоценённой** диагностикой.

**Отрицательные N01–N04:** все четыре — проверяемые ложные предпосылки (не «ответ отсутствует во всём корпусе»). В первом V0 top-3 опровергающий текст найден только для N01 (хронология Бухенвальда); для трёх остальных целевой source не присутствует в top-3. False-premise correction и true-negative abstention модели **не измерялись**: собственные сгенерированные ответы и их цитатные наборы отсутствуют.

## 4. Затраты и полнота ответов

| RU→DE (10 семей, завершённый search) | V0 | V1 | V2 | V3 | V4 |
|---|---:|---:|---:|---:|---:|
| Search calls, всего | 10 | 10 | 20 | 20 | 14 |
| Медиана суммы backend/search на семейство, мс | 378 | 544 | 747 | 745 | 410 |
| Медиана суммы измеренного client tool wall/search на семейство, мс | 1 074 | 1 147 | 1 949 | 1 918 | 1 076 |
| Макс. backend сумма на семейство, мс | 418 | 668 | 919 | 909 | 904 |
| Макс. wall сумма на семейство, мс | 2 037 | 2 541 | 2 895 | 3 021 | 2 335 |

Медианная парная разница native search V1−V0 в RU→DE = **+175 мс** (округлено). Это *только search*, без всего fetch, генерации, озвучивания/Slack и user→answer; p95 продуктового цикла не вычислялся. Между сериями имел место сторонний API рестарт; не объявляем новый SLO, causal latency benefit или регрессию целого клиента. Вывод PR519 на другой RU→RU стратификации был +274 мс native V1−V0; эти цифры не объединены.

**Чтение и затраты fetch:** в парном DE→RU пакете дополнительно выполнены 14 реальных `fetch(id)` для уникальных кандидатов (общий read-cache внутри одного диагностического прогона); отрицательные N01–N04 потребовали ещё 2 fetch. Из-за разделяемого чтения нельзя присваивать каждому arm одинаковую или нулевую latency fetch. Для RU→DE отдельного per-arm fetch ledger и непрерывного user→answer wall нет; эти ячейки **н/и**. Сохранённый PR519 даёт 60 fetch с медианами wall 932 мс / backend 209 мс **только в своём пилоте**.

**Answer groundedness / полнота ответа / полнота процитированного subset**: для новых статических V0–V3 и proxy V4 **н/и (не измерено)**. Raw search+fetch не является фактически сгенерированным независимым ответом. В прежнем PR519 для *своего*, а не нашего, V4: answer own-packet 5/8, citation complete 4/8. Не переносить эти значения на RU→DE.

## 5. Короткая против полной инструкции V4

Две версии из PR515 §10.1 (полная) и §10.2 (короткая) прочитаны и сопоставлены по **предписанным действиям**. Изолированного A/B с новыми контекстами/моделями, слепым судейством и сравнимым количеством генераций **не было**: один исполнитель видел решения вариантов, а история всех tool calls общая. Поэтому нельзя писать «короткая выиграла» либо «полная лучше». Обе требуют чтения, stop-on-sufficiency и ограниченного gap-directed шага; длинная дополнительно формализует неопределённость, provenance, условия AND/NOT и выход по техническому status. Наблюдённые ошибки (пропуск немецкого источника, анафора и неполные цитаты) исправляются **выбором действия**, а не длиной промпта. Для следующего контролируемого A/B короткая версия — более простой кандидат.

### Рекомендуемый тестовый текст — общий для Full MCP и Миры

> Отвечай по принятым источникам РКБ с проверяемыми ссылками. Восстанови самостоятельный вопрос; сохрани человека/объект, место, период, отрицание и все запрошенные части.  
> Начни с одного содержательного запроса **на языке пользователя**. Не склеивай русский и немецкий текст в одну обязательную строку и не подставляй предполагаемый ответ. Когда пользователь называет конкретную книгу, учитывай её как источник и используй доступный `document_ids`, если он установлен.  
> Прочитай полный найденный фрагмент и доступное продолжение. Проверь, подтверждены ли все части вопроса и связи между ними. «Этот», «он», «из этих» без понятного antecedent и совпадение названия книги сами по себе не доказательства.  
> Если доказательств достаточно — отвечай и процитируй **все** фрагменты, необходимые для фактов и связи. Иначе выбери **только один** следующий шаг по причине пробела: дочитай ограниченное соседство той же книги при обрыве контекста; уточни `document_ids` при ошибочном источнике; **отдельно** повтори запрос на немецком или русском языке источника при языковом расхождении. Не запускай все варианты подряд.  
> Не объединяй разных однофамильцев, не меняй смысл при переводе и не делай вывод «книга не содержит ответа» из top-3. Остановись при достаточной опоре, исчерпании бюджета или технической недоступности; назови оставшийся пробел, конфликт или неопределённость. Уточнение пользователя — лишь при реальной неоднозначности вопроса, которую нельзя разрешить источниками.

**Операционная оговорка:** названия tool-методов и лимиты берутся из реально доступного клиенту профиля. Full MCP допускает `search`/`fetch` и второй свободный query; Мира вызывает реальные function tools Google Live (не отдельный «Live MCP»). В Slack→dot старый receiver может игнорировать новый query — инструкция не заменяет исправление маршрута. Product limits для поиска/чтения задаёт host; промпт не создаёт новый технический gate.

## 6. Чего результат не доказывает и следующий приёмочный шаг

1. **Не доказаны** преимущество V4 над V2/V1, качество сгенерированных ответов и цитат в RU→DE, превосходство короткого текста, статистическая обобщаемость по всему корпусу. Редкие успешные anchor hits не замещают атомарного оригинального gold и независимого судьи; D01–D04 зависимы от прежних семей F01–F04.
2. В отдельном новом held-out банке ≥30 **независимых** eligible семейств включить RU→RU / RU→DE / DE→RU / DE→DE, ложные предпосылки и настоящие corpus-unanswerable вопросы. Развести подготовителя accepted gold, исполнителей V0–V4 и слепых оценщиков. В каждом arm дать **свой** fresh context; сравнить short/full V4 и одинаковые search/fetch бюджеты.
3. Сохранить закрытый фактический trace и прогнать существующий **`scripts/benchmarks/rkb_cascade_pilot_summary.py`**; публично вывести только агрегаты и честные N. После этого RKB-Ответы принимает текст для Full MCP и Миры; RKB-Opus решает вопрос PR, Шкипер — дальнейшую live установку.

**Продуктовое решение на текущих данных:** универсальную mixed-инструкцию PR 517 (уже откатанную PR 521) не возвращать. Проверять короткую адаптивную инструкцию выше: отдельный DE поиск при языковом провале + локальное дочитывание при недостающей связи, без новых серверных компонентов.
