# Задание RKB-Импорт И2: картинка страницы для модели-читателя в нормальном качестве

Заказчик: RKB-Импорт (Claude). Основание: аудит [§10.4](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/docs/rkb-import-efficiency-audit-20261027/docs/audits/rkb-import-efficiency-audit-20261027.md), план [§1 И2, §7 К5, §8.4](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/docs/rkb-import-efficiency-audit-20261027/docs/audits/rkb-import-fix-plan-20261027.md). Решение владельца 27.10: требования экономить на весе картинок **не было**; модель должна видеть страницу в нормальном качестве; цвет не трогать.

## Цель для человека

Модель-читатель получает страницу книги, чтобы дословно её переписать. Сейчас плотный разворот DjVu (оригинал 4680×3310) приходит к ней в 1280×905 px при JPEG q55 — около 640 px на печатную страницу двухколонного словаря. Мелкие буквы читаются неуверенно: перечитывания спорных имён, ошибки в отдельных буквах топонимов (Albinus p39, p48, аудиты 46/48/49 — 2/49 BODY). Причина — лимит 256 КиБ из пилота 20.10 (коммит `628696d9`), а не требование продукта. AGENTS.md запрещает принимать пилотные пределы за продуктовые.

## Что сделать

1. **Одна политика рендера страницы для модели**, общая для PDF и DjVu, в одном месте констант:
   - длинная сторона — до родного разрешения источника, но не больше разумного предела для vision-клиента (по умолчанию 3200 px; для PDF — снять ограничение `scale≤2` до этой длины);
   - JPEG q85, цвет RGB как сейчас, без перевода в серый;
   - бюджет файла по умолчанию 8 МиБ. Если не влезает — снижать quality, затем длину, но не ниже нынешних 1600 px;
   - фактические ширина, высота, quality и байты — в `preview_render`, как сейчас. Поле `preview_only` оставить, если оно что-то значит для потребителей; иначе обосновать в PR.
2. **Снять 256 КиБ** во всех местах таблицы и заменить общим бюджетом из п. 1. DjVu child — принимать выбранный edge из той же политики. Существующие лимиты CPU, памяти и PPM пересчитать под новый размер, не убирая (не безграничный декодер).
3. **Квитанции не трогать:** уже выданная картинка неизменна (`_record_issued_image`, [`original_intake_controller.py:345-353`](../../src/regional_knowledge/original_intake_controller.py#L345-L353)). Новое качество — только для новых выдач. Не переписывать прежние receipts и не выдавать другой JPEG для уже выданной страницы той же ingestion.
4. **Документ:** обновить `docs/operations/kaggle-native-original-intake.md` (раздел про preview policy): 256 КиБ был пилотным пределом, новая политика и её основание.

## Чего нельзя

- Не переводить в серый, не резать разворот на половины, не менять канал и транспорт.
- Не рендерить все страницы книги заранее, не добавлять OCR/VLM и новые сервисы.
- Никаких новых флагов поведения, состояний, ретраев, проверок и режимов восстановления.
- Не трогать live, Kaggle и API.

## Бюджет

Production: ≤ 60 изменённых строк в перечисленных файлах.

## Один различающий тест

Синтетический плотный разворот (например, 4680×3310 с мелким текстом-шумом) через PDF-путь и через DjVu-путь даёт JPEG с длинной стороной ≥ 3000 px, q ≥ 80, байтов > 256 КиБ и ≤ бюджета. Его принимают native, controller и `book_pages`. На текущем main тот же вход даёт ≤1600 px и ≤256 КиБ. Повторная выдача уже выданной страницы возвращает прежний receipt без замены.

## Живая проверка — Шкипер вместе с RKB-Ответы

После слияния (RKB-Опус) и установки controller и native в обычное окно обновления Шкипер выдаёт новую страницу (не ранее выданную) и проверяет фактические размеры, байты и время выдачи. RKB-Ответы — читается ли мелкий шрифт в ChatGPT (что модель реально видит после клиентского сжатия). Сравнение ошибок — на пробной книге: независимый аудитор считает дефекты регионов и заголовков, как раньше.

## Кто заметит и как часто

Модель-читатель — на каждой странице: меньше перечитываний, меньше ошибок в буквах. Пользователь — в точности имён и топонимов в ответах.
