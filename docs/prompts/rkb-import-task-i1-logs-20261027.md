# Задание RKB-Импорт И1: логи импорта по каждому вызову читателя

Заказчик: RKB-Импорт (Claude). Основание: план [`docs/audits/rkb-import-fix-plan-20261027.md`](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/docs/rkb-import-efficiency-audit-20261027/docs/audits/rkb-import-fix-plan-20261027.md) §1 И1, §7 К4 (аудит Pro), §8.4 шаг 1. Решение владельца 27.10: «Процесс импорта должен быть нормально покрыт логами, чтобы он был прозрачен и понятен».

## Цель для человека

Сейчас нельзя сказать, куда уходит время импорта страницы: модель читает 3–7 минут, а потом ещё 1–2 минуты уходят неизвестно на что. Полных журналов нет: продуктовая телеметрия выключена (`RKB_PRODUCT_LOG_MODE=off`) и почти не покрывает книжные вызовы. После этой доработки владелец запускает импорт одной книги, и по логам строится таблица по каждой физической странице:

| страница | выдача картинки (book_pages) | отправка пакета (stage) | stage принят | текст опубликован | семантика применена | Saved | число status | число fetch | паузы между вызовами | исходы и ошибки |

Таблица должна получаться одной командой из сохранённых логов, без ручной работы и без текста книги.

## Доказательства (main `da7ed36a`)

- Санитайзер телеметрии пропускает только фиксированные поля и молча отбрасывает остальные: [`product_telemetry.py:24-60`](../../src/regional_knowledge/product_telemetry.py#L24-L60), `_clean` — [`:66`](../../src/regional_knowledge/product_telemetry.py#L66). Нет физической страницы, команды, `next_action`, размеров и счётчиков.
- Book-вызовы сейчас: `_timed_native_phase` пишет только `phase/status/operation_ref/duration_ms` и хеширует ingestion ([`kaggle_native_source_intake.py:32-58`](../../src/regional_knowledge/kaggle_native_source_intake.py#L32-L58)). Событие применения пишет `phase=stage` для stage/batch/finish и хеширует operation key — с вызовом его не связать ([`:346-349`](../../src/regional_knowledge/kaggle_native_source_intake.py#L346-L349)).
- `book_pages` и `book_ingest` на MCP-границе не наблюдаются ([`server.py:1568`](../../src/regional_knowledge/server.py#L1568), [`:1762`](../../src/regional_knowledge/server.py#L1762)). `fetch` наблюдается, но без источника и страниц ([`server.py:1383-1394`](../../src/regional_knowledge/server.py#L1383-L1394)).
- Диск телеметрии ограничен 32 МиБ, при заполнении sink отключается, потери видны только в счётчиках ([`product_telemetry.py:21`](../../src/regional_knowledge/product_telemetry.py#L21), [`:229-268`](../../src/regional_knowledge/product_telemetry.py#L229-L268), [`docs/operations/rkb-product-telemetry-20261023.md`](../operations/rkb-product-telemetry-20261023.md)).

## Что сделать

1. **Расширить существующий bounded-контракт** `product_telemetry` (не новый сервис и не новый формат) событиями импорта:
   - `import.call` на MCP-границе `book_pages`, `book_ingest` (каждая команда) и `fetch` по `source_id`: `command`, длительность всего вызова (включая auth), исход (`status`, `reason`/`error_class` из существующих стабильных кодов), `next_action`, `state`.
   - Общий ключ корреляции на всю книгу: один и тот же `ingestion_ref` (хеш ingestion_id) во всех событиях импорта, включая события применения. Плюс `operation_ref` исходной операции и `attempt` — чтобы связать stage → text → semantic → Saved.
   - Физическая страница (`physical_page_index` или диапазон для stage из 1–4 страниц) — целое число, не текст.
   - Числа без текста: байты пакета stage, число регионов, чанков, отметок границ, story/entity/POI кандидатов; для `book_pages` — байты, ширина и высота картинки; для `fetch` — число чанков, `has_more`.
   - Применение на native-пути различает компонент: `stage`, `text`, `semantic`, `finish`, `saved` — вместо одного `phase=stage`.
2. **Видимые потери:** каждая запись несёт монотонный `seq` процесса, а счётчики `emitted/dropped/failed/sink_disabled` пишутся периодически и при остановке. Отсутствие записи в отчёте — «неизвестно», а не ноль.
3. **Бюджет диска для книги:** проверить, что импорт книги в 200 страниц укладывается в существующий бюджет с запасом. Если нет — поднять только значения по умолчанию для import-событий или ротацию и выгрузку уже существующих сегментов. Новый сервис хранения не нужен.
4. **Отчёт одной командой:** `scripts/import_timeline.py` (read-only) читает сегменты телеметрии и печатает таблицу из «Цели» по каждой физической странице в CSV и Markdown. Отдельно — сводка: медианы и p90 по интервалам, доля времени между вызовами, страниц в час, потери логов. Без текста книги.
5. **Документация:** короткий раздел в `docs/operations/rkb-product-telemetry-20261023.md` — как включить (переменная окружения уже есть), где лежат сегменты, как запустить отчёт, что значит «неизвестно».

## Чего нельзя

- Никакого текста книги, запросов, URL скачивания, токенов и секретов в логах — только числа, коды, хеши ссылок.
- Не менять поведение импорта, контракты stage, ретраи, блокировки и состояния. Телеметрия best-effort: её ошибка не влияет на результат вызова.
- Не путать телеметрию с durable receipts; не ждать её записи в горячем пути (используется существующая очередь).
- Никаких новых сервисов, очередей, флагов поведения, гейтов и режимов восстановления. Новые поля — только в существующем санитайзере.

## Бюджет

Production: ≤ 150 строк в `product_telemetry.py`, `kaggle_native_source_intake.py`, `server.py` (и при необходимости `kaggle_importer.py`). Скрипт отчёта ≤ 200 строк. Тесты — сколько нужно.

## Один различающий тест

Синтетический прогон двух страниц через существующие фикстуры native-импорта (book_pages → stage → status → text → semantic → fetch) пишет события, а `import_timeline.py` строит по ним таблицу: у каждой страницы заполнены выдача, отправка, применение текста и семантики, число status. Без правки те же поля пустые или неразличимы. Дополнительно: запись с полем, содержащим текст, отбрасывается санитайзером.

## Живая проверка — Шкипер

После слияния (RKB-Opus) Шкипер ставит API/controller в тихий момент и включает `RKB_PRODUCT_LOG_MODE=standard`. Пробный вызов `book_pages`/`status` на уже существующей книге без stage даёт записи `import.call` с правильной страницей. Затем Шкипер сообщает RKB-Импорту «логи готовы», и владелец запускает импорт книги. По первым 5 страницам — таблица `import_timeline.py`.

## Кто заметит и как часто

Владелец и RKB-Импорт — на каждой импортируемой странице: таблица времени вместо догадок. Читатель книги — никак (поведение не меняется).
