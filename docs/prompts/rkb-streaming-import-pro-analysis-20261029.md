Прочитай репозиторий https://github.com/onedayonemasterpiece/regional-knowledge-base (ветка main): `AGENTS.md`, навык простоты https://github.com/onedayonemasterpiece/codex-devcoveer-mcp/blob/main/skills/devserver-simplicity/SKILL.md, документы ниже. ## Цель владельца

Наполнить базу: **100 книг меньше чем за месяц**. Это ~20–25 тыс. физических страниц, около **30 стр/ч круглосуточно, включая ночь**. Без потери качества и функциональности: дословный текст, смысловые фрагменты, границы статей и глав (из них собирается PDF), сущности, факты, истории, иллюстрации. Истории и сущности — важная часть базы, а не необязательное приложение. Борьба идёт за **общую скорость наполнения**, а не за секунды доступности одной книги.

## Как сейчас

- Архитектура зафиксирована: Kaggle — вычисления (PostgreSQL/pgvector + BGE-M3), Kaggle Dataset — хранение, Dev (DevCoveer) — MCP API и контроллер, без хранения корпуса. Верхний уровень не пересматривать.
- Читатель — окно ChatGPT с коннектором RKB MCP. Цикл: `book_ingest(start)` → `book_pages` (изображение разворота) → модель пишет дословный текст, регионы, фрагменты, границы, сущности → `book_ingest(stage)` → следующий разворот. Порядок чтения выбирает модель (PR 606).
- Окна запускаются через ChatGPT Launcher (`chatgpt_start` / `chatgpt_continue`). Ход окна заканчивается примерно через 8 страниц. RKB-Импорт сделал автопродолжение: скрипт ждёт `done` и шлёт «продолжай» в то же окно.
- Оригинал попадает в Kaggle двумя путями: вложение файла от модели (`fileParams`) или **`book_ingest(start, telegram_original=…)`** — Kaggle сам скачивает оригинал из архива Telegram (topic 2) по точному локатору, без передачи байтов через Dev или модель: `docs/operations/kaggle-native-original-intake.md`, раздел «Direct Telegram PDF ingress».
- Список книг к импорту (32 PDF/DjVu в topic 2) сегодня вручную собрал оператор и вручную же подготовил JSON для старта.
- Каталог уже импортированного: `book_find`.

## Замеры 29.10 (Albinus, плотный немецкий словарь, ~7 тыс. символов на разворот)

- Чистое чтение одного окна — **18–20 разворотов/ч** (~200 с на разворот; payload ~24 КБ JSON: 30–40 регионов, 25–35 фрагментов). Сервер stage→apply ~0,8 с.
- Остановки за день: отказ страницы без указания места (исправлено), сбой старта Kaggle, падение replay после rollout. Это отдельная работа, не тема задания.
- Поиск во время импорта: одно чтение в Kaggle одновременно, цикл ~450 мс (BGE encode 160–230 мс, SQL 30–50 мс, транспорт 100–200 мс). Владелец согласовал параллельные чтения: последовательна только BGE. Параллельный импорт нескольких книг владелец тоже согласовал.

План опытов: `docs/product/rkb-import-speed-rnd-20261029.md` (PR 633). Владелец **снял** E3 (обогащение отдельно: не ускоряет общее наполнение) и E5 (черновик OCR: модель всё равно выполняет свои операции). В работе: E1 (без per-page отчётов в Slack), E2 (режим рассуждения), E4 (2 разворота на stage), E6 (параллельные книги).

## Предложение владельца: «обратная схема» поточного импорта

1. Владелец выкладывает книги в архив Telegram topic 2 (решение владельца — см. уточнение ниже; Kaggle Dataset как точка выкладки снят, чтобы не дублировать хранилища).
2. Модель по MCP спрашивает, какие книги ждут импорта. Выбирает одну — или находит по названию из своего задания.
3. Импорт начинается без передачи байтов от модели: Kaggle берёт оригинал сам. Оригинал сразу оказывается в архиве (Telegram), обратная передача не нужна.
4. Несколько окон работают параллельно, каждое на своей книге, в том числе ночью. Закончив книгу, окно берёт следующую.

### Уточнение владельца 29.10: точка выкладки — Telegram

Чтобы не дублировать хранилища, владелец просто загружает книги в архив Telegram (topic 2). Сейчас легальное направление одно: **сервис → Telegram** (оригинал, принятый сервисом, архивируется в Telegram). Нужно законное обратное направление: **загрузил в Telegram → сервис**. Сообщение с файлом в архиве становится книгой к импорту.

Для этого обязателен контроль: был ли **этот файл по этой конкретной ссылке** (chat/topic/message/document, SHA-256) уже импортирован или импортируется сейчас. Повторный старт той же книги — например, вторым окном или после сбоя — должен вести в существующий импорт, а не создавать дубль. Тот же файл, загруженный повторно другим сообщением, тоже должен опознаваться как дубль — по SHA-256.

### Что уже есть и где остаётся разрыв

- **Получение оригинала:** `telegram_original` уже скачивает PDF/DjVu непосредственно в Kaggle и проверяет точный chat/topic/message/document и байты. Но locator требует заранее известный SHA-256; обычная загрузка владельцем в Telegram ещё не превращается в такой готовый запрос. `file_id` — hash **всего locator**, поэтому повтор тех же байтов другим сообщением получает другую идентичность ([locator](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/c2f9f6be5dcf6f65a5e36b846f6e95301c67e629/src/regional_knowledge/telegram_original.py#L19-L48), [download](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/c2f9f6be5dcf6f65a5e36b846f6e95301c67e629/src/regional_knowledge/telegram_original.py#L153-L183)).
- **Состояние уже хранится:** control intake и original receipts/locator на Dev; staging, original SHA и research frontier — в Kaggle. `book_find` показывает принятый каталог, в том числе ещё незаконченные книги, и не перечисляет сообщения архива. Новый реестр не нужен: нужен запрос, соединяющий входящие с имеющимися состояниями ([control](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/c2f9f6be5dcf6f65a5e36b846f6e95301c67e629/src/regional_knowledge/kaggle_importer.py#L123-L130), [receipts](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/c2f9f6be5dcf6f65a5e36b846f6e95301c67e629/src/regional_knowledge/original_intake_controller.py#L52-L64), [PG](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/c2f9f6be5dcf6f65a5e36b846f6e95301c67e629/sql/kaggle/006_source_import.sql#L4-L28), [catalog](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/c2f9f6be5dcf6f65a5e36b846f6e95301c67e629/sql/kaggle/034_source_catalog_corrections.sql#L66-L85)).
- **Повторный start и владение — разные вещи.** Сейчас reuse ищет `person_id + file_id`, требует совпадения metadata и может вернуть `next_cursor=0` вместо актуального продолжения. Единственный `acquiring` освобождается после получения оригинала; это допускает несколько верифицированных книг. Lock охватывает API-вызов, но не 200 секунд чтения: два окна одного owner не различаются ([start](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/c2f9f6be5dcf6f65a5e36b846f6e95301c67e629/src/regional_knowledge/kaggle_importer.py#L287-L331), [lock](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/c2f9f6be5dcf6f65a5e36b846f6e95301c67e629/src/regional_knowledge/kaggle_importer.py#L855-L895)).

Но переносит исходный prompt и ссылку, не текущее состояние книги; `done` — окончание хода модели, не доказательство полноты импорта ([доставка/rollover](https://github.com/onedayonemasterpiece/chatgpt-mcp-launcher/blob/e1c63ebd64fc47b98d2f16353a6a877e8a9d77f0/relay/queue.mjs#L345-L430), [контекст](https://github.com/onedayonemasterpiece/chatgpt-mcp-launcher/blob/e1c63ebd64fc47b98d2f16353a6a877e8a9d77f0/relay/queue.mjs#L21-L43)). ### Сколько окон

Единица — **физическая страница файла**, даже если изображает две печатные. При `R = N × r × A`, где `r=18–20 стр/ч`, а `A` учитывает календарные простои и доведение полного результата:

| Окон | При условном A=80% | За 30 суток |
|---|---:|---:|
| 2 | 28,8–32 стр/ч | 20 736–23 040 |
| 3 | 43,2–48 стр/ч | 31 104–34 560 |

**30 стр/ч дают 21 600 страниц за 30 суток. Для 25 000 за 29 суток нужны 35,92 стр/ч.** Два окна потребуют A≈90–100%, три — ≈60–67%, если скорость масштабируется. Четыре CPU не означают четыре допустимых окна: модель читает вне Kaggle. Предел зависит от BGE/рендеринга, RAM/диска, поиска и доступности браузера/аккаунта; сейчас он не измерен.

### Минимальный план: пять шагов

1. **RKB-Импорт + разработчик intake, ревью Opus: входящие и дедупликация.** Owner-only режим существующей MCP-группы постранично читает topic 2; выбор по названию разрешается в точное сообщение, библиография затем сверяется по книге. Статусы «не начат / идёт / завершён» выводятся из текущих receipts/progress. Для нового сообщения Kaggle вычисляет SHA при первом скачивании; атомарное сопоставление проверенного SHA в том же owner/archive scope возвращает канонический intake и сохраняет связь второго locator, не публикуя второй source. До скачивания дедуп по байтам неизвестен. Повторный start ведёт в существующий `status/next_action`, сохраняет metadata и receipts. Эффект: без ручного JSON и повторного импорта; принцип SHA-уникальности уже есть в [legacy SQL](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/c2f9f6be5dcf6f65a5e36b846f6e95301c67e629/sql/015_source_identity.sql#L4-L37), переносится принцип, не старый backend.

2. **Тот же исполнитель: одно назначение читателя на intake.** Атомарно закреплять логического читателя и поколение в существующей control-row; другой читатель выбирает другую книгу. Ход закончился — назначение сохраняется; при смене чата сохраняется reader key, меняется поколение. Сервер отклоняет новые stage старого поколения. Таймаут сам по себе не доказывает остановку. Уже ACCEPTED-команды доисполняются прежним ledger; notebook writer-fence и исторический replay не менять. Эффект: параллельность разных книг без конкурирующих записей одной. Единственный unresolved upload сохраняется; устаревшую формулировку «один импорт вообще» согласовать с решением владельца 29.10.

3. **RKB-Импорт: довести имеющийся цикл продолжения.** Скрипт отвечает за доставку и запоминает request/job/фактический successor chat; модель в owner MCP читает актуальный RKB status и выбирает продолжение либо, завершив обязательное наполнение, следующую книгу. В handoff передаются ingestion/source, последний принятый порядок, открытые единицы и хвост; `next_cursor` остаётся подсказкой. Потерянный ответ проверяется по прежнему ключу, warming — через штатный startup/status; при смене runtime — свежий status того же intake после READY. Нужен редкий `chatgpt_report(progress)`: 8×200 с≈27 мин близко к [30-минутному порогу тишины](https://github.com/onedayonemasterpiece/chatgpt-mcp-launcher/blob/e1c63ebd64fc47b98d2f16353a6a877e8a9d77f0/relay/queue.mjs#L168-L175). Детерминированный отказ фиксируется в текущем intake без бесконечных повторов; остальные книги продолжаются; неопределённую доставку нельзя превращать в новый reader без сверки и назначения. Эффект: непрерывность без нового watchdog и без owner-прав техническому боту.

4. **Импорт + Ответы: ускорить одно окно, сохранив качество.** E1 — убрать per-page Slack/fetch; следовать `continue_pages`, даже пока сервер публикует предыдущий пакет ([готовое перекрытие](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/c2f9f6be5dcf6f65a5e36b846f6e95301c67e629/src/regional_knowledge/kaggle_native_source_intake.py#L595-L614)); выигрыш измерить. Следующий stage проходит существующий барьер обогащения; при `wait` сохранить подготовленный payload и свериться по status. E2 — High/Extra High на сопоставимых страницах. E4 — два разворота: экономия только половины 0,8 с составляет ≈0,2% от 200 с; больший эффект требует замера накладных расходов. Дополнительно убрать **если обнаружен** повтор тождественного `normalized_text`: [контракт сам подставляет оригинал](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/c2f9f6be5dcf6f65a5e36b846f6e95301c67e629/src/regional_knowledge/contracts.py#L193-L208). Оценки E1/E2/E4 из плана — гипотезы, не гарантии. На выборке сверять строки/числа, порядок и стыки, границы, сущности, факты, настоящие story bodies, иллюстрации/подписи; не принимать ускорение за счёт пропусков.

5. **Шкипер + Импорт + Ответы: один пилот 1→2→3 окна, затем 24 часа выбранного режима.** По 10 новых страниц на окно на коротких ступенях; включить сложный скан, смену чата, штатную ротацию Kaggle и восстановление скрипта. Измерять суммарные полностью обработанные страницы/час, простои, BGE-ожидание, RAM/диск, поисковые p50/p95 и ошибки, отставание Saved. Нынешний [единый слот](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/c2f9f6be5dcf6f65a5e36b846f6e95301c67e629/src/regional_knowledge/bge_admission.py#L425-L430) не равен согласованным параллельным поискам. При их внедрении document encode тоже должен использовать общий forward-допуск: [native materializer сейчас вызывает encoder напрямую](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/c2f9f6be5dcf6f65a5e36b846f6e95301c67e629/src/regional_knowledge/kaggle_source_materializer.py#L786-L802). Эффект: доказанное число окон при живом пользовательском поиске, без второй BGE.

**Критерий результата:** stage accepted → TEXT → semantic → Saved измеряются отдельно; исходные 0,8 с без границы замера не описывают весь серверный труд. `finalized` [не означает завершение research](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/c2f9f6be5dcf6f65a5e36b846f6e95301c67e629/sql/kaggle/026_source_batch_activation.sql#L937-L961) и [не означает Dataset Saved](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/c2f9f6be5dcf6f65a5e36b846f6e95301c67e629/src/regional_knowledge/kaggle_native_source_intake.py#L490-L503). Следующая книга не ждёт отдельного checkpoint; итоговый счёт подтверждается Saved. В «100 книг» входят результаты без отложенного обязательного обогащения; facts-only допустим по содержанию, квоты историй нет. Для плохого скана — честный пропуск и признак неполноты, не выдуманный текст; для читаемой пропущенной строки — исправление. Входящие/claim/start остаются owner-personal; публичность каталога не открывает оригиналы.

### Что сознательно не делать; вопросы владельцу

Для пилота технически требуется непрерывно доступный браузер; поддержка трёх окон и восстановление автоскрипта пока требуют подтверждения.


## Раунд 2 — позиция RKB-Продукт по результату и вопросы (29.10.2026, вечер)

Требование владельца: **без «космолёта»**, минимум нового; прорабатывается вместе с RKB-Импорт (его зона). RKB-Импорт дополняет этот раздел.

### Что принимаем

- Поток внутри существующих intake, `telegram_original`, Launcher и автопродолжения. Без нового сервиса, очереди и реестра.
- Дедупликация по SHA-256 при первом скачивании в Kaggle. Повторный локатор того же файла ведёт в существующий импорт.
- Повторный `start` возвращает актуальный `status`/`next_action`, а не `next_cursor=0`. Это дефект, исправляется отдельно и первым.
- Пилот 1 → 2 → 3 окна с замером поиска и Saved. Учёт итогов — по Saved.
- **E4 снимаем:** по расчёту Pro выигрыш ≈0,2%.

### Где предлагаем проще

1. **Шаг 2 (закрепление читателя за книгой с поколениями) — не делать в v1.** Книгу окну назначает скрипт RKB-Импорт: название приходит в задании, его подсказывал и владелец. Модель не выбирает книгу сама. Тогда достаточно идемпотентного `start` и дедупликации из шага 1. Серверное закрепление вводим, только если в пилоте увидим реальный конфликт двух окон.
2. **Передача контекста при смене чата — без нового формата.** Первым действием в новом чате модель вызывает `book_ingest(status)`: он уже отдаёт `next_action`, хвост и курсор. Порядок и открытые единицы — в `book_find(view=units)`.
3. **Список входящих (шаг 1)** — переиспользовать то, чем Шкипер сегодня вручную собрал 32 книги topic 2. Не писать второй читатель Telegram.
