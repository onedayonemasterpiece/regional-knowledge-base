## Цель владельца

Наполнить базу: **100 книг меньше чем за месяц**. Это ~20–25 тыс. физических страниц, около **30 стр/ч круглосуточно, включая ночь**. Без потери качества и функциональности: дословный текст, смысловые фрагменты, границы статей и глав (из них собирается PDF), сущности, факты, истории, иллюстрации. Истории и сущности — важная часть базы, а не необязательное приложение. Борьба идёт за **общую скорость наполнения**, а не за секунды доступности одной книги.

## Как сейчас

- Архитектура зафиксирована: Kaggle — вычисления (PostgreSQL/pgvector + BGE-M3), Kaggle Dataset — хранение, Dev (DevCoveer) — MCP API и контроллер, без хранения корпуса. Верхний уровень не пересматривать.
- Читатель — окно ChatGPT с коннектором RKB MCP. Цикл: `book_ingest(start)` → `book_pages` (изображение разворота) → модель пишет дословный текст, регионы, фрагменты, границы, сущности → `book_ingest(stage)` → следующий разворот. Порядок чтения выбирает модель (PR 606).
- Окна запускаются через ChatGPT Launcher (`chatgpt_start` / `chatgpt_continue`). Ход окна заканчивается примерно через 8 страниц. RKB-Импорт сделал автопродолжение: скрипт ждёт `done` и шлёт «продолжай» в то же окно.
- Оригинал попадает в Kaggle двумя путями: вложение файла от модели (`fileParams`) или **`book_ingest(start, telegram_original=…)`** — Kaggle сам скачивает оригинал из архива Telegram (topic 2) по точному локатору, без передачи байтов через Dev или модель: `docs/operations/kaggle-native-original-intake.md`, раздел «Direct Telegram PDF ingress».
- Список книг к импорту (32 PDF/DjVu в topic 2) сегодня вручную собрал оператор и вручную же подготовил JSON для старта.
- Каталог уже импортированного: `book_find`.

## Замеры 29.10 (Albinus, плотный немецкий словарь, ~7 тыс. символов на разворот)

- Чистое чтение одного окна — **18–20 разворотов/ч** (~200 с на разворот; payload ~24 КБ JSON: 30–40 регионов, 25–35 фрагментов). Сервер stage→apply ~0,8 с.
- Остановки за день: отказ страницы без указания места (исправлено), сбой старта Kaggle, падение replay после rollout. Это отдельная работа, не тема задания.
- Поиск во время импорта: одно чтение в Kaggle одновременно, цикл ~450 мс (BGE encode 160–230 мс, SQL 30–50 мс, транспорт 100–200 мс). Владелец согласовал параллельные чтения: последовательна только BGE. Параллельный импорт нескольких книг владелец тоже согласовал.

План опытов: `docs/product/rkb-import-speed-rnd-20261029.md` (PR 633). Владелец **снял** E3 (обогащение отдельно: не ускоряет общее наполнение) и E5 (черновик OCR: модель всё равно выполняет свои операции). В работе: E1 (без per-page отчётов в Slack), E2 (режим рассуждения), E4 (2 разворота на stage), E6 (параллельные книги).

## Предложение владельца: «обратная схема» поточного импорта

1. Владелец выкладывает книги в хранилище (Kaggle Dataset или уже существующий архив Telegram topic 2).
2. Модель по MCP спрашивает, какие книги ждут импорта. Выбирает одну — или находит по названию из своего задания.
3. Импорт начинается без передачи байтов от модели: Kaggle берёт оригинал сам. Оригинал сразу оказывается в архиве (Telegram), обратная передача не нужна.
4. Несколько окон работают параллельно, каждое на своей книге, в том числе ночью. Закончив книгу, окно берёт следующую.

## Вопросы

1. Насколько предложение уже покрыто существующим (`telegram_original`, `book_find`, оригинальный intake)? Чего минимально не хватает? Например: MCP-список «ожидают импорта» и выбор книги без ручного JSON. Где граница «Dataset vs Telegram» как точка выкладки?
2. Как гарантировать «одна книга — один читатель» при нескольких окнах без нового сервиса: существующий acquiring/ingestion, идемпотентный start по книге, захват книги?
3. Поток без человека, в том числе ночью: окно закончило книгу или ход → следующее действие. Что уже даёт Launcher плюс автопродолжение, где точки потери (окно зависло, ход не продолжился, Kaggle остыл), как обнаруживать и продолжать без дублей?
4. Сколько окон параллельно реально выдержат Kaggle (один notebook, 4 CPU, одна BGE), поиск пользователей и Launcher (окна в браузере владельца)? Как это замерить?
5. Расчёт: при 18–20 разворотах/ч на окно сколько окон нужно для 30 стр/ч круглосуточно с учётом остановок? Какие ещё рычаги скорости одного окна ты видишь (кроме снятых E3/E5), с оценкой выигрыша и способом проверки качества?
6. Риски для качества и данных: дубли книг, частичные импорты, плохие сканы (перевёрнутые блоки, двойная экспозиция — оба случая есть в Albinus), права и ACL.

- что уже есть;
