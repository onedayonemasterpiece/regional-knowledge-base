## Цель и границы

Не повторять установку моделей и исходный benchmark. Продолжить результаты PR #26, commit `f77f78427984fd970c85339c7de4f53a0f253004`, и закрыть конкретные ограничения: полнота импортированного источника, независимая оценка релевантности и сравнение E5/Gemma, согласованность индекса batch-1 и batch-4. При наличии результатов устройства — оценить именно его query-векторы по сохранённой матрице документов.

Результат — не новая embedding-платформа, а проверенный отчёт, маленькие fixtures и тесты. Production corpus, active revision, схема БД, работающий поиск и provider configuration в этой задаче не изменяются. Никаких платных inference/API, новых внешних LLM, GPU или Kaggle. Разрешены локальные вычисления уже скачанных моделей, чтение явно указанного приватного источника и имеющихся результатов. Разбор и содержательная разметка книги остаются задачей ChatGPT: не внедрять серверный OCR/ASR/LLM и не заменять пропущенный текст выдуманными сведениями.

## A. Приоритет: полнота книги, а не только число страниц

Контрольное чтение выявило:

- `src/regional_knowledge/ingestion.py` содержит `MAX_NATIVE_BLOCK_TEXT = 1_000` и `text[:MAX_NATIVE_BLOCK_TEXT]`.
- Первый импорт был построен по `native_blocks` — ограниченным preview, а не полным проверенным регионам.
- В retained snapshot 712 чанков, 461233 символа, максимальная длина 1000; 200 чанков ровно по 1000 символов.
- Чанки есть на физических страницах 1–144. На 145–174 их нет, хотя эти страницы не следует считать автоматически пустыми: исходный PDF содержит сканированные иллюстрации с подписями.
- Проверка оригинала: содержание на физической странице 3 длиннее 1000; на физической странице 4 исходный native text длиннее импортированного. Сравнения сумм символов недостаточно для точной оценки потерь из-за различий extraction/layout.

Проверить это read-only против исходного PDF и active text projection. Не делать новый неявный импорт. Не публиковать PDF, распознанный текст, матрицы пользовательского корпуса или длинные фрагменты в Git.

Deliverable A: `docs/reports/gause-import-coverage-audit-20261004.md` и приватный page/region coverage manifest. Для каждой страницы отдельно: metadata exists / native text exists / clipped preview / coverage proven / image-only / requires ChatGPT visual review. Не выдавать hash/count equality за содержательную полноту.

При подтверждении clipping подготовить минимальный fix транспорта: явные original_length/truncated/continuation или ограниченные порции полного блока. Нельзя просто убрать лимиты и вернуть всю книгу одним гигантским MCP-ответом. Staging должен отличать полный материал от preview и запрещать подтверждать полноту лишь потому, что перечислены page IDs. Нужны unit tests на блок >1000, несколько порций, повтор продолжения и textless-page с изображением. Код и PR подготовить, production в этой задаче не выкатывать. Полную новую семантическую ревизию книги не создавать без её разбора ChatGPT.

Существующий benchmark остаётся полезным как сравнение encoder’ов на фиксированном неполном корпусе. Новый отчёт обязан так его обозначить. Recall по существующим чанкам не равен полноте извлечения из всей книги.

## B. Достаточно ли проверена релевантность

1. Сохранить исходные 30 вопросов и результаты неизменными. Новую разметку версионировать отдельно.
2. Проверить required-evidence groups и допустимые альтернативные чанки. «Релевантен по теме» и «содержит нужный факт» — разные уровни. Составные вопросы требуют всех фактов, а не одного тематического совпадения.
3. Добавить примерно 30 новых вопросов, источник и ответ проверены до запуска ranking. Включить перефразирование, отношения между людьми/событиями, отрицания, редкие имена и составные вопросы. Парафразы одного факта не распределять по независимым train/test частям. Сохранить минимум 10 сложных отрицательных/неразрешимых запросов: не только события 2026 года, но и неверная предпосылка, перепутанное лицо, требуемая деталь, отсутствующая в доступном источнике. «Нет в обрезанном snapshot» не означает «нет в книге» — это `source_gap`, не unanswerable.
4. Новые вопросы/разметку заморозить до просмотра кандидатов. Если исходник недоступен для доказательства, пометить item blocked, не придумывать qrel.
5. Объединить top-10 E5, Gemma и lexical; независимо разметить pool без названия модели и ранга. Степени: 0 нерелевантен/не подтверждает; 1 полезный контекст; 2 прямое доказательство. Не заменять разметку regex совпадением слов.
6. Рассчитать Precision@3/5/10 и nDCG@10 только с явным coverage judgment. Неизвестный relevance не считать автоматически нулём. Required-evidence Recall и all-evidence@10 сохранить отдельно. Показать natural/keyword/multi/paraphrase/negative slices и количество вопросов в каждой.
7. Если нет независимого второго разметчика, прямо назвать разметку model-assisted, а не независимой экспертной истиной. Для спорных позиций сохранить короткое обоснование и точный locator, пригодный для проверки ChatGPT.
8. Не называть 96.43% Recall «96.43% точных ответов». Конечная генерация ответа Мирой отдельно не проверена. В этой задаче не вызывать внешний платный judge и не запускать provider canaries.

## C. Узкий повтор E5 и Gemma

POTION заново не оптимизировать — есть достаточное доказательство слабого соответствия текущему сценарию. E5 и Gemma обе укладываются в ограничения: разницу 23/177 мс нельзя использовать как автоматическое доказательство превосходства качества E5.

Использовать сохранённые vectors/rankings там, где входы совпадают. Для новых query только локальный encoder. Предел 1 CPU / 1 GiB / swap=0. Приватный snapshot менять нельзя; документные embeddings не пересчитывать без необходимости.

Проверить batch-1 index против batch-4 index: исходный отчёт выбирает batch1 по throughput, но quality index был последним batch4. Нужны одинаковые вопросы, роли query/passage, pooling, normalization, модель и hashes. Показать max/cosine differences и изменения ranking, а не просто совпадение размерности. Не смягчать tolerances после того, как они провалились, ради PASS.

Lexical baseline сохранить как production simple/websearch AND, включая его нулевую выдачу на естественных вопросах. Второй разумный lexical baseline допускается только в lab, отдельно помеченным, с фиксированным алгоритмом. Не выдавать fusion с пустым lexical за доказанный выигрыш ансамбля и не менять production RPC.

Для разницы качества E5/Gemma показать per-query wins/losses, причины и неопределённость на малом наборе. При bootstrap единица resampling — вопрос/семейство вопросов, не чанки и не 104 повторённых latency-вызова. Не требовать статистической значимости любой ценой.

## D. Результаты устройства: оценить именно клиентские query-векторы

Диагностический стенд подготовлен в Projects Hub: `web/public/labs/embedding-benchmark.html`, ветка `chatgpt/device-embedding-lab-20261004`. Он выполняет E5 INT8 CPU/WASM, сравнивает 10 query/document пар, измеряет скорость и сохраняет 30 query-векторов в `rkb-device-embedding-run.v1` JSON. Приватную книгу/индекс в браузер не публикует. Отдельный evaluator находится рядом с этой постановкой/в переданном тестовом пакете как `evaluate_device_run.py`.

Когда пользователь передаст JSON, проверить schema, все hashes/версии, 30 уникальных qIDs, 384 finite components и L2 нормы. Выполнить brute-force и прежний RRF по той же сохранённой E5 document matrix. Никаких новых inference/API вызовов. Сравнить device queries → server documents с native server queries → same documents: Recall, MRR, multi coverage, top-k overlap, per-query rank changes. Не объявлять phone acceptance по desktop Chromium smoke.

Отчёты с interrupted/failed статусом сохранять как отказ/неполный запуск, не исключать молча из знаменателя стабильности. Ошибка общего JS bundle — ошибка стенда, не слабый телефон. PWA API не измеряет полный process RAM: `deviceMemory` — подсказка о ресурсе, а не измерение потребления. Native/RSS/PSS ADB профиль — опциональная отдельная фактическая проверка при подключённом устройстве.

## Deliverables и DoD

- Фактический corpus coverage audit; подтверждённая граница между preview и полным источником.
- Новый небольшой fixture и его источник/локаторы; исходные результаты не переписаны.
- Таблица E5 vs Gemma: доказательства/релевантность отдельно от latency; sparse/unjudged ограничения явно видимы.
- Проверка batch1/batch4 или доказанный конкретный blocker, не бесконечный поиск нового runtime.
- Unit tests метрик и входных контрактов; исходный suite зелёный.
- `docs/reports/embedding-retrieval-validation-followup-20261004.md` с одним решением: подтверждаем E5, выбираем Gemma или сохраняем неопределённость из-за source/labels; нельзя заранее назначить победителя.
- При наличии device JSON — отдельный датированный результат с моделью телефона/браузером со слов пользователя и реально измеренными метриками. При отсутствии файла этот подпункт pending, не blocker остальных результатов.
- Никаких production writes, paid inference, source text в Git или нового orchestration framework. Сохранённые evidence не удалять как мусор.

Не останавливайся на новом плане. Используй уже выполненную работу; исправляй только доказанные gaps. В конце дай ссылки на отчёт/PR, отдели `retrieval quality`, `source completeness`, `answer correctness` и `device compatibility` — это четыре разных результата.
