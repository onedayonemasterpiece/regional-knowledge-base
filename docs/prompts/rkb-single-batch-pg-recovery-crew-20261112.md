## 6. Минимальная реализация без WSS

Повторно использовать существующие компоненты репозитория `onedayonemasterpiece/regional-knowledge-base`:

- `src/regional_knowledge/recovery_journal.py` — формат и последовательность журнала;
- `control_spool.py` — exact command и outcome semantics;
- `kaggle_source_materializer.py`, `kaggle_source_batch.py` — уже существующее преобразование принятых source inputs;
- `kaggle_pg_snapshot_native.py` — существующие PG tools/backup semantics;
- соответствующие SQL migrations и исторические версии handler/compiler.

Наличие этих модулей не означает, что готовая автономная команда уже есть. `pg_snapshot_recovery.py` содержит online-оркестрацию и зависит от WSS: не запускать его старый controller как «автономное восстановление». Сделать тонкий конечный notebook entrypoint вокруг подходящей существующей логики. Не создавать альтернативный domain compiler или универсальный удалённый shell.

Перед реализацией применить [devserver-simplicity](https://github.com/onedayonemasterpiece/codex-devcoveer-mcp/blob/main/skills/devserver-simplicity/SKILL.md) и [kaggle-warm-debugging](https://github.com/onedayonemasterpiece/codex-devcoveer-mcp/blob/main/skills/kaggle-warm-debugging/SKILL.md).

Три основания изменения:

- Кто замечает: владелец не может получить восстановленную БД после утраты Dataset.
- Наблюдаемый дефект: полный журнал есть, готовый без-WSS batch entrypoint отсутствует; старый online restore многократно зависел от запуска контроллера и старого Saved.
- Корень: восстановление связано с online transport, хотя преобразование сохранённых команд можно выполнить внутри одной конечной задачи.

Бюджет первого адаптера: до 250 net production lines, без изменения protected materializer fingerprint и domain guards ради упрощения. Превышение обосновать конкретным недостающим компонентом; не уплотнять код и не вырезать смысл ради числа строк. В PR привести таблицу simplicity, net lines и что не добавлено.

Один обязательный различающий тест: частичный replay → реальный checkpoint → restore → продолжение, затем correction/rejected/unknown и повтор без дублей. Дополнительно сохраняется исходная проверка: без сети/WSS из вымышленного журнала с APPLIED, последующей correction, REJECTED и неизвестным исходом получается правильная БД; повторение **локального** шага с тем же operation key не создаёт дублей; исторический отказ не становится успешной записью. Тест должен падать на отсутствии/ошибке batch-пути и проходить после реализации. Не делать реальный Kaggle запуск ради RED/GREEN.

## 7. Содержание каждой конечной части

Линейная программа, а не сервер и не бесконечный цикл:

1. Загрузить один immutable входной пакет штатным разрешённым способом. Предпочесть один private input Dataset с одной версией, если нет уже действующего подходящего способа доставки. Не поднимать новый публичный file server/proxy. Подготовка этого входа не является публикацией итоговой PG.
2. Установить необходимые закреплённые зависимости и поднять один локальный PostgreSQL на loopback/Unix socket. Публичный listener, WSS, broker registration и controller callback не запускать.
3. Проверить входную цепочку, схему, версии и внешние зависимости; восстановить начальную базу из имеющихся допустимых данных. Не импортировать старые заблокированные ресурсы через другой аккаунт.
4. Выполнить команды в исходном порядке и с историческими executor/function/schema revisions. Сохранить исходные UUID, logical time, corrections и preconditions. Не применять старые команды безусловно через последний main и не подменять authority фиктивным grant.
5. Исторические APPLIED восстановить; исторические REJECTED отразить как отклонённые, без доменных изменений; NOT_SENT/SENT_UNKNOWN учесть отдельно. Пропуск из-за отсутствия зависимости — ошибка покрытия, а не повод переставить команды или сбросить guards.
6. Не выполнять заново принятые решения модели и внешние эффекты: Telegram-публикации, выдачу токенов, старые Dataset finalize, оригинальные user uploads. Восстанавливаются принятые данные и их квитанции. Не создавать новых readers и не читать все книги заново.
7. Если производные embeddings не сохранились, использовать существующий BGE-путь внутри этого же notebook при совпадающей модели, tokenizer и параметрах. Один вход не вычислять повторно без нужды. Не менять chunks, размерность, 512-token guard или модель ради ускорения. Если без индекса задача не укладывается, не объявлять полностью готовую поисковую БД; отразить ограничение до запуска в оценке реализуемости.
8. Проверить таблицы и связи: документы/ingestions, physical TEXT/SEM, chunks, истории с Variant.body, сущности, ссылки иллюстраций, исходные UUID и записи applied operations. Сопоставлять с локальными квитанциями/учётными snapshot, а не только общий COUNT.
9. Выполнить один WAL-consistent physical backup существующим PG-инструментом. По бюджету добавить переносимый compressed logical dump; если два полных формата не помещаются, физический backup и переносимые метаданные обязательны, отсутствие logical dump явно указать. Не архивировать изменяющийся PGDATA простым tar.
10. Проверить backup штатным `pg_verifybackup`, а затем реально восстановить его в отдельный временный PG-каталог **внутри этого же notebook** и проверить выбранные таблицы/связи и SQL-чтение. Это проверка результата, не второй Kaggle runtime. Предусмотреть её диск и время заранее.
11. Сохранить только конечный набор файлов в output, записать итоговый отчёт и завершить процесс PG/ноутбука обычным выходом. Не ждать команды с сервера и не поддерживать сессию после результата.

При неизбежной ошибке сохранить компактный обезличенный error report и имеющиеся промежуточные данные штатным output. Не перезапускать notebook автоматически. Успех по данным и успех по публикации различать.

## 8. Единственная публикация результата

Наименее сложный путь — использовать штатно сохранённый notebook output и создать из него private Dataset один раз после окончания успешного вычисления. Если выбран существующий publisher внутри notebook, единственный владелец публикации — он. Crew тогда только читает его квитанцию и не делает вторую публикацию. Выбрать **один** из этих путей до submit; не держать оба как соревнующиеся fallback.

Пакет версии 1:

- физический backup PG, сжатый штатным подходящим способом;
- manifest с версиями PG/extensions, исходным prefix, применённым покрытием, составом файлов и одним SHA/размером на внешний файл;
- `recovery-report.json` с coverage и фактическими проверками restore;
- читаемый `README` с командой/порядком восстановления и известными пробелами;
- опционально compressed logical dump в пределах бюджета.

Не включать исходный private журнал, credentials, `.env`, session-файлы Telegram, signed URLs или служебные upload grants в output. БД содержит приватные материалы: private Dataset обязателен, автоматический CC0 не назначать; метаданные прав должны соответствовать содержимому.

Перед create сохранить в существующем state/operation receipt имя результата, batch identity и факт попытки. Если ответ потерян, на следующем проходе найти результат **этой же** операции и прочитать receipt; отсутствие в одном listing не доказывает, что create не было. Не повторять неизвестный create и не добавлять новый suffix. Финальный Dataset остаётся версии1; промежуточные checkpoint версии допустимы в одном выбранном ресурсе.

Dataset `Ready` означает только provider publication. Проверить состав файлов и binding к успешному notebook output. Для заявления «данные независимо сохранены» нужна также закрытая копия вне этого Kaggle-аккаунта и проверка внешней передачи; не выдавать local notebook output за такую копию. Если независимое хранилище не настроено, выдать уже полученный проверенный Dataset владельцу и отдельно назвать незакрытый риск. Не скрывать готовый результат и не держать compute включённым ради отсутствующего места для второй копии.

Старые unknown Dataset intents не переносить как исполнимую очередь. Входной временный Dataset/outputs удалять лишь после проверенного результата и независимой копии, и только если очистка прямо включена в действующее поручение. Удаление ничего не должно доказывать о смерти compute.

## 10. Полезные действия на каждом проходе

| Что есть к началу прохода | Действие |
|---|---|
| Нет batch-кода/полных входов | Продолжить подготовку или исправление конкретного offline дефекта; Kaggle не запускать |
| Всё подготовлено, входы/аккаунт/ресурсы допустимы, submit отсутствует | Отправить пилот либо следующую разрешённую часть после проверенного checkpoint, terminal предыдущей и перерыва; сохранить receipt |
| Submit начат, ответ неизвестен | Разрешить исход этой попытки по существующей квитанции; новый submit не делать |
| Notebook работает | Один редкий status/progress read; при реальном blocker работать с кодом/артефактами, не продлевать compute искусственно |
| Notebook закончил вычисление | Получить привязанный к запуску report, проверить результаты и выполнить единственный выбранный путь публикации |
| Dataset processing | Следующий scheduled read того же результата, без новой версии |
| Dataset Ready | Проверить files/binding/restore proof; использовать уже доступное разрешённое независимое хранилище или сообщить об отсутствии второй копии, не продлевая compute |
| Всё подтверждено | Сообщить результат, paused=true |
| Нет разрешённого доступа, исчерпан бюджет или notebook terminal failure | Сохранить результаты и точный blocker; остановить бессмысленные запросы; не заявлять DONE |

Роль должна доводить разрешённые действия до результата; расписание не отменяет внешние ограничения. «Проверяю каждые 30 минут» — плановая частота Crew, не гарантия доставки каждого прохода.

### Конечный план пилота и перерывов (выбор реализации)

Пилот: общий ориентир20 минут от начала bootstrap, первые12 минут для bootstrap/модели/replay, оставшиеся8 минут — резерв для backup, pg_verifybackup, настоящего restore, coverage и выхода. Лимит replay проверяется только между транзакциями; уже начатый COMMIT не прерывается. Если bootstrap съедает рабочее окно, новых команд не применять, сохранить честную разбивку и доступный checkpoint. Размер резерва уточняется по фактическому пилоту; это не обещание непроверенного времени backup.

После terminal и сохранения результата планируется60 минут без compute. Это выбор исполнителя для реального перерыва, не дополнительное прежнее решение владельца. Следующая часть примерно2 часа включает сохранение и restore; её рабочий бюджет определяется временем пилотного сохранения с запасом. Предыдущий checkpoint должен быть реально проверен, затем использовать тот же prefix и неизменные operation keys. Частичный отчёт содержит next_sequence и accepted_last_sequence и не называется полной БД.

Профиль каждой части отдельно учитывает bootstrap, загрузку модели, encoder_seconds и устройство CPU/GPU, SQL/материализацию, backup, restore и сохранение; числа посещённых записей и уникальных фактически вычисленных входов отделены от полного журнала. Текущий worker закреплён на CPU; GPU совместимость не доказана и не вводится изменением precision/chunks/guards.
