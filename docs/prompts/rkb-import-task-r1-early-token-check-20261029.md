# Задание RKB-Импорт R1 (редакция 2): отказ 512 токенов называет фрагмент и число токенов

Заказчик: RKB-Импорт (Claude). Владелец 29.10: импорт должен быть надёжным — нестандартность не должна молча ломать или останавливать импорт.

## Наблюдение (живое, Albinus 28–29.10)

p59 и p60 Albinus: `book_ingest(stage)` ответил «принято», через ~30 с фаза text в Kaggle отказала `complete_native_input_exceeds_512_tokens`. Читатель не знал, какой фрагмент длинный и насколько: p60 стояла ~11 ч, p59 ушла дырой.

## Почему не проверка на Dev (редакция 1 отозвана)

Точный полный BGE-вход собирает и токенизирует только Kaggle (AGENTS: final-input tokenization в Kaggle; замечание Шкипера 29.10). Второй компилятор на Dev ради ранней ошибки — второй механизм, расходящийся с первым. PR 611 закрыт. Явный предел 512 в инструкции читателю — PR 610 (RKB-Ответы).

## Код (main)

`kaggle_source_materializer.py`, `NativeSourceCompiler._counts` (~строка 308–316): при превышении бросает `failure('complete_native_input_exceeds_512_tokens')` без указания фрагмента и счёта. Эта причина доходит до читателя через `rejected_reason` в status.

## Что сделать

В этой же существующей проверке включить в текст причины `chunk_key` (или, если ключа на этом уровне нет, `chunk_id`/порядковый номер фрагмента в пакете, который читатель может сопоставить) и фактическое число токенов, например `complete_native_input_exceeds_512_tokens:chunk_key=p60-c3:tokens=611`. Проверить, что это строка доходит до `book_ingest(status)` читателя без обрезки. Ничего больше.

## Чего нельзя

- Не переносить токенизацию/сборку входа на Dev. Не менять предел 512, токенизатор, правила нарезки, инструкции.
- Новые состояния, флаги, ретраи, проверки, режимы — нет.
