# Задание RKB-Импорт Н3b: конец статьи «до конца региона» без подсчёта символов

Заказчик: RKB-Импорт (Claude). Основание: план [§7 К… / аудит Pro F5](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/docs/rkb-import-efficiency-audit-20261027/docs/audits/rkb-import-efficiency-audit-20261027.md) и [план §8.4, шаг 3](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/docs/rkb-import-efficiency-audit-20261027/docs/audits/rkb-import-fix-plan-20261027.md). Цель владельца 28.10: скорость импорта без потери функций и качества.

## Цель для человека

На каждой странице словаря модель-читатель ставит ~20 отметок конца статьи. Для каждой она обязана сама сосчитать длину своего же транскрибированного региона в Unicode-символах (например, `offset: 986`). Это чистая арифметика, а не смысл: она стоит времени генерации и даёт ошибки, которые валидатор ловит не всегда (Pro F5: 985 вместо 986 молча обрежет последний символ). Нужно, чтобы модель могла сказать «статья кончается в конце этого региона», не считая символы, а длину подставлял сервер.

Граница остаётся решением модели: она сама выбирает `action=end` и конкретный `region_key`. Код только считает длину названного региона.

## Доказательства (main `40c9f6f1`)

- `offset` обязателен для всех отметок: `src/regional_knowledge/contracts.py:247` (`offset: int = Field(ge=0, le=8000)`).
- Проверка отметок по длине региона — в `StagePageInput.validate_local_graph`: `contracts.py` (блок `source_unit_boundaries`, ~стр. 322–342).
- Оба транспорта (inline и JSON-файл) проходят через модель `StagePageInput` до сериализации: inline — `server.py:~1653` (`page.model_dump(mode="json", exclude_none=True)`), файл — `stage_file.py:55` (`parse_stage_file`).

## Что сделать

1. В `StageSourceUnitBoundary` сделать `offset` необязательным **только для `action="end"`**. Для `start` он остаётся обязательным: отсутствие — ошибка валидации.
2. В `StagePageInput.validate_local_graph` для end без `offset` подставить `len(region.source_text)` названного региона этой страницы **до** остальных проверок порядка. Результат — обычное числовое значение, которое дальше сериализуется, как сейчас.
3. Обновить одну фразу в описании `book_ingest` (`server.py`, где про `source_unit_boundaries`): «для конца статьи на конце региона offset можно не указывать».

## Обязательные свойства (Pro F5)

- Явный `offset=0` и явный конец внутри региона не меняются; не использовать `offset or len(...)`.
- Длина — в Unicode codepoints исходного `source_text`, не `normalized_text`, не байты UTF-8.
- End без `offset` на неизвестный регион — ошибка, как сейчас.
- Принятые раньше пакеты не переписываются и при replay дают то же самое (у них `offset` всегда числовой).
- Inline и JSON-файл дают одинаковое каноническое числовое представление.

## Один различающий тест

Страница с двумя статьями в одном регионе: первая заканчивается внутри региона (явный offset), вторая — end без offset. После валидации у второй `offset == len(source_text)`, у первой — исходное число. Та же страница с явным `offset=len(...)` даёт побайтно тот же канонический пакет. `start` без offset → ошибка. На текущем main end без offset → ошибка валидации.

## Живая проверка — Шкипер

После слияния (RKB-Opus) и установки API: читатель на очередной странице ставит end без offset. `book_find(view=units)` показывает статью complete с правильным концом. По `import_timeline` сравнить время модели на страницу до и после.
