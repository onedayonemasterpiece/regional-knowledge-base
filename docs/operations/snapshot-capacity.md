# PostgreSQL snapshot capacity

The save pipeline uses one decimal 200 GB per-file upper bound from [Kaggle Dataset technical specifications](https://www.kaggle.com/docs/datasets), across upload grants, transfer tickets, Dataset pins, backup and restore configuration. This is a provider ceiling, not an account quota grant or a proof that a 200 GB database fits. A deployment can supply a lower measured budget using the existing configuration fields.

Native backup reserves workspace from the current owned PG file sizes, including tar headers. The backup directory and uncompressed archive coexist. It does not reserve twice the provider ceiling for a small database. Native archive and unpacked byte checks remain bounded; direct transfers stream chunks rather than loading an archive into RAM. Capture logs record required scratch and configured byte budgets, with a warning at 80% of the configured capacity. A live cluster can grow during backup, so the OS and final archive byte checks remain authoritative.

The provider also documents 200 GB for private datasets in aggregate. Available account quota, other datasets, archive plus control files, and retained versions must all fit; raising the code ceiling does not increase that quota. Retention remains current plus at most three old versions and preserves the sole verified recovery copy and unresolved provider operations. Do not rotate dataset names or accounts to evade limits. Capacity above the actual account allocation needs a separate approved storage design, rather than another larger constant.

The November 28 incident occurred before upload: pg_basebackup and pg_verifybackup passed, while an explicit 4 GiB unpacked budget rejected a 4,412,633,349-byte native tree. An 8 GiB archive / 16 GiB unpacked configuration completed backup and packing in 70.76 seconds on the same worker. Those values recovered the current save; they are not the intended capacity of the collection. Metadata tests above 8 GiB check the complete descriptor/configuration path without allocating a giant fixture. They do not prove that thousands of books fit or that provider upload/restore of a 200 GB snapshot meets the runtime deadline. Actual retained storage, backup/verify time and restore time must be measured as the collection grows.
