## F1. PR 489 (P0-2): детерминированная ошибка `source_command` не должна давать цикл падений

**Проблема.** Сейчас любое исключение `source_command` в транспорте → `ConnectionError` → reconnect → повтор той же команды. Если ошибка детерминированная (баг в материализаторе/apply, не связь с PG), получается цикл: каждый круг рвёт канал (теряются поиски в полёте), `outage_started` не сбрасывается без 30 с стабильной сессии, через `reconnect_grace_seconds`=600 с — `BgeChannelStopped`, worker завершается; новая сессия восстанавливается и падает на той же команде.

**Существующий механизм.** `kaggle_source_commands.py` `WorkerSourceExecutor.__call__` уже превращает подтверждённый откат (`psycopg.Error`) в канонический отказ: `apply_accepted(..., reject_reason='native_source_sql_rolled_back')`. `apply_accepted` сначала ищет итог по `operation_key`/`sequence` в `applied_ops` — если команда уже применена, вернётся записанный итог, а не отказ.

**Сделать (в ветке PR 489).**
1. В `WorkerSourceExecutor.__call__` любое неожиданное исключение из материализатора или `apply_accepted`, **кроме** `ApplyUnknown`, `PermissionError`, `StaleWriter`, обрабатывать так же, как `psycopg.Error`: установить `reject_reason='native_source_sql_rolled_back'` и выполнить существующий вызов `apply_accepted(..., reject_reason=...)`.
2. В транспорте (`bge_wss_transport.py` `_encode`) путь `ConnectionError` для `source_command` оставить только для `ApplyUnknown` (после двух уже существующих попыток в executor). Прочие исключения `source_command` сюда больше не доходят; если всё же дошли — прежнее поведение PR 489.

**Нельзя.** Новые reason-коды, счётчики попыток, состояния, карантин; трогать `kaggle_apply.py`, Dev admission, heartbeat.

**Бюджет.** ≤ 12 строк production добавлено к текущему PR 489.

**Тест (один, заменяет нужный в PR).** Реальный `WorkerSourceExecutor` с материализатором, бросающим `RuntimeError` → возвращается receipt `rejected_precondition` с `reason=native_source_sql_rolled_back`; повторный вызов той же команды → `duplicate=True`, тот же итог; reconnect не происходит.

## F2. PR 488 (P1-3): один разворот манифеста книги на строку, а не три

**Проблема.** `038_source_passage_packet_metadata.sql` вызывает `rkb_v4.read_source_manifest_v1(p.source_id)` трижды на строку (catalog, pages, regions), строк до 5 → до 15 полных сворачиваний манифеста книги на один fetch. `source_batch_manifest_v1` (026, ~L964) сворачивает все пакеты книги (DISTINCT ON по pages/regions/passages) — на большой книге это задержка на критическом пути fetch.

**Сделать (в ветке PR 488, только файл 038).** `FROM ... CROSS JOIN LATERAL rkb_v4.read_source_manifest_v1(p.source_id) AS f(manifest)`; `pages` и `regions` брать из `f.manifest`; `catalog` вернуть как было до PR: `m.manifest->'metadata'`.

**Бюджет.** Не больше текущих 16 строк файла.

**Тест.** Существующий тест PR 488 (книга из 2 пакетов, второй пакет с непустыми pages/regions) — без изменений.
