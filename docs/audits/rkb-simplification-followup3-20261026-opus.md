## P0-5. Ответ поиска не должен стоять в очереди за служебными кадрами

**Причина по коду (проверено RKB-Opus на `main`).** Ответ поиска на обеих сторонах пропускается вперёд служебными кадрами, а служебные кадры на Dev могут ждать секунды:
1. **Kaggle-worker отправляет освобождение ресурса раньше результата.** `scripts/production/bge_wss_transport.py`: исходящая очередь приоритетная, меньший приоритет уходит первым; результат чтения кладётся с `priority=1` (L500), а `RESOURCE_RELEASED` и `HEARTBEAT` — с приоритетом по умолчанию 0 (L467, L516, L541, L577). Оба кладутся в одном проходе `states()` до того, как writer их заберёт, — уходит сначала RELEASED, потом QUERY_RESULT. Комментарий рядом прямо говорит обратное намерение («Preserve the completed result before advertising compute release»).
2. **Dev обрабатывает RELEASED в основном приёмнике и ждёт там замок admission.** `bge_channel.py` L413: `RESOURCE_RELEASED` → `shared.resource_released` → `async with self._lock` (`bge_admission.py` L382). Этот же замок держит `next_channel_work` (L418–420) **на всё время** выбора durable-задания, включая синхронную запись `_claim_specific` (L507: SQLite `BEGIN IMMEDIATE`, ожидание блокировки до 5 с) и `dispatch_payload` (L512–516; для части фаз — вызов Kaggle API). Во время рендера страницы `book_pages` такие задания создаются каждые 2 с (опрос `snapshot_status`), во время checkpoint — тоже. Пока приёмник ждёт замок, QUERY_RESULT, пришедший следом, не читается.
3. **HEARTBEAT на Dev — тоже в основном приёмнике** (`bge_channel.py` L509): `queue.heartbeat` — пишущая транзакция SQLite (`BEGIN IMMEDIATE`, до 5 с ожидания писателя), каждые 20 с.

**Сделать.**
1. Worker (`bge_wss_transport.py` `queue_read_result`, L500): класть результат чтения с тем же приоритетом, что и служебные кадры (`priority=0`), чтобы он уходил в порядке постановки — **раньше** освобождения ресурса, как и задумано. Приоритет `priority=1` для durable-результатов (`RESULT`, `SOURCE_COMMAND_RESULT`, `RECOVERY_PHASE_RESULT`) не трогать.
2. Dev (`bge_channel.py`): добавить `'HEARTBEAT'` в существующий список кадров, уходящих в служебную задачу (L386, рядом с `RECOVERY_PHASE_RESULT`…`SOURCE_COMMAND_RESULT`). Обработчик HEARTBEAT не менять.

**Нельзя.** Менять замок admission, `next_channel_work`, порядок/семантику RESOURCE_*, durable-приоритеты, таймауты; добавлять таймеры, ретраи, логи.

**Бюджет.** ≤ 3 изменённые строки production.

**Тест (один).** Реальный `channel_route` + поддельный worker: замок admission удерживается 1,5 с (имитация медленного `_claim_specific`); worker присылает результат чтения и освобождение ресурса за один проход `states()`; `finish_read` вызван раньше, чем через 200 мс.

**Живая проверка (Шкипер).** Повторить исходный 3-часовой прогон 1/мин, с рендером страниц и checkpoint в окне прогона. Критерий: 0 `deadline_exceeded`, MCP p95 ≤ 1500 мс. Параллельно, только чтение: для 7 прошлых сбоев сопоставить время с `jobs.updated` (recovery_phase/source_command, claimed) и с HEARTBEAT ±2 с — подтвердит или опровергнет причину независимо от правки.

## P0-6. Владелец Telegram-слота должен попадать в штатную сверку после ротации

**Продукт.** После ротации Kaggle новый run 159 был готов для поиска, но **не** для импорта: Telegram-слот архива остался за старым run 144, и импорт новой книги не мог начаться. Шкипер восстановил вручную штатной операцией.

**Причина (Шкипер, подтверждено ссылкой на код).** `bge_queue.py` ~L1112–1119 `_provider_owner_ids` собирает current/successor/shared/writer, но не владельца `rkb_telegram_session_lease`; контроллер вызывает сверку только для этого набора, поэтому старый run не получает штатную проверку завершения.

**Сделать.** Готовый патч Шкипера `telegram-owner-reconciliation-proposal.patch` (2 строки: добавить владельца существующей аренды в тот же набор) — оформить PR как есть, с его 4 регрессиями. Автор — Шкипер.

**Нельзя.** Новые очереди, ожидание старых UNKNOWN, ручной сброс аренды.

**Бюджет.** 2 строки production.
