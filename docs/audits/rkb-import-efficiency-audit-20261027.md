## Итог одной фразой

Сам импорт не замедлился в 3–5 раз: страница Albinus содержит в ~4–5 раз больше текста, чем страница Трауготта, и по символам в час чтение идёт с той же скоростью. Реальные потери — простой между отладочными блоками (~60% времени за последние 3 часа) и отладочная обвязка в промпте читателя (сверки через fetch, отчёты в Slack, ожидание apply). ## 3. Доказательства по коду

### 3.1. Границы статей ставит модель по смыслу — и начало, и конец

Решение владельца (27.10, уточнение к #504): где начинается и где кончается глава или статья, определяет модель, читающая страницу, по логике текста. Код не выводит эти границы сам. Поэтому **явный end от модели остаётся на каждой единице**, в том числе когда сразу за ней начинается следующая. Предложение первой редакции аудита «не ставить end перед следующей статьёй» **отозвано**.

Для чего это нужно. Функция «полный текст главы в PDF» — новая генерация документа из принятого при импорте дословного текста регионов внутри логической единицы, а не нарезка оригинала. Поэтому она одинакова для любого формата источника ([`source_unit_pdf.py:73-87`](../../src/regional_knowledge/source_unit_pdf.py#L73-L87)) и целиком зависит от точности границ, поставленных моделью.

Что дорого в нынешней форме end, по коду:
- `offset` — обязательное целое в Unicode-символах ([`contracts.py:247`](../../src/regional_knowledge/contracts.py#L247)). Для end в конце региона это длина собственного транскрибированного текста (например, 986). Счёт символов — арифметика, а не смысл: модели он труден, а ошибку отвергает валидатор ([`contracts.py:322-342`](../../src/regional_knowledge/contracts.py#L322-L342)).
- Читатель ставит такой end у ~20 статей на страницу (p38 — 20, p40 — 21, p41 — 18).

Найденная детерминистика в коде (вопрос, не правка): если модель не поставила end, следующий start того же вида сам закрывает предыдущую единицу ([`source_units.py:101-110`](../../src/regional_knowledge/source_units.py#L101-L110), тест [`test_source_unit_anchors_p0a.py:102`](../../tests/test_source_unit_anchors_p0a.py#L102)). Это вывод границы кодом, а не моделью. Если модель end забыла, буква раздела или рисунок между статьями молча попадут в текст предыдущей статьи. Оставить ли это правило или требовать end от модели явно — решение RKB-Продукта / RKB-Opus (§5, Р5).

### 3.2. Сервер разрешает читать следующую страницу, пока применяется предыдущая

- Следующий stage отвергается с `prior_write_pending`, пока предыдущий не применён: [`kaggle_importer.py:706-716`](../../src/regional_knowledge/kaggle_importer.py#L706-L716). Это обычный отказ, данные не теряются.
- `book_pages` проверяет только квитанцию оригинала и не ждёт apply: [`kaggle_importer.py:973-986`](../../src/regional_knowledge/kaggle_importer.py#L973-L986).
- Инструкция же велит: «For next_action=wait, call status» ([`server.py:653`](../../src/regional_knowledge/server.py#L653)). Читатель ждёт apply (47–83 с), затем делает readback и только потом открывает следующую страницу.

### 3.3. Readback через fetch кодом не требуется

- APPLIED виден в `status`: `state=staged, next_cursor=N+1, next_action=continue_pages|continue_tail` (сообщения читателя p39/p40, [`kaggle_native_source_intake.py:404-449`](../../src/regional_knowledge/kaggle_native_source_intake.py#L404-L449), [`:649`](../../src/regional_knowledge/kaggle_native_source_intake.py#L649)).
- `fetch` отдаёт не больше 8 чанков (схема MCP fetch: `limit` ≤ 8), поэтому страница из 20 чанков — это 3 вызова и ещё ~7 тыс. символов в контексте. При правиле «одно окно на всю книгу» каждая сверка удваивает рост контекста на страницу. Это главный риск для книги в сотни страниц.

### 3.4. Картинка страницы для плотного разворота — 1280 px

- Рендер пробует 1600, затем 1280 px по длинной стороне при лимите 256 КиБ: [`kaggle_djvu_pixels.py:29`](../../src/regional_knowledge/kaggle_djvu_pixels.py#L29), [`:212`](../../src/regional_knowledge/kaggle_djvu_pixels.py#L212). У Albinus все страницы приходят 1280×905 (аудитор p39–41, p46/48), то есть ~640 px на печатную страницу с двумя колонками мелкого шрифта.
- Последствия: повторное чтение спорных имён (p39), лишняя буква в адресе (p48), оговорка аудитора о «неопределённости в мелких графемах». Это качество и время модели, но выигрыш надо замерить (Н4).

## 4. Правки по убыванию выигрыша

Бюджет строк — только production. Прогноз выигрыша — до таблицы Шкипера; подтверждать парным сравнением минут между stage-сообщениями на соседних страницах.

### Н1. Одно окно читает книгу до конца, без отладочных блоков и пауз на аудит

- Выигрыш: 3,3 → 7–10 стр/ч за 3 часа (×2–3), простой 60% → <15%.
- Код: 0 строк. Это процесс, решение владельца уже есть ([RKB-Продукт 10:32](https://mira-projects.slack.com/archives/C0C8RT9JB2P/p1793089920425099)).
- Различающий тест: нет, это не код.
- Живая проверка (Шкипер): стр/ч и доля простоя по журналу stage за 3 часа.
- Кто заметит: владелец — сразу, по числу книг в каталоге за день.
- Маршрут: (б) RKB-Продукт / владелец — кто принимает основное чтение Albinus после p51 (запрос Шкипера 10:20).

### Н2. Промпт основного читателя без отладочной обвязки

Убрать `status` перед страницей, `fetch`-сверки принятого текста и отчёты в Slack на каждую страницу. Оставить один `status` перед следующим stage, отчёт раз в 10 страниц и при BLOCKED.

- Выигрыш (прогноз): 1–2 мин/стр из 5,7–8,5. Рост контекста на страницу ~в 2 раза меньше, значит длинная книга дольше держит темп в одном окне.
- Код: 0 строк, текст промпта читателя.
- Различающий тест: не код. Проверка — две соседние пары страниц с обвязкой и без.
- Живая проверка (Шкипер): минуты между stage-сообщениями p_N и p_N+1 до и после; в логах API нет fetch от читателя.
- Кто заметит: читатель — на каждой странице; владелец — по стр/ч.
- Маршрут: (б) тот, кто ведёт основное чтение (RKB-Продукт по предложению RKB-Opus), промпт — в задании Н3.

### Н3. Ожидание apply и форма end без счёта символов

Две независимые части; правки не запускаются до выводов ChatGPT Pro.

**Н3a. Читать следующую страницу, пока применяется предыдущая.** Пункт 6 чеклиста (`server.py:653`): «after stage returns wait, read the next page with book_pages and prepare its packet; call status once right before the next stage; prior_write_pending means resend the same stage after status».
- Выигрыш (прогноз): ~1 мин/стр (apply 47–83 с).
- Бюджет: ≤ 2 изменённых строки инструкции.
- Различающий тест: текст чеклиста содержит «read the next page with book_pages» и не содержит прежнего «For next_action=wait, call status».
- Живая проверка (Шкипер): минуты между stage-сообщениями соседних страниц до и после.
- Кто заметит: читатель — на каждой странице.

**Н3b. End «до конца этого региона» без числа.** Модель так же решает по смыслу, что статья кончается на этом регионе, но не считает его длину: `offset` у end можно опустить, и сервер подставляет длину того региона, который модель назвала. Граница — решение модели, код выполняет только арифметику.
- Выигрыш (прогноз): нет счёта символов для ~20 end на страницу, меньше отказов валидатора. Отметки и границы те же.
- Бюджет: ≤ 8 строк в `contracts.py` (необязательный `offset` только для end) и одна фраза инструкции.
- Различающий тест: страница с end без `offset` даёт те же `end_anchor` и `source_spans`, что с явным `offset=len(region)`; end без `offset` на чужой регион отвергается.
- Живая проверка (Шкипер): `book_find(view=units)` после страницы с новой формой — те же complete-единицы.
- Кто заметит: читатель — на каждой странице словаря или энциклопедии.

Маршрут: правки не запускаются до выводов ChatGPT Pro. Первая редакция задания (`docs/rkb-import-task-stage-guidance-20261027`) и draft-PR 573 реализуют отозванный вариант — **PR 573 не сливать**.

### Н4. Чёткость картинки плотного разворота

Гипотеза: при 256 КиБ разворот в градациях серого (JPEG `L`) поместится в 1600 px, а не в 1280.

- Выигрыш (прогноз): меньше перечитываний и ошибок в буквах. Цифр нет.
- Код: сначала 0 строк — замер. Правка ≤10 строк в `kaggle_djvu_pixels._jpeg`, только если замер покажет 1600 px в лимите.
- Различающий тест (если дойдёт до кода): у одного и того же PPM-разворота серый JPEG при 1600 px ≤256 КиБ, а у RGB — нет.

### 9.2. Критические замечания

#### F1. Н3a опирается на другой путь исполнения; status выполняет продвижение пакета

**Механизм в коде, высокая значимость для предлагаемой инструкции.** Ссылка §3.2 на `kaggle_importer.py:706–716` недостаточна: при native intake `_stage` немедленно передаёт работу в `NativeSourceIntake.stage` ([развилка][c-import-stage]). В этом пути пакет проходит отдельные команды:

| Команда/компонент | Что подтверждает её результат |
|---|---|
| `stage` | Пакет принят как `staged_inactive`; это ещё не опубликованный текст |
| `batch: text` | Публикация текстовой части |
| `batch: semantic` | Отдельное применение семантической части |
| Dataset checkpoint | Отдельное подтверждение сохранности; не тождественно перечисленным APPLIED |

[Код результатов][c-commit-progress] различает эти компоненты. `status` вызывает `_drive`, затем `_packet_progress`; последний выбирает и создаёт следующий `text` либо `semantic` ([status][c-status], [progress][c-progress]). В проверенном фоновом пути receive/reconcile фиксируется результат уже существующей команды, а не автоматически создаётся вся следующая цепочка ([dispatch][c-dispatch]).

**Различающий случай:** stage N вернул `wait`; модель пять минут готовит N+1. Если до этого была создана только команда stage, первый последующий status может лишь согласовать её и запустить text. Следующий stage ещё рано отправлять. Задержка передвинулась после чтения, а не исчезла. [Существующий тест][t-status] последовательно выполняет `finish → status` для stage/text/semantic. [Другой тест][t-early] специально защищает семантику предыдущего пакета при раннем следующем stage.

**Что сохранить из Н3a:** `book_pages` действительно не требует завершения предыдущего apply ([код][c-pages]); предварительно увидеть следующую страницу можно. **Что исправить:** снять обещание «~1 мин скрывается» и требование «ровно один status». Следовать фактическому `next_action` исходной операции; визуальная подготовка следующей страницы не означает разрешения записать её. Проверка наличия слов в инструкции не доказывает такую последовательность. Для локальной правки полезен один различающий сценарий с задержанными stage/text/semantic в существующей fixture, без новой машины состояний.

#### F2. «prior_write_pending → повтори stage» слишком широко

**Механизм в коде.** На native-пути разные ситуации дают разные ответы ([сравнение pending payload][c-native-stage], [защита предыдущего пакета][c-prev-packet], [admission][c-admission]):

| Ситуация | Значение для читателя |
|---|---|
| Прежний stage ещё не согласован; прислан другой payload | Возможен `native_pending_payload_changed`, а не `prior_write_pending` |
| Stage уже применён, но предыдущий пакет ещё обогащается | Может вернуть `processing` / `previous_packet_applying`; эта ветка предлагает повторить **этот ещё не принятый** следующий пакет после status |
| Неопределённый исход или недопустимый pending prefix | `prior_write_pending` не доказывает непринятие исходной попытки |
| Подтверждённый SQLITE_BUSY до принятия stage | Узкий ответ `source_stage_not_accepted_retry_same_stage` позволяет повтор того же входа |
| Потеря ответа после сохранения команды | Сначала согласуется исходная команда; timeout не разрешает новую операцию |

Защита от изменённого pending payload уже существует — это сильное контрдоказательство против предположения, что ранняя подготовка неизбежно портит данные. Но отказ защищает данные ценой лишнего хода и не делает любую инструкцию повтора правильной. **В Н3a следует убрать безусловный retry по одному имени `prior_write_pending`, сохранив существующие точные исходы и IDs.** Новые retries, флаги и recovery-пути для этого не нужны.

#### F3. Курсор просмотра, опубликованный результат и Saved нельзя объединять

**Механизм в коде.** Pending-ответ native stage не обязан иметь `next_cursor`; продолжение дополняется на status из принятого research либо applied-page cursor ([native output][c-output], [research continuation][c-research]). Курсор `book_pages` означает следующую выдачу изображения, а не подтверждение принятия предыдущей страницы.

Также `stage APPLIED`, `text published`, `semantic applied`, `projection current` и `Dataset Saved` — разные факты. Код разрешает продолжение на проверенном APPLIED при ещё не завершённом durable outcome ([settlement][c-settle]); reading finish отдельно инициирует checkpoint ([результаты][c-commit-progress]). Сам [DONE p39–41][reader3941] честно отличает `864/864` от неподтверждённого Dataset Saved=864.

**Следствие для Н2:** убрать можно заведомо дублирующий status в непрерывном ходе. После обрыва окна, неясного ответа, смены runtime или при `continue_tail` status имеет самостоятельную функцию. Нельзя восстанавливать принятие по одному курсору ранее просмотренного скана. Это не требование ждать Dataset перед каждой страницей — такого нового барьера аудит не предлагает.

Для интервалов 47–83 с нужно назвать компонент и начало/конец измерения: stage-submit → receipt, stage → создание text, text → первая успешная выдача или semantic completion. Без этого «минута сервера» не воспроизводится.

#### F4. Отсутствие body не делает needs_context пустым

**Механизм в коде; риск потери функций §0.** В `_semantic` сначала создаётся finding с `proposition`, evidence, `event_dates`, `observations`, `entity_keys`; только затем проверяется наличие `basic_variant`. Без body finding остаётся, а для `needs_context` дополнительно сохраняется pending ([materializer][c-findings]). Следовательно, эти записи могут быть носителями фактов и дат независимо от Story.

В замере Albinus39–45 действительно сообщены 19 candidates, из них 18 needs_context и 1 facts_only, body=0. Это не доказывает ни 19 пустых записей, ни отсутствие извлечённого знания. `knowledge_reviewed=true` — аттестация выполненного рассмотрения, а не замена самих утверждений и evidence ([контракт][c-page-contract]).

**Минимальное решение Н6:** убрать навязанную квоту и неподкреплённые «кандидаты на будущее», если такие действительно есть. Не удалять candidates только по `body is None`. Сначала ответить, какие поля и потребитель полезны в конкретных уже сохранённых записях. Сам аудит private содержимое этих 19 записей не исследовал. Отдельная таблица/сервис для этого не требуется.

#### F5. Н3b обоснован только как нормализация точного конца региона

**Механизм в коде; направление поддерживается с ограничениями.** Допустимое правило: модель выбирает `action=end` и конкретный `region_key`; опущенное числовое смещение означает ровно конец **исходного `source_text` этого региона**. Это не угадывание конца статьи кодом, если модель явно выбрала такой смысл.

Однако фраза §3.1 «ошибку отвергает валидатор» неверна в общем. [Валидатор][c-anchor-validation] проверяет диапазон, порядок, существование региона и уникальность. Для синтетического региона длиной 986 символов ошибочный end=985 может пройти и обрезать последний символ; end=987 будет отвергнут. Семантический конец валидатор не знает. Частота подобных ошибок в живом импорте не измерена.

Нормализацию нужно выполнить **до сериализации и сохранения канонического входа**, а не только в читающей проекции: inline вызывает model_dump ([MCP][c-inline]), file-путь тоже сериализует проверенный объект ([stage_file][c-stagefile]); SQL читает markers из сохранённых stage bytes ([SQL44][c-sql44]), resolver ожидает числовой `offset` ([resolver][c-resolver]). Простое объявление поля optional без разрешения значения до сохранения недостаточно.

Существующие свойства, которые должны сохраниться в этой маленькой правке:

- `start` без числа и end на неизвестный регион остаются ошибками.
- Явный `offset=0` и явный конец внутри региона не меняются; выражение `offset or len(...)` здесь неверно.
- Длина считается в Unicode codepoints исходного текста, не в UTF-8 bytes, UTF-16 units, видимых графемах или `normalized_text`.
- Порядок событий проверяется после разрешения опущенного значения; принятые старые payload не переписываются.
- Inline и JSON-file приводят эквивалентные новые входы к тому же числовому представлению до фиксации операции.

**Различающий случай:** две статьи делят один регион: первая заканчивается внутри него, вторая — в конце. Текущий [I03][t-units] поддерживает такой случай. Н3b применим ко второй; первая сохраняет точный внутренний offset. Поэтому нельзя обещать отмену подсчёта смещений вообще или экономию всех 9% end-разметки. Основная структура end остаётся.

#### F6. Р5 пропустил автоматическое закрытие по EOF и последствия смены семантики

**Механизм в коде.** Помимо `next_boundary`, resolver при `read_complete` и отсутствии пропущенных физических страниц закрывает открытые units на последнем непустом регионе источника с `close_reason=verified_eof` ([код][c-autoclose]). Это закреплено I04, включающим последнюю сноску ([тест][t-units]).

Сильнейший аргумент в пользу нынешнего `next_boundary`: если A и B действительно смежные, подтверждённое моделью начало B даёт корректный полуоткрытый конец A; I02 это проверяет. Но начало B не утверждает, что вся промежуточная буква раздела, подпись или издательский текст принадлежат A. Аналогично, конец просмотренного источника не всегда является смысловым концом последней статьи: после неё может идти указатель или колофон.

[Уточнение владельца в координации][owner-boundaries] требует модельного начала и конца. **Рекомендация:** для новых инструкций сохранять явные end; не возвращать отозванный вариант PR573. Вопрос согласования уже действующего resolver с этим решением должен охватывать оба автозакрытия и судьбу ранее выданных complete units. Удалить правило под видом косметической оптимизации нельзя: один и тот же принятый источник может начать давать другую полноту/доступность units.

Дополнительная граница текущего контракта: одновременно открыт максимум один unit каждого `kind`. Два вложенных `section` не могут оставаться открытыми вместе: новый start закрывает старый. Это вопрос о требуемой структуре книги, а не предложение немедленно добавлять новую иерархию, таблицы или поля.

#### F7. Точные границы необходимы, но недостаточны для полного PDF

**Механизм в коде.** Генерация из принятого текста действительно не зависит от того, пришёл оригинал как PDF или DjVu. Но это не означает поддержку любой внутренней структуры. `_blocks` требует полный набор spans, отвергает `needs_review` и принимает только BODY/HEADING; значимые FOOTNOTE/TABLE/CAPTION/FIGURE/MARGINALIA сейчас дают явный отказ ([рендерер][c-pdf], [тесты][t-pdf]). Есть отдельные ресурсные пределы и требования к библиографии/меткам страниц.

Поэтому `book_find(view=units) → complete` не доказывает PDF-ready. В публичной выдаче units spans ограничены preview до 16 ([read path][c-units-read]); усечённый preview также не полный вход для PDF.

**Контрпример:** точные start/end и принятая сноска → complete unit, но `unsupported_structure:footnote` при PDF. Нельзя убрать сноску ради прохождения рендера. Проверка Н3b «те же end_anchor/source_spans» полезна как доказательство эквивалентности формы stage, но не закрывает пользовательскую выдачу полной главы. Это отдельный существующий объём PDF, а не повод расширять Н3b до нового проекта.

#### F8. Fetch-readback не равен status, хотя полный повтор каждой страницы может быть лишним

**Разделение обязанностей.** Status отвечает о ходе принятой операции и продолжении. Fetch показывает реально опубликованный текст, который получает потребитель. Он может выявить неполноту выдачи, потерянный фрагмент, неправильную связь или впервые опубликованный хвост. Поэтому оценка §2 «ничего сверх status» неверна.

Сильное контрдоказательство в пользу Н2: код не требует полного fetch каждой страницы для допуска следующей записи. Один и тот же полный текст не обязательно перечитывать основным читателем и аудитором подряд. **Разумное удаление — дублирующая сверка в обычном ходе**, при сохранении независимого выборочного аудита, адресной проверки выявленной ошибки и предусмотренного контрактом readback настоящего Story body ([AGENTS][agents]).

Новый tail предыдущей страницы, опубликованный вместе со следующей, — не повтор старого проверенного результата. [DONE p39–41][reader3941] отдельно оставляет p41 tail непубликованным. Если впоследствии он впервые стал доступен, его проверка имеет самостоятельную ценность. Это не новый обязательный page gate.

#### F9. Сравнение плотности верно по направлению; «скорость та же» и «60% простоя» не установлены

**Пересчёт по числам самого исходного аудита:** среднее Трауготта по трём страницам = 1355 символов; без карты = 1755. Albinus = примерно 7078. Соотношения 5,22 и 4,03 объясняют, почему физические страницы/час плохо сравнимы. Но это разные книги, дни, жанры, контракты и размеры пакетов, а не парный эксперимент. Пересечение прогнозных диапазонов 35–90 и 50–75 тыс. символов/ч не доказывает равенства скоростей.

Есть и арифметические несостыковки §1.2:

- p42…p48 включительно — **7 страниц**, не 6.
- 09:47:43 → 10:25:00 — **37 мин 17 с**.
- 25 мин 20 с + 37 мин 17 с = **62 мин 37 с**, не 72 мин; даже диапазон 34–38 мин даёт 59:20–63:20.

Из этого **не следует новая точная оценка простоя**. Остаток 180-минутного окна содержит отказ до приёма, reboot, назначения, проверки и интервалы с неизвестной деятельностью. Считать весь остаток устранимым ожиданием нельзя. [Позднее наблюдение p50][p50] особенно важно: изображение выдано, неприменённых source-команд нет, а stage долго не приходит; это не ожидание apply. Сообщение координатора о Launcher — полезная гипотеза/операторский диагноз, но данный аудит не проверял его runtime.

Защищаемая формулировка: **«Плотность объясняет часть видимой разницы страниц/час; имеющихся данных недостаточно, чтобы установить величину замедления или доказать его отсутствие. Есть организационные паузы, но их устранимая доля ещё не разложена».** Выигрыши Н1, Н2 и Н3a могут пересекаться; их нельзя складывать.

#### F10. Новый фактический замер важнее синтетического профиля p40

[Шкипер][timings] сообщил следующие данные; они относятся к выбранным пакетам, а не ко всей книге:

| Показатель | Albinus | Трауготт |
|---|---|---|
| Выборка model JSON | p39–45, 7 страниц | p3–7, 5 страниц |
| UTF-8 bytes | 245 695; 35 099/страницу | 82 417; 16 483/страницу |
| `story_candidates` | 28 349 bytes = 11,54% | 24 016 bytes = 29,14% |
| Candidates / непустые body | 19 / 0 | 10 / 7 |
| Source-unit markers | 259 | 0, старый контракт |
| Внутренняя `original_pages` фаза | 111,8–180,9 мс | Другой счётчик created→updated, напрямую не сопоставим |

Полные внешние status/stage/fetch именно читателя, время чтения отдельно от сборки пакета и полный MCP wall time **не восстановлены**: product telemetry была выключена. Stage→создание text тоже включает клиентское продвижение и не является чистым серверным временем. p42 с отказом и reboot нельзя выдавать за обычный темп чтения.

Два расхождения надо сохранить явно: в замере p39 — 7104 символа, в DONE — 7121; p39–41 соответственно 21 218 и 21 235, разница 17. Причина различия охвата не установлена. В DONE p40 имеет **25 regions**, а не 21 из синтетической формы. Синтетика полезна для объяснения JSON, но не является фактическим разложением p40.

#### F11. Размер JSON, стоимость контекста, время модели и точность — разные измерения

Неперекрывающиеся строки синтетической таблицы §1.3 дают 24 493 символа; вложенная строка end повторно не суммируется. Ещё 7000 символов readback увеличили бы этот объём примерно на **28,6%**, а не вдвое. Это лишь арифметика той синтетики, не замер полного контекста: в нём также изображения, инструкции, ответы tools, caching и токенизация. Удвоение повторяемого исходного текста не равно удвоению всего хода или стоимости.

UTF-8 bytes не равны токенам; доля JSON-поля не равна доле задержки. Н3b сохраняет событие end, его ID и region_key, поэтому ему нельзя приписать экономию всех 9% end-разметки. Утверждение «инструкции один раз на чат» описывает размещение текста, но не доказывает однократную стоимость его обработки.

Оценка `10/53 → 0/63` тоже требует аккуратной подписи: это последующая визуальная выборка других страниц, а не выделенный причинный эффект PR561. [Исходный аудит][audit3638] сам ограничивает метод и знаменатели. Отсутствие обнаруженного дефекта не означает отсутствие дефектов книги, особенно если читатель и аудитор видят одинаково ограниченное превью. Подтверждённое улучшение наблюдений сохраняется; универсальный quality PASS из него не выводится.

#### F12. Н4 и Н7 разумно ограничить; их нынешние основания слишком сильны

**Н4.** `_jpeg` строит RGB Pixmap и перебирает quality 82/70/55; внешний цикл пробует 1600, затем 1280 ([код][c-jpeg]). Grayscale для плотного чёрно-белого разворота — разумная гипотеза. Но «1600 px ≤256 КиБ» не доказывает более различимые буквы: важны JPEG quality и фактический показ. Глобальное обезцвечивание может уничтожить различия цветовой карты/легенды с близкой яркостью. Удалять цветовую информацию по одному удачному примеру нельзя. Замер читаемости и размера относится к выбранному классу материала; новых флагов/классификаторов этот аудит не требует.

**Н7.** Даже при перекрытии части ожидания пакетирование потенциально уменьшает число stage/text/semantic-команд и общей сериализации. Поэтому «больше ничего не экономит» не доказано. При этом больший JSON, область отказа, лимиты кандидатов и время генерации — реальные причины **пока не менять** пакетирование. Кроме того, [инструкция][c-instructions] уже разрешает прочитать продолжение эпизода и отправить 1–4 страницы ради цельного body. Нельзя превратить отложенную оптимизацию Н7 в новый безусловный запрет функционально необходимого многостраничного пакета.

### 9.3. Полнота §0: сохранять нужно не только названия полей

В таблице §0 перечислены основные смысловые результаты. Прямого предложения удалить текст, геопривязку или иллюстрации в ней нет. Но фраза «ни одна функция не выброшена» должна учитывать сквозные свойства, не сводимые к наличию массива в stage:

| Свойство | Почему затронуто рекомендациями |
|---|---|
| Точный источник и структура: порядок, headings, сноски, подписи, таблицы, связи, cross-page provenance | Влияют на chunks, PDF и аудит; границы сами по себе не сохраняют всю структуру |
| Факты без Story, атрибуция, точность даты/календарь, observations и evidence | Могут исчезнуть при механическом удалении candidates без body |
| Настоящий Variant.body, default ref и readback достаточного эпизода | Не заменяются `knowledge_reviewed`, summary или отметкой успеха |
| Частичная полезность: ранний поиск, независимость текста от поздней семантики/медиа | «Страница готова» нельзя трактовать как завершение всех выходов |
| Согласование принятых команд, UNKNOWN, сохранность и продолжение после закрытия чата | «Одно окно до конца» — организация работы, а не владелец durable состояния |
| Pinned tokenizer, около 256 BGE tokens и максимум 512 полного входа без обрезки | Символы/байты в аудитной таблице не заменяют эти ограничения |
| Независимые разрешения на текст, иллюстрацию, скан/оригинал и публикацию | Ускорение чтения не расширяет доступ и не разрешает внешнюю публикацию |

Основания — [AGENTS][agents], [owner alignment][owner], [ingestion][ingestion]. Это дополнение к пониманию функций, **не семь новых гейтов**.

Список ремонтных путей §5 тоже нельзя объявить исчерпывающим по нескольким найденным веткам. Для reprocess/rechunk важен профиль: unsupported native-команды следует согласованно убрать из enum, описаний и достижимого пути, сохранив независимо используемую семантику другого профиля. На контрольной точке PR574 оставался открытым; скрытие enum без исправления подсказок уже оспорено в координации. Ни эта работа, ни обычное согласование принятого UNKNOWN не дают разрешения заново импортировать источник.

### 9.5. Рекомендуемый порядок и конкретное решение по Н1–Н7

| Предложение | Вывод независимого аудита | Удаляемая обязанность / что сохранить |
|---|---|---|
| Н1 | **Поддержать устранение лишних ручных назначений**, без обещания ×2–3 | Убрать паузы на новое поручение между произвольными блоками; сохранить одного владельца импорта, принятые IDs и продолжение после обрыва. «Один чат навсегда» не новый технический контракт |
| Н2 | **Поддержать адресное сокращение повторов** | Убрать полный повторный fetch и отчёты на каждую страницу, когда это только дублирующая отладка; сохранить status для progress/неясного исхода/tail и полезную независимую проверку |
| Н3a | **Переформулировать перед реализацией** | Разрешить предварительное чтение; убрать «один status», универсальный retry и обещанную минуту. Не менять существующие acceptance/UNKNOWN механизмы |
| Н3b | **Поддержать как отдельную узкую нормализацию** | Убрать ручной счёт только для явно выбранного конца региона; сохранить явный end, внутренние offsets, ноль, canonical accepted bytes и оба входных транспорта |
| Р5 рядом с Н3b | **Отдельное согласование требований и существующих данных** | Не смешивать вычисление длины с next_boundary/verified_eof; новые подсказки должны соблюдать модельное решение начала и конца |
| Н4 | **Гипотеза для ограниченного замера** | Возможное уменьшение потерь на сжатии; цвет, мелкие графемы и геометрия должны остаться пригодными. Общая grayscale-правка пока не обоснована |
| Н5 | **Оставить отложенным** | Небольшая предполагаемая экономия не оправдывает изменение идентичности/replay без измерения |
| Н6 | **Не удалять по признаку отсутствия body** | Убрать только доказанную фиктивную квоту/повтор; сохранить facts/evidence/dates/observations и нужный frontier в существующих записях |
| Н7 | **Оставить оптимизацию отложенной**, не объявляя её пользу нулевой | Сохранить допустимые 1–4 страницы для связного материала; не увеличивать пакет ради обещания скорости без данных |

Первый самостоятельный участок — **Н1 и исправленный Н2**, без новых runtime-механизмов: непрерывная ответственность за чтение и устранение дублирующих отчётов/сверок. Н3b может идти отдельной небольшой правкой после согласования точной семантики отсутствующего offset. Н3a сначала требует корректной инструкции относительно существующего active progress. Эти участки не обязаны ждать решения всех вопросов PDF, вложенности и пакетирования.

**Ответы на шесть вопросов §8:** (1) главные функции перечислены, но сквозные инварианты и facts-without-body требуют дополнения; (2) Н3b допустим при условиях F5, а Р5 включает ещё EOF и судьбу существующих units; (3) плотность пересчитана корректно по направлению, равенство скоростей не доказано; (4) status-progress и readback были частично спутаны с отладкой; (5) порядок выше основан на доказанности и риске, а не на неподтверждённых минутах; (6) полнота реестра ремонтных путей не установлена, но native path/retry и подсказки профиля проверены предметно.

**Итоговый статус:** исходный текст сохранён; критические выводы и вопросы дописаны. Никаких production-исправлений, переимпортов, повторов принятых страниц, новых флагов/состояний, замеров live или изменений runtime данный аудит не выполнял. Указанные различающие проверки предложены; результаты исполнения не заявляются.
