## Итог одной фразой

Сам импорт не замедлился в 3–5 раз: страница Albinus содержит в ~4–5 раз больше текста, чем страница Трауготта, и по символам в час чтение идёт с той же скоростью. Реальные потери — простой между отладочными блоками (~60% времени за последние 3 часа) и служебная работа, которую навязывает промпт читателя, а не код: сверки через fetch, отчёты в Slack, ожидание apply и избыточные end-отметки. На служебную разметку уходит ~70% символов, которые модель пишет на каждую страницу.

## 3. Доказательства по коду

### 3.1. End-отметка перед следующей статьёй не нужна, а инструкция её требует

- Следующий start того же вида сам закрывает предыдущую единицу: [`source_units.py:98-110`](../../src/regional_knowledge/source_units.py#L98-L110) («At most one open unit per kind: a confirmed next same-kind start closes the prior one»).
- Это закреплено тестом: [`tests/test_source_unit_anchors_p0a.py:102`](../../tests/test_source_unit_anchors_p0a.py#L102) `test_i02_next_chapter_start_is_confirmed_end_without_redundant_end_marker`.
- Описание `book_ingest` для модели: «Use end markers at real next boundaries» — [`server.py:1553`](../../src/regional_knowledge/server.py#L1553). Читатель ставит end на каждую статью: p38 — 21 start + 20 end, p40 — 21/21, p41 — 19/18.
- `offset` — обязательное целое в Unicode-символах ([`contracts.py:247`](../../src/regional_knowledge/contracts.py#L247)); для end это длина собственного транскрибированного региона (например, 986). Считать символы модели трудно, и ошибку отвергает валидатор ([`contracts.py:322-342`](../../src/regional_knowledge/contracts.py#L322-L342)). Start в словаре почти всегда стоит на offset 0, и считать ничего не нужно.

### 3.2. Сервер разрешает читать следующую страницу, пока применяется предыдущая

- Следующий stage отвергается с `prior_write_pending`, пока предыдущий не применён: [`kaggle_importer.py:706-716`](../../src/regional_knowledge/kaggle_importer.py#L706-L716). Это обычный отказ, данные не теряются.
- `book_pages` проверяет только квитанцию оригинала и не ждёт apply: [`kaggle_importer.py:973-986`](../../src/regional_knowledge/kaggle_importer.py#L973-L986).
- Инструкция же велит: «For next_action=wait, call status» ([`server.py:653`](../../src/regional_knowledge/server.py#L653)). Читатель ждёт apply (47–83 с), затем делает readback и только потом открывает следующую страницу.

### 3.3. Readback через fetch кодом не требуется

- APPLIED виден в `status`: `state=staged, next_cursor=N+1, next_action=continue_pages|continue_tail` (сообщения читателя p39/p40, [`kaggle_native_source_intake.py:404-449`](../../src/regional_knowledge/kaggle_native_source_intake.py#L404-L449), [`:649`](../../src/regional_knowledge/kaggle_native_source_intake.py#L649)).
- `fetch` отдаёт не больше 8 чанков (схема MCP fetch: `limit` ≤ 8), поэтому страница из 20 чанков — это 3 вызова и ещё ~7 тыс. символов в контексте. При правиле «одно окно на всю книгу» каждая сверка удваивает рост контекста на страницу. Это главный риск для книги в сотни страниц.

### 3.4. Картинка страницы для плотного разворота — 1280 px

- Рендер пробует 1600, затем 1280 px по длинной стороне при лимите 256 КиБ: [`kaggle_djvu_pixels.py:29`](../../src/regional_knowledge/kaggle_djvu_pixels.py#L29), [`:212`](../../src/regional_knowledge/kaggle_djvu_pixels.py#L212). У Albinus все страницы приходят 1280×905 (аудитор p39–41, p46/48), то есть ~640 px на печатную страницу с двумя колонками мелкого шрифта.
- Последствия: повторное чтение спорных имён (p39), лишняя буква в адресе (p48), оговорка аудитора о «неопределённости в мелких графемах». Это качество и время модели, но выигрыш надо замерить (Н4).

## 4. Правки по убыванию выигрыша

Бюджет строк — только production. Прогноз выигрыша — до таблицы Шкипера; подтверждать парным сравнением минут между stage-сообщениями на соседних страницах.

### Н1. Одно окно читает книгу до конца, без отладочных блоков и пауз на аудит

- Выигрыш: 3,3 → 7–10 стр/ч за 3 часа (×2–3), простой 60% → <15%.
- Код: 0 строк. Это процесс, решение владельца уже есть ([RKB-Продукт 10:32](https://mira-projects.slack.com/archives/C0C8RT9JB2P/p1793089920425099)).
- Различающий тест: нет, это не код.
- Живая проверка (Шкипер): стр/ч и доля простоя по журналу stage за 3 часа.
- Кто заметит: владелец — сразу, по числу книг в каталоге за день.
- Маршрут: (б) RKB-Продукт / владелец — кто принимает основное чтение Albinus после p51 (запрос Шкипера 10:20).

### Н2. Промпт основного читателя без отладочной обвязки

Убрать `status` перед страницей, `fetch`-сверки принятого текста и отчёты в Slack на каждую страницу. Оставить один `status` перед следующим stage, отчёт раз в 10 страниц и при BLOCKED.

- Выигрыш (прогноз): 1–2 мин/стр из 5,7–8,5. Рост контекста на страницу ~в 2 раза меньше, значит длинная книга дольше держит темп в одном окне.
- Код: 0 строк, текст промпта читателя.
- Различающий тест: не код. Проверка — две соседние пары страниц с обвязкой и без.
- Живая проверка (Шкипер): минуты между stage-сообщениями p_N и p_N+1 до и после; в логах API нет fetch от читателя.
- Кто заметит: читатель — на каждой странице; владелец — по стр/ч.
- Маршрут: (б) тот, кто ведёт основное чтение (RKB-Продукт по предложению RKB-Opus), промпт — в задании Н3.

### Н3. Инструкция stage: без end перед следующей статьёй и без ожидания apply

Две правки текста в `server.py`:

1. в описании `book_ingest` заменить «Use end markers at real next boundaries» на «A start closes the previous unit of the same kind; add an end only where a unit stops without a following same-kind start (before non-unit material or at the real end of a chapter)»;
2. пункт 6 чеклиста: «after stage returns wait, read the next page with book_pages and prepare its packet; call status once right before the next stage; prior_write_pending means resend the same stage after status».

- Выигрыш (прогноз): −9% символов пакета, нет подсчёта Unicode для ~20 end на страницу, плюс ~1 мин/стр ожидания apply. Итого ~1–1,5 мин/стр.
- Бюджет: ≤ 6 изменённых строк production (только строки инструкций), без новых полей, состояний и проверок.
- Различающий тест: словарная страница из 3 статей только со start даёт те же `source_spans` для закрытых единиц, что и со start+end, а последняя статья остаётся `unit_not_ready`. Плюс проверка, что описание `book_ingest` больше не содержит «Use end markers at real next boundaries».
- Живая проверка (Шкипер): после установки API — p_N со старой и p_N+1 с новой инструкцией: число отметок, минуты между stage, `book_find(view=units)` даёт те же complete-единицы.
- Кто заметит: читатель — на каждой странице словаря или энциклопедии; PDF-экспорт — никто (границы те же).
- Маршрут: **(а)** задание [`docs/prompts/rkb-import-task-stage-guidance-20261027.md`](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/docs/rkb-import-task-stage-guidance-20261027/docs/prompts/rkb-import-task-stage-guidance-20261027.md) + окно-исполнитель.

### Н4. Чёткость картинки плотного разворота

Гипотеза: при 256 КиБ разворот в градациях серого (JPEG `L`) поместится в 1600 px, а не в 1280.

- Выигрыш (прогноз): меньше перечитываний и ошибок в буквах. Цифр нет.
- Код: сначала 0 строк — замер. Правка ≤10 строк в `kaggle_djvu_pixels._jpeg`, только если замер покажет 1600 px в лимите.
- Различающий тест (если дойдёт до кода): у одного и того же PPM-разворота серый JPEG при 1600 px ≤256 КиБ, а у RGB — нет.
- Живая проверка (Шкипер): размер JPEG p48 при 1600 px в RGB и в сером. Затем аудитор на тех же p46/p48 — дефекты букв.
- Кто заметит: аудит точности — в каждом аудите словарных страниц.
- Маршрут: (б) Шкипер — замер без изменения live.

### Н5. `page_id` в ссылках чанков на страницу пакета — «не делаем» сейчас

Около 4% символов пакета. Чтобы его убрать, нужно менять схему stage и replay принятых команд. Выигрыш мал против риска; вернуться к этому после цифр Шкипера, если разметка останется узким местом.

### Н6. Пустые кандидаты `needs_context` на словарных страницах

3 на страницу, ~5% символов, без тела истории. Можно ли на справочной странице ограничиться `knowledge_reviewed=true` без «кандидатов на будущее» — продуктовое решение. Маршрут: (б) RKB-Продукт.

### Н7. Пакет из 2–4 страниц — «не делаем»

После Н3 ожидание apply скрыто чтением следующей страницы, и упаковка в один stage больше ничего не экономит. Пакет на 28 тыс. символов текста и ~100 тыс. символов JSON в одном вызове увеличивает риск отказа целого пакета и сбоя длинного вызова в ChatGPT.
