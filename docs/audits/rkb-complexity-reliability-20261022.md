## Краткий вердикт

Выбирать между «удалить всю Kaggle-обвязку» и «сохранить каждый новый механизм» неверно. Kaggle уже предоставляет private/versioned Dataset с version/upload/status/download; RKB должна хранить **прикладную причинно-следственную целостность**: original immutable ID, авторизация/owner/import lease, no duplicate provider effects, correct predecessor, UNKNOWN/reconcile, точный recovery snapshot + tail/ordered schema и verified Saved только после подтверждённого покрытия. Потери/хрупкость создают **разошедшиеся независимые границы**: handler count vs config bytes vs component inventory, предзапусковый final fingerprint vs миграция после восстановления, параллельные представления provider «ready», непроверенные глобальные control caps и неполная интеграционная тестовая матрица. Эти слои можно сократить **без второго orchestrator и без потери гарантий**.

Классы evidence: **A** — непосредственно воспроизведённый отказ или конкретная ветка reject + независимый receipt; **B** — доказанный кодом structural coupling/лишняя дублированная логика, но негативный live эффект не измерен; **C** — наблюдаемый единичный trace/CI boundary, требующий измерения p95/E2E. Последствия, помеченные «риск», не утверждаются как случившиеся инциденты.
