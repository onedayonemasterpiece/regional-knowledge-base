## 1. Главный вывод и границы доказательства

**Низкая латентность сейчас ограничена не только retrieval. На пути к готовому ответу есть повторные проверки одного состояния, лишняя сериализация, обращения к чужой очереди и служебные ожидания на общем WSS-приёмнике.** Часть этих затрат можно вычесть без изменения архитектуры. Самые первые пакеты должны освобождать путь готового поискового ответа: S1–S8, SQL-3/4/5. Принцип: одна проверка на настоящей границе доверия или ожидания; один готовый evidence-ответ, когда клиенту нужен первый текст; существующее владение compute и точная отмена остаются.

Найдено и несколько связанных рисков надёжности, которых недостаточно искать только по списку H1–H17: бессрочное накопление покрытых recovery тел (I2), lifetime предел original requests внутри допустимой большой книги (RT04), повторное хеширование всей истории `applied_ops` с потолком sequence (RT03), provenance новых passages из manifest первого пакета (SQL-7). Это достижимые сценарии по коду. Они не выдаются за происшествия, воспроизведённые аудитором на production.

**Реестр #481 содержит неточные предпосылки.** H1 уже исправлен на этом main; native packet может стать видимым до Saved; Kaggle apply не обязательно читает удалённый журнал; подтверждённый SQL rollback уже превращается в rejected outcome; `before/after` читаются decoders. Эти различия влияют на порядок исправлений и не позволяют «упростить» recovery удалением действующих гарантий. Полный разбор каждой строки — §8.

### Как читать оценки

- **Доказано кодом:** есть конкретный caller, ветвь, изменяемое состояние и достижимая последовательность. Это доказывает лишние операции/отказ, но не его частоту в production.
- **Сообщено в координации и сверено перед публикацией:** [PR482](https://github.com/onedayonemasterpiece/regional-knowledge-base/pull/482) уже слит и переносит две DjVu inventory/ELF проверки вне event loop; этот кодовый дефект не предлагается исправлять повторно. Live acceptance этой установки аудитор не проверял; S1 относится к другому участку Dev. [PR483](https://github.com/onedayonemasterpiece/regional-knowledge-base/pull/483) также слит: авторизованный direct search_adapter теперь продлевает useful-idle внутри backend deadline; ordinary MCP prehook остаётся прежним. PR476–480 также учтены. Полные diff482/483 прочитаны, их тесты не запускались.
- **Условное вычитание:** лишняя работа доказана, но точная замена требует проверки существующего caller/ownership/retention контракта. Это явно отмечено, особенно RT06–RT10 и SQL-2. Такие пункты не являются разрешением добавить новый сервис, очередь, режим или ослабить Saved.
- **Выигрыш** — количество удаляемых обращений, обходов, состояний или причин отказа. Строки кода до реализации можно оценить только границами удаляемого блока; выдуманных миллисекунд, процентов ускорения и подтверждённого p95 здесь нет. Эффекты S4/S5/S6/S7/SQL-5 пересекаются и не складываются арифметически.

Целевые p95 backend ≤1000 мс, MCP ≤1500 мс и предел обычного текстового read 2000 мс — **требования**, а не результаты этого аудита. Текущее достижение этих целей по срезу кода установить нельзя.

## 4. Dev, MCP и общий путь готового ответа

### S1. Служебная обработка занимает общий приёмник WSS и цикл событий

**Вердикт: ЗАМЕНИТЬ синхронный SQLite доступ существующим исполнением DB вне event loop; УДАЛИТЬ ожидание maintenance-owner из последовательного приёма сообщений.** Высокая уверенность в блокирующем пути, средняя в минимальной перестановке владельца recovery receipt. Это самостоятельный дефект относительно уже слитого PR482 с DjVu.

**Доказательство:** [kaggle_recovery_dispatch.py:206–239](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/src/regional_knowledge/kaggle_recovery_dispatch.py#L206) входит в `queue.connect()` прямо из async `receive`; [bge_queue.py:136–148](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/src/regional_knowledge/bge_queue.py#L136) выполняет синхронный `BEGIN IMMEDIATE` с `timeout=5`. Вызов ожидается единственным [receiver, bge_channel.py:528–551](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/src/regional_knowledge/bge_channel.py#L528). Перед ним тот же receiver может до `2*SEND_TIMEOUT_SECONDS`, то есть до 10 секунд, ждать появления `_recovery_phases` после READY. Поисковые frames за этим receipt ещё не читаются. Другой синхронный SQL на loop — callback `binding_current` и source barriers из S4/S5.

1. **Ценность/пользователь.** Пользователь поиска должен получать уже готовый `QUERY_RESULT`, пока импорт или snapshot заканчивает собственную операцию. Receipt всё равно необходимо закрепить до ACK, чтобы accepted работа не потерялась.
2. **Достижимый сбой.** Другой SQLite writer удерживает транзакцию; приходит recovery result; `BEGIN IMMEDIATE` блокирует поток event loop, включая обработку поиска и его таймер. Отдельно: после перезапуска API READY предшествует восстановлению recovery-owner; receiver ждёт owner, последующий `QUERY_RESULT` стоит за ним. Это вывод из последовательности кода, не воспроизведённый live-инцидент.
3. **Существующий механизм.** `queue_call`/`asyncio.to_thread` уже используются для queue DB операций в [bge_channel.py:386–392](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/src/regional_knowledge/bge_channel.py#L386), а durable source outcomes имеют ограниченные settlement tasks в [kaggle_source_commands.py:416–461](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/src/regional_knowledge/kaggle_source_commands.py#L416). Worker удерживает pending receipt до ACK: [bge_wss_transport.py:571–574,679–697](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/scripts/production/bge_wss_transport.py#L571). Использовать этих существующих владельцев, не новую очередь.
4. **Хрупкость.** Один служебный ответ тормозит несвязанные запросы. Async timeout не может прервать уже выполняющийся синхронный SQLite call на том же потоке. `to_thread` устраняет остановку loop, но само по себе не устраняет ожидание следующего frame последовательным receiver — обе границы надо различать.
5. **Дублирование.** Прочность ACK обеспечивается фиксацией точного receipt, а не тем, что приёмник перестал читать другие frames. Ожидание owner внутри receiver не даёт дополнительной durability.
6. **Копии/слои.** WSS receiver → recovery receive → queue transaction; source gate → sync spool; аналогичный риск на native DjVu отдельно рассматривает [PR482](https://github.com/onedayonemasterpiece/regional-knowledge-base/pull/482). Его перенос inventory/ELF проверки не исправляет Dev SQLite/HOL. JPEG в потоки здесь не предлагается.
7. **Один различающий тест.** В одном параметризованном WSS regression поставить перед `QUERY_RESULT` recovery receipt: в варианте A удержать SQLite writer lock, в B задержать восстановление maintenance owner. Search должен завершаться в общем бюджете, receipt затем получить один логический settlement и корректный ACK; повтор после потерянного ACK может получить duplicate ACK, но не повторяет effect. Этот тест отличает неблокирующее владение receipt от его потери.

**Минимальная правка:** DB-only часть исполнять через уже применяемый helper вне loop; `rebind_current` и `schema_context` из receive оставить у их loop-owner с проверкой binding, не выносить всю функцию в thread механически. Убрать 10-секундное ожидание из receiver, передав тот же receipt существующему ограниченному settlement/reconciliation owner с ACK после commit. SourceCommand publications — пример уже применяемого способа владения, но не готовый consumer recovery receipt. Точный callback этой передачи ещё требует просмотра исполнителем; это не готовый однострочный patch. **Нельзя** просто `continue`, вернуть фиктивный accepted ACK или надеяться на повтор в той же сессии: worker отправляет pending один раз за session. Выигрыш — удаление синхронного writer wait и maintenance wait с пути чтения следующего search frame; измеренных миллисекунд нет.



### S2. Двухсекундный бюджет не охватывает весь MCP-путь

Обновление по слитому PR483: direct trusted search_adapter теперь вызывает existing record_request_activity после authority.require, внутри backend timeout ([kaggle_public_backend.py:469–473](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/src/regional_knowledge/kaggle_public_backend.py#L469-L473)). Это сохраняемое исправление useful-idle, не второй activity вызов ordinary MCP. Указанные ниже ordinary MCP prehook и final issuance по-прежнему вне backend budget.

**Вердикт: ЗАМЕНИТЬ несколько частичных границ одним существующим absolute read deadline от входа до выдачи; УДАЛИТЬ обязательное ожидание служебной записи перед стартом этого бюджета.** Высокая уверенность в разрыве бюджета; средняя в безопасном переносе полезной активности без изменения idle semantics.

**Доказательство:** [server.py:308–314](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/src/regional_knowledge/server.py#L308) сначала ожидает `record_request_activity`; запись [bge_queue.py:221–226](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/src/regional_knowledge/bge_queue.py#L221) требует writer lock с timeout5. Deadline создаётся лишь внутри [kaggle_public_backend.py:425–458](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/src/regional_knowledge/kaggle_public_backend.py#L425). После `return output` (:580) middleware [read_issuance.py:199–218](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/src/regional_knowledge/read_issuance.py#L199) ещё делает refresh, render и JSON encode, потенциально дважды, вне `timeout_at` backend.

1. **Ценность/пользователь.** Пользователь замечает время от MCP-вызова до ответа, а не только время retrieval. Сам факт запроса обязан продлевать useful-idle — это полезное поведение, его не удалять.
2. **Достижимый сбой.** Writer lock задерживает activity UPDATE до начала таймера; либо backend уложился, но финальный refresh/SQLite/serialize задержал выдачу. В обоих случаях локальная двухсекундная отсечка не ограничивает полный вызов. Финальная gate имеет собственный TTL и может отказать в выдаче; это не ограничивает продолжительность её работы.
3. **Существующая гарантия.** В проекте уже есть absolute deadline, cancel request, terminal callback после `send`, полезная активность и существующий runtime controller. Нужно передать ту же границу раньше/дальше, не вводить второй таймер или watchdog.
4. **Хрупкость.** Ошибка наблюдения выглядит как быстрый backend и медленный MCP; повторные финальные проверки способны превратить готовый ответ в отказ. Отдельно из S1: даже правильно расположенный asyncio timer не прерывает блокирующую работу на loop.
5. **Повтор/смысл метрик.** [read_telemetry.py:140–193](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/src/regional_knowledge/read_telemetry.py#L140) заканчивает `backend_elapsed_ms` при возврате backend; [read_issuance.py:128–130](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/src/regional_knowledge/read_issuance.py#L128) сохраняет прежнее значение после нового render. Не принимать это число за end-to-end MCP. Контрдоказательство: `issued.complete` действительно вызывается после `send` (:238–246), `finish_attempt` получает финальную фазу; утверждение «нет terminal измерения» неверно.
6. **Копии/слои.** Public backend deadline; admission timer; source-gate TTL; request activity prehook; финальный issuance; backend/product/attempt telemetry. [test_bge_queue.py:406–410](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/tests/test_bge_queue.py#L406) закрепляет правильное продление по запросу; его смысл сохранить. Не добавлять новую телеметрию: пользоваться существующим финальным событием.
7. **Один тест.** В end-to-end ASGI сценарии отдельно задержать внешнюю authentication, prehook и final refresh относительно одного абсолютного deadline, отправив запрос непосредственно перед useful-idle cutoff. MCP не должен продолжать полезную работу после бюджета, а runtime не должен выключиться, игнорируя факт запроса. Проверить final terminal event, не только `backend_elapsed_ms`.

**Минимальная правка для обычных текстовых reads:** создавать/передавать уже используемый deadline от ASGI ingress до внешней authentication и activity hook, включив финальную выдачу; если граница начинается лишь в call_tool, честно называть её tool-call→ASGI send, не полным MCP временем. Убрать повторный render/refresh, который станет ненужным после S4/S7. Illustration path сознательно отключает этот backend timeout, mutation/import имеют иной бюджет — не распространять на них 2 секунды механически. Синхронное ожидание persistence activity убрать с пути ответа только при сохранении существующим controller факта запроса до idle decision. **Готовый coalesced updater в текущем коде не найден**; нельзя выдавать `create_task` без владельца и учёта shutdown за безопасное исправление. Перенос deadline сам по себе не делает sync JSON encode прерываемым. Выигрыш — одна обязательная служебная write transaction перестаёт предшествовать budget, один общий измеримый предел вместо ложного покрытия всего вызова.



### S3. Уже найденный текст отбрасывается, вынуждая второй MCP-вызов

**Вердикт: УДАЛИТЬ ограничение существующего `knowledge_search` только профилем live; использовать готовый evidence response там, где клиенту сразу нужен текст.** Высокая уверенность в лишнем цикле; конфигурация установленного production connector отдельно проверяется оператором.

**Доказательство:** [kaggle_public_backend.py:281–317](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/src/regional_knowledge/kaggle_public_backend.py#L281) уже получает `item.text`, citation, locator, revisions. При `evidence=True` всё это возвращается; при `False` остаются id/title/url. [server.py:1253–1294](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/src/regional_knowledge/server.py#L1253) регистрирует `knowledge_search` только в live, затем возвращает server; full предлагает `search`, инструкция которого требует `fetch`. Fetch снова проходит backend [kaggle_public_backend.py:687–709](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/src/regional_knowledge/kaggle_public_backend.py#L687). В доступных описаниях подключённого kalinigrad-base обнаружены `search`/`fetch`, `knowledge_search` не обнаружен; live инструмент не вызывался.

1. **Ценность/пользователь.** Пользователь, задавший вопрос по книгам, получает текст, citation, locator, source revisions и continuation из первого ответа поиска. Это существующий продуктовый результат; подробные `source_provenance.pages/regions` evidence renderer не возвращает.
2. **Сбой, который предотвращает урезание.** Совместимость search/fetch DTO со старым клиентом реальна; её сохранять. Но отбрасывание текста для всех клиентов не защищает релевантность, авторизацию или source identity: evidence уже прошёл тот же gate.
3. **Замена.** Уже реализованные `search_evidence`, `EvidenceSearchOutput` и `knowledge_search`; новый tool, поисковый движок или кэш не нужен. Fetch остаётся для длинного продолжения и подробного page/region provenance, когда они нужны. Первый текст с цитатой уже не требует его обязательного повторного чтения.
4. **Хрупкость.** Между search и fetch могут истечь authority/runtime binding, смениться версия или начаться rotation. Пользователь получает id, но не текст, хотя текст был готов. Есть дополнительный client/transport/auth/admission/SQL/final-gate цикл.
5. **Дублирование.** Это повторный end-to-end read ради уже гидратированных данных, а не ускорение inference. Сохранение всего текста в первом bounded response не требует нового хранения.
6. **Копии.** Profile gate в server; renderer bool в backend; инструкции tool descriptions; [test_server_contract.py:43–51](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/tests/test_server_contract.py#L43) проверяет live-набор. Схему и инструкции текущего full connector проверяет оператор; metadata сама по себе не доказывает фактическую схему каждого клиента.
7. **Один тест.** Реальный full-profile MCP schema + ASGI вызов существующего knowledge_search возвращает тот же bounded text/citation/source revisions, что native result, за один вызов; legacy search/fetch продолжает соблюдать свой DTO, длинная выдача сохраняет явный next_id. Никакого обязательного fetch для уже полученного evidence.

**Минимальная правка:** вынести регистрацию уже существующего knowledge_search выше `if profile == 'live': return mcp`, сохранив early return только для live и остальные full tools; обновить описание используемого connector на готовый путь. Простое расширение if на full вместе с return уберёт tools ниже него и неверно. Не менять search DTO несовместимо и не создавать новый режим. Выигрыш — один обязательный MCP round trip на получение первого текста; величина экономии зависит от клиента и не измерялась.



### S4. Пять чтений книжных restriction barriers на один ответ

**Вердикт: УДАЛИТЬ проверки прав/видимости книг из accepted-public-book read path согласно решению владельца.** Сохранить participant auth, private Case/draft policy, точный source и active content revision. Высокая уверенность.

**Доказательство:** [source_read_gate.py:103–109](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/src/regional_knowledge/source_read_gate.py#L103) вызывает синхронный `_barriers_for` и использует только `restriction_active`. В `_gate` barrier читается до фильтрации и ещё раз после неё ([281–281,366–366](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/src/regional_knowledge/source_read_gate.py#L281)); `_gate` выполняется в finish и refresh (:392–415), затем issuance_current ещё раз читает restrictions (:417–434). При обычном успешном ответе: 2+2+1=5 чтений. [control_spool.py:933–949](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/src/regional_knowledge/control_spool.py#L933) делает до четырёх SELECT на source и ещё один meta SELECT; pending/unknown/meta этому consumer не нужны.

1. **Ценность/пользователь.** Все участники закрытой группы видят все книги; книжный ACL не даёт требуемой продуктовой ценности. Нельзя путать его с подлинностью участника, private Case или корректностью active revision.
2. **Предотвращаемый сбой и контрдовод.** Текущий gate немедленно прячет ранее принятую книгу при локальном restriction/withdrawal intent ещё до PG apply. Это реальная старая семантика, закреплённая тестом. Более позднее решение владельца эту книжную visibility policy отменяет; бизнес-удаление/смена active revision остаётся в accepted PG path. Удаление всех source joins было бы ошибкой.
3. **Гарантии.** Participant auth на входе/перед delayed output; PG active revision и source identity; MVCC retrieval; точные continuation/database-generation поля. Они не требуют чтения control журналов всех страниц на каждом ответе.
4. **Хрупкость.** Сбой локальной spool, writer contention или старый restriction intent закрывает уже найденный текст. При трёх различных источниках, у каждого из которых есть operation row, один проход — 13 SELECT, обычный ответ — **65 SELECT** только на barriers. Это арифметика ветки кода, не измерение SQL-трассы и не оценка ms.
5. **Повтор.** Внутри `_gate` после единственного `await` authority до второго barrier нет await, но другой поток теоретически может изменить spool. Финальный output boundary всё равно повторяет проверку. Нельзя обосновывать каждый дубль только таким возможным race и затем выдавать сумму за единую атомарную гарантию.
6. **Копии/слои.** Source gate finish/refresh/issuance; spool barrier/pending/unknown projections; worker SQL source_visibility; docs с accessible/visible; [test_source_read_gate.py:109–153](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/tests/test_source_read_gate.py#L109) требует withdrawal и actor revocation в одном сценарии. Разделить ожидаемое поведение книги и действительную отмену participant/private grants, не удалять тест безопасности целиком.
7. **Один тест.** В одном реальном read сценарии accepted книга возвращается всем действующим участникам при старом book-restriction intent; одновременно disabled participant и чужой private Case не получают данные, а неактивная content revision не попадает в выдачу. SQL trace accepted-book пути не обращается к restriction/pending/unknown spool.

**Минимальная правка:** вычесть book restriction branch и его repeated refresh/issuance consultations для accepted public sources, не переписывать весь gate других доменов. Если для отдельного оставшегося домена нужен final restriction policy, использовать один set-based query только нужного факта на его финальной границе. Выигрыш — 5 barrier проходов и до 65 SELECT в приведённом трёхисточниковом сценарии, меньше причин отказа после retrieval. Эффект пересекается с S5/S6/S7; не складывать счётчики как независимые миллисекунды.



### S5. Принятый READY-манифест заново доказывается при каждом binding

**Вердикт: ЗАМЕНИТЬ повторную полную READY validation существующим `accepted_generation` и текущими run/connection/expiry фактами.** Высокая уверенность; защита от stale attachment остаётся.

**Доказательство:** [kaggle_public_backend.py:114–140](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/src/regional_knowledge/kaggle_public_backend.py#L114) заново читает expected/observed JSON и вызывает `_runtime_check`. Тот повторно получает ту же runtime row и делает full manifest validation ([bge_queue.py:525–566](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/src/regional_knowledge/bge_queue.py#L525)). Уже есть полноценная проверка при READY/reconnect с записью accepted_generation ([568–595](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/src/regional_knowledge/bge_queue.py#L568)). В обычной настроенной ветке один current_binding делает 9 SQLite SELECT: shared-enabled2, control1, run1, runtime2, повтор runtime2, owner1.

1. **Ценность.** Пользователь не должен получить результат от старого run, database generation или неподходящего BGE space. Проверка свежести attachment нужна; повторная проверка неизменившихся manifest строк не делает его свежее.
2. **Сбой.** Reconnect меняет connection_generation; старый READY не авторизует новое соединение. Это предотвращает сравнение accepted_generation с текущим generation. Другая runtime/configuration должна пройти существующий READY/migration acceptance заново.
3. **Гарантия.** `accept_search_runtime`, ordered migration promotion и записанный accepted_generation; уже существующий [channel_status:457–476](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/src/regional_knowledge/bge_queue.py#L457) использует компактный признак, не пересобирая manifest. Не вводить дополнительный cache/fingerprint/TTL.
4. **Хрупкость.** JSON/schema/hash validation и несколько SQLite соединений становятся обязательными до dispatch и после готового результата. Синхронные callbacks из [kaggle_service_startup.py:329–335](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/src/regional_knowledge/kaggle_service_startup.py#L329) выполняются на event loop; дополнительно проверяется writer_current, который нужен прежде всего mutation owner.
5. **Повтор.** Initial binding + dispatch + finish + refresh + issuance = пять current_binding в обычном пути: **45 SELECT** по показанным функциям, без дополнительного writer-current и auth. Полный runtime proof не изменился между ними; меняющиеся run/generation/expiry не удалять.
6. **Копии.** Queue runtime acceptance, public current_binding, startup binding_current, source gate, channel status/admission, [kaggle_readiness.py:136–182](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/src/regional_knowledge/kaggle_readiness.py#L136). Тесты [test_kaggle_public_backend.py:294–307](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/tests/test_kaggle_public_backend.py#L294) на смену binding полезны; assertion о числе повторных proof checks не должен заменять проверку реальной смены поколения.
7. **Один тест.** Принять настоящий READY proof, выполнить тёплый read, затем reconnect с новым generation без нового READY: первый ответ разрешён, второй запрещён; счётчик full manifest validator растёт только на acceptance/reconnect, а не на каждом read. После принятия нового READY поиск восстанавливается.

**Минимальная правка:** убрать `_runtime_check` из read binding: это две повторные SELECT и deep validation за вызов. Первое чтение expected/observed пока нужно: из него берутся `database_generation` и `min_data_seq` (:135–136). На следующих проверках использовать уже переданный TargetReadBinding плюс current generation/owner/expiry, не перечитывая immutable proof; min_data_seq и актуальную schema promotion не потерять. Свести повторные same-phase вызовы к одному на реальной границе ожидания, пользуясь существующими полями, не глобальным кэшем. Выигрыш — до четырёх повторных binding проходов после консолидации и отсутствие full READY validation на hot path; 45 — текущая иллюстрация, не обещанный остаточный ноль SQL.



### S6. Авторизация участника нужна, семь повторов одного состояния — нет

**Вердикт: УДАЛИТЬ повторную загрузку уже проверенного OAuth token и соседние rechecks без новой границы ожидания; ОСТАВИТЬ входную аутентификацию и свежесть перед delayed/private output.** Высокая уверенность в дублировании, средняя в точном числе проверок, которое останется после совместной правки gate/admission.

**Доказательство:** [server.py:72–82](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/src/regional_knowledge/server.py#L72) уже получает AccessToken от MCP authenticated context, но [read_authority.py:164–186](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/src/regional_knowledge/read_authority.py#L164) снова зовёт provider.load_access_token. [oauth_provider.py:683–708](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/src/regional_knowledge/oauth_provider.py#L683) снова читает encrypted state; [133–176](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/src/regional_knowledge/oauth_provider.py#L133) читает/расшифровывает весь файл под lock, а [213–227](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/src/regional_knowledge/oauth_provider.py#L213) обходит семь buckets ради prune, изменения которого read не сохраняет. Дополнительно ordinary personal read имеет `_state` на resolve и require в dispatch, begin_read, next_channel_work, finish_read, source finish, refresh — семь проходов без повторных попыток.

1. **Ценность.** Только действующий участник получает данные, отозванный доступ прекращается, private Case/draft не раскрываются. Закрытая библиотека не отменяет эту защиту.
2. **Реальный сбой.** Подделанный UUID вместо OAuth credential; revocation во время ожидания compute; смена adapter destination. Входная аутентификация и последняя проверка после задержки предотвращают это. Повторные adjacent checks до queue wait не защищают от revocation после них.
3. **Гарантия.** SDK authenticated token, resolver-owned VerifiedReadAuthority с identity/expiry, текущие participant/grant revisions, одна проверка после реального ожидания. Для иных ingress вроде adapter/expert собственная реальная authentication boundary сохраняется.
4. **Хрупкость.** Каждый recheck зависит от control DB и планировщика thread pool. Полный OAuth-file read/prune растёт со всем числом записей вместо конкретной family. Ошибка соседнего ненужного чтения закрывает уже авторизованный запрос.
5. **Повтор.** Не путать token verification со свежестью participant rights. Передача уже проверенного token в trusted resolver не требует второй расшифровки файла, если issuer/resource/client/family projection проверяется в том же trusted context. Prune всех чужих buckets не нужен, чтобы проверить expiry одной найденной записи.
6. **Копии.** [source_read_gate.py:190,225](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/src/regional_knowledge/source_read_gate.py#L186), [bge_admission.py:200,485,586](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/src/regional_knowledge/bge_admission.py#L180), `require→recheck→_state` [read_authority.py:210–242](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/src/regional_knowledge/read_authority.py#L210); OAuth provider, private-domain gates. Begin_read имеет самостоятельных callers Case/GEO/editorial/acceptance: удалять его проверку глобально без аудита этих входов нельзя.
7. **Один тест.** Через реальный MCP authenticated context поставить read в ожидание, отозвать participant/family перед выдачей и проверить отказ; valid request выдаётся, fabricated context и чужая private destination не проходят. Инструментировать provider load/state reads, чтобы подтвердить отсутствие adjacent повторов, не подменять resolver голым UUID.

**Минимальная правка:** переиспользовать полученный SDK token в существующем trusted resolver; оставить общую границу в admission для самостоятельных callers, вычесть дублирующие public wrapper checks; финальный participant check оставить один после задержки. Убрать read-side full-state prune, если current-row expiry остаётся проверенным и существующие mutate paths выполняют cleanup. Новую IAM/кэш/сервис не создавать. Выигрыш — одна полная повторная загрузка encrypted OAuth store и несколько одинаковых DB rechecks на обычном запросе; финальное точное число зависит от границ S4/S8.



### S7. Проверка собственного typed результата через JSON повторяется на обеих сторонах

**Вердикт: УДАЛИТЬ внутренние encode→decode и discarded serialization; ОСТАВИТЬ ограничение фактически отправляемых bytes и одну проверку внешнего wire.** Высокая уверенность. Native детали дополнены SQL-5 ниже; это один пакет, не два независимых выигрыша.

1. **Ценность.** Untrusted frame должен пройти schema/duplicate-key/nonfinite/byte bounds, а результат — совпасть с request/generation. Пользователь не получает пользу от повторного parsing собственных immutable DTO без недоверенной границы.
2. **Достижимый сбой.** Oversize Unicode payload, duplicate keys, неверный vector или forged dependency могут прийти снаружи; их проверка остаётся. Тестовый `model_copy` с произвольным обходом validation сам по себе не доказывает production trust boundary.
3. **Гарантия.** Typed constructors и actual wire decoder; уже есть [ItemDependencies validator, kaggle_protocol.py:219–230](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/src/regional_knowledge/kaggle_protocol.py#L219). Byte cap проверять на реальном outgoing frame, не на выброшенной промежуточной строке. Один encode означает один full-frame encode на реальную отправку; обязательная JSON-строка MCP content.text и внешний envelope имеют разные назначения.
4. **Хрупкость.** Уже выполненный retrieval может не дойти до пользователя из-за CPU/allocations и повторной validation после результата. Особенно неприятно на event loop при нескольких запросах.
5. **Повтор.** [encode_envelope:492–496](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/src/regional_knowledge/kaggle_protocol.py#L492) сериализует и тут же декодирует собственный объект; decoder (:451–489) парсит дважды. [bge_admission.py:189,572](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/src/regional_knowledge/bge_admission.py#L180) делает discarded encode. [bge_channel.py:383,421–422](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/src/regional_knowledge/bge_channel.py#L377) преобразует уже разобранный dict обратно в JSON перед decoder. [source_read_gate.py:241–268](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/src/regional_knowledge/source_read_gate.py#L241) повторно model_validate(model_dump()) и тот же dependency invariant в finish/refresh. [read_issuance.py:189–215](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/src/regional_knowledge/read_issuance.py#L189) парсит и переписывает весь уже сериализованный MCP response.

### S8. Готовый read дважды собирает головы очереди импорта

**Минимальная правка:** в finish_read использовать существующие channel/owner проверки без `docs/resumed`, оставить два identity checks только по разные стороны await, если race test требует оба. Один channel_status недостаточен: он не возвращает incarnation/persisted owner tuple, сравнение из _snapshot:292–293 сохранить в компактном чтении. ### SQL-1. Scoped dense намеренно отключает индексируемую форму

Пусть планировщик выбирает indexed source subset + exact sort для узкой области или HNSW для широкой; принудительный `MATERIALIZED` убрать.
4. **Хрупкость.** Лимит 1..32 источников не ограничивает число passage vectors. Одна большая книга может сделать данный путь несоразмерно дорогим; count cap скрывает ресурсный риск вместо его ограничения. Сам scope predicate нужен и не подлежит удалению.

### SQL-3. Финальный source SELECT внутри того же snapshot не делает данные свежее

**Основные источники:** [kaggle_query.py:187–198](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/src/regional_knowledge/kaggle_query.py#L187-L198); [kaggle_search.py:143–167](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/src/regional_knowledge/kaggle_search.py#L143-L167); [003_search_scope.sql:59–71](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/sql/kaggle/003_search_scope.sql#L59-L71).

**Доказательство.** `_search` открывает один `REPEATABLE READ READ ONLY` transaction ([kaggle_search.py:143–167](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/src/regional_knowledge/kaggle_search.py#L143)). Source hydrate already joins `active_revision` и `sources` ([001_search.sql:86–96](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/sql/kaggle/001_search.sql#L86), `003:59–71`). Затем callback `finish` опять читает те же source IDs через `active_revision + source_visibility + sources` и сравнивает revision ([kaggle_query.py:187–198](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/src/regional_knowledge/kaggle_query.py#L187)). Пока работает этот transaction, внешний COMMIT не меняет его snapshot; значит этот SELECT не способен обнаружить смену книги после hydrate. Единственное действительно новое поле — `eligibility_revision`, которое можно получить в том же hydrate join. При нулевой выдаче SELECT с пустым массивом тоже выполняется.

1. **Ценность.** Пользователю нужны текст, правильный source и ссылка на текущую content revision. Дополнительный roundtrip после уже успешного hydrate сам по себе эту гарантию не усиливает.
2. **Сбой.** Возврат старой content revision или чужого source при ошибочной candidate сборке предотвращён hydrate joins и requested scope в этом же snapshot. Concurrent change после начала transaction этот callback не видит.
3. **Замена.** Существующие SQL joins + MVCC transaction. ### SQL-4. SQL-настройки превратились в самостоятельную последовательность на каждом поиске

**Основные источники:** [kaggle_search.py:145–188](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/src/regional_knowledge/kaggle_search.py#L145-L188); [kaggle_apply.py:244–245](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/src/regional_knowledge/kaggle_apply.py#L244-L245).

**Доказательство.** Каждая функция `execute` выполняет `SELECT set_config('statement_timeout', remaining, true)` перед целевым SQL ([kaggle_search.py:145–155](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/src/regional_knowledge/kaggle_search.py#L145)). Обычный source search проходит frontier, три отдельные HNSW SET LOCAL, lexical, dense, hydrate, finish: 8 целевых statement + 8 отдельных timeout statement, ещё отдельно `SET TRANSACTION` и transaction begin/finish. Это точный подсчёт текущих Python await cursor.execute, не число сетевых пакетов. До lexical, параллельно encode, последовательны шесть calls ради трёх HNSW settings. Для scoped forced exact эти HNSW значения вообще не используются выбранной SQL формой.

3. **Замена.** Уже существующий `asyncio.timeout_at(deadline)` охватывает SQL, fetch и ожидание encoder; `connection.transaction()` откатывает до выхода. Один transaction-local server timeout ограничивает зависший statement и после сбоя клиента. HNSW settings и server timeout можно выставить одним SELECT с несколькими `set_config`, без отдельной per-op фазы; подобный batching уже есть [kaggle_apply.py:244–245](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/src/regional_knowledge/kaggle_apply.py#L244) и [kaggle_database_probe.py:147](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/src/regional_knowledge/kaggle_database_probe.py#L147).

5. **Повтор.** Повторяет границу существующего absolute deadline. HNSW statements сами получают server timeout setter; из трёх простых assignments получается шесть SQL awaits.
6. **Копии.** [kaggle_query.py:303](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/src/regional_knowledge/kaggle_query.py#L303) exact passage; [kaggle_story_read.py:50](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/src/regional_knowledge/kaggle_story_read.py#L50); [kaggle_fact_read.py:105](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/src/regional_knowledge/kaggle_fact_read.py#L105); [kaggle_editorial_read.py:85](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/src/regional_knowledge/kaggle_editorial_read.py#L85); [kaggle_source_read.py:176](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/src/regional_knowledge/kaggle_source_read.py#L176); rg также [kaggle_case_read.py:51](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/src/regional_knowledge/kaggle_case_read.py#L51), [kaggle_geo_read.py:41](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/src/regional_knowledge/kaggle_geo_read.py#L41), [kaggle_source_graph_read.py:218](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/src/regional_knowledge/kaggle_source_graph_read.py#L218), [kaggle_public_illustration_native_read.py:283](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/src/regional_knowledge/kaggle_public_illustration_native_read.py#L283) (последние только inspected). 4. **Хрупкость.** Runtime CPU work растёт с количеством candidate fragments; perfragment LATERAL latest batch lookup дополнительно усложняет план. План текущей схемы здесь не выполнялся.
5. **Повтор.** Own accepted output rehash на read, при том же immutable body and vector binding.

Один current-schema native accepted scenario: несколько batches, fragments старой и новой книги/Story, близкие unrelated passage vectors; выполнить story scoped/unscoped dense, проверить exact body+best late fragment и EXPLAIN current SQL026. Если одинаковый ID может легально соответствовать разному body в accepted rows, этот тест покажет необходимость точной binding, которую следует брать из уже принятой relation, а не повторно хешировать весь corpus.

**Минимальная правка.** Удалить только read-time SHA computation в обеих view branches после подтверждения immutable ID binding в current accepted path. Не удалять fragment branch и не подменять retrieval representative first vector. Не менять fingerprint compiler. **Уверенность средняя:** лишнее вычисление подтверждено; полный минимальный indexed rewrite batch view пока не доказан. Это отдельный условный кандидат с указанным тестом, без обещания дешёвого восстановления ANN.



### SQL-7. Fetch продолжает читать provenance из первого пакета, хотя passages уже добавляются по пакетам

**Основные источники:** [009_story_editorial.sql:509–523](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/sql/kaggle/009_story_editorial.sql#L509-L523); [026_source_batch_activation.sql:817–820](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/sql/kaggle/026_source_batch_activation.sql#L817-L820); [031_case_packet_evidence_provenance.sql:1–54](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/sql/kaggle/031_case_packet_evidence_provenance.sql#L1-L54); [kaggle_source_read.py:110–119](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/src/regional_knowledge/kaggle_source_read.py#L110-L119); [kaggle_query.py:322–334](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/src/regional_knowledge/kaggle_query.py#L322-L334).

**Доказательство.** Единственное definition `source_passage_metadata_v1` в всех migrations — SQL009:509–523. Оно выбирает `pages` и `regions` разворотом `m.manifest` из `source_manifests`. Текущий packet apply добавляет этот manifest только один раз `ON CONFLICT DO NOTHING` (`026:817–818`), а `source_passage_provenance` новых passages — каждый пакет (`819–820`). Уже SQL031:1–6 прямо объясняет это различие и чинит Case evidence через resolved accessor (`031:48–54`), но обычный passage metadata reader остаётся старым. В production `TargetRuntime` включает `source_provenance=True` ([kaggle_target_runtime.py:441–442](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/src/regional_knowledge/kaggle_target_runtime.py#L441)); `read_continuation` делает metadata query на каждом fetch ([kaggle_query.py:322–334](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/src/regional_knowledge/kaggle_query.py#L322)); `_render_fetch` отдаёт её пользователю ([public_backend.py:332–336](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/src/regional_knowledge/kaggle_public_backend.py#L332)).

Достижимый сценарий без аварии: accepted text packet1 содержит page A → accepted text packet2 содержит новую page B → поиск находит passage B → fetch получает его body из актуальной `passage_search`, а `metadata.pages/regions` ищет B только внутри first-packet manifest A → агрегаты для B пустые/NULL. Никакого corrupted DB для этого не требуется. Для старых whole-book manifests тот же код перебирает все pages и regions, хотя requested passage ≤1.

1. **Ценность.** Читателю необходимы точная страница/регион найденного текста. Это причинно связано с проверкой источника; весь book manifest и его reconstruction на путь этого fetch не нужны.
2. **Реальный предотвращаемый сбой.** Изначально manifest связывал passage с original page/region. При packet import та же таблица описывает только первый пакет, поэтому прежняя гарантия уже неверна для обычного следующего пакета.
3. **Замена.** Уже существующий `_accepted_chunks` читает `source_stage_pages` и `source_regions` по exact ID ([kaggle_source_read.py:110–119](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/src/regional_knowledge/kaggle_source_read.py#L110)), а `source_passage_provenance` даёт точные `page_ids`, `region_ids`, `source_spans`. Повторно использовать эту существующую row lookup форму для нужных публичных metadata. Full manifest accessor тоже существует, но folding всей книги на каждый passage fetch будет новой лишней работой на критическом пути.
4. **Хрупкость.** Успешный search/fetch отдаёт неполные подтверждающие metadata. При старом большом manifest runtime work пропорциональна размеру всей книги; при packet path оно одновременно неполное. Return `not_ready` на эту ситуацию добавлять нельзя: текст уже доступен, надо убрать stale prerequisite.
5. **Повтор/недоверие.** Runtime JSON reconstruction поверх уже нормализованных passage/page/region rows; старый snapshot используется как serving projection. Это остаточная legacy ветка, не необходимость новых metadata hashes.
6. **Копии.** SQL009 old metadata; SQL026 first immutable manifest and incremental provenance; SQL031 Case accessor workaround; `_accepted_chunks` exact lookups; `kaggle_query.read_continuation`; `_render_fetch`. [test_source_batch_pg.py:91–107](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/tests/test_source_batch_pg.py#L91) проверяет первый опубликованный пакет; multi-packet tests:112–136,165–224 проверяют passages/story effects, но не native `execute_passage_read(source_provenance=True)` второго пакета. Из inspected tests такого current-schema regression не найдено.
7. **Что сломается / один тест.** Можно потерять нужные публичные page fields или перепутать source page при замене. Один native PG integration test: опубликовать два разных пакета одного source, выполнить production `execute_passage_read` второго passage с provenance, проверить matching page B/region IDs/offsets, отсутствие page A, сохранение текста и согласованный bounded output. Для того же query план не должен разворачивать весь book manifest. Не исполнялся.

**Минимальная правка.** Заменить `source_passage_metadata_v1`'s два whole-manifest array scan на точные существующие row lookups от `p.data` IDs; canonical first manifest оставить для accepted provenance/replay. Согласовать display catalog с SQL-2 отдельным patch, не менять immutable accepted payload. Не делать новую таблицу/phase/lookup service и не вставлять automatic whole-book aggregation перед каждым fetch. Если требуются остальные manifest-only поля, возвращать только те, которые уже реально используются публичным contract, через существующий exact read механизм; этот shape вопрос должен решить автор вместе с одним regression test, а не новая конфигурационная ветка.

**Контрдовод.** Metadata dict сейчас может содержать исторические image receipts/geometry, которых нет в разрешённых identity columns `source_stage_pages`; simple exact lookup не даёт автоматической полной field equivalence. Это ограничивает размер безопасной правки, но не отменяет доказанную first-packet inconsistency. Повторное использование `read_source_manifest_v1` исправит correctness, однако до принятия как latency fix необходимо проверить его whole-book fold cost. Уверенность в reachable failure высокая.



## 6. Импорт, spool и междоменные зависимости

### I1. Удалить повторный полный обход уже применённого pending prefix

**Основные источники:** [kaggle_native_source_intake.py:167–258](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/src/regional_knowledge/kaggle_native_source_intake.py#L167-L258); [control_spool.py:680–726](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/src/regional_knowledge/control_spool.py#L680-L726).

**Вердикт:** ЗАМЕНИТЬ полную повторную десериализацию истории существующей узкой проверкой незавершённой операции по source и текущего writer binding. Не добавлять очередь или режим. Приоритет: page → search-visible / массовый поток. Уверенность высокая в повторной работе, средняя в точном объёме безопасного удаления без интеграционного regression.

**Где:** [src/regional_knowledge/kaggle_native_source_intake.py:167–194,217–258,609–637](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/src/regional_knowledge/kaggle_native_source_intake.py#L167); [src/regional_knowledge/control_spool.py:680–726](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/src/regional_knowledge/control_spool.py#L680); вызовы `_inactive_prefix_current` на `:231` и `:616`.

1. **Ценность и пользователь.** Импортирующий книгу пользователь должен продолжать следующую страницу сразу после её PG commit, не ждать checkpoint. Проверка должна остановить именно незавершённый apply этой книги или смену writer, а не заставлять перечитывать все предыдущие успешно применённые страницы.
2. **Достижимая цепочка.** Применить первый packet; outcome остаётся `NOT_SENT` до сгруппированного Dataset checkpoint. При следующем `_packet_progress` `scope.pending=True`; `_inactive_prefix_current` делает `SELECT * ... outcome_state<>'DURABLE'`, fetchall, `_entry` и decode payload для каждой старой команды. Затем `_stage_exact` повторяет ту же проверку. После каждого packet число таких строк увеличивается до очередного checkpoint. Для n новых команд в интервале получаем сумму исторических проходов порядка n², в каждом — перенос BLOB, hash/decode/schema/receipt проверки. Это вывод по управляющему потоку, не измерение latency.
3. **Уже имеющаяся гарантия.** Запись receipt в spool после PG `applied_ops`, один writer и per-source sequence, точная идемпотентность operation_key/command bytes; при первом принятии `_validate`, при receipt `_record_apply`, PG transaction и duplicate lookup. Они остаются. Смена writer и unresolved operation остаются достаточными причинами паузы.
4. **Хрупкость.** Старая ошибка decode/registry contract в уже применённой строке останавливает новую страницу. За время проверки `_stage_exact` держит `self.spool._lock`; другая работа на этом control owner ждёт. Это не блокировка всего async loop в данном helper: он вызван через `asyncio.to_thread`, но объём работы и lock реально растут.
5. **Повторная проверка.** `_entry` не просто читает id/status: повторно декодирует exact command, сверяет hash, registry/dependency/receipt поля. Затем `verified.command` и `json.loads(command.payload)` повторно извлекают уже известные route/ingestion. Факты сохранены в строке и доказаны в момент обработки receipt.
6. **Копии/слои.** Два вызова prefix check в Dev native intake; общая spool `_entry`; PG `apply_accepted` exact next seq и duplicate; source history verifier `INACTIVE_SOURCE_ROUTES` используется в helper. [tests/test_kaggle_native_source_intake.py:35–160](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/tests/test_kaggle_native_source_intake.py#L35) фальсифицирует read facts/current coverage и подменяет validators; fake scope flags тестируют ветку, но не рост real prefix. Документы требуют immediate page publication и один поток повторяемого импорта; Dataset durability отдельно.
7. **Что может сломаться и один тест.** Нельзя позволить новому packet обогнать неопределённый предыдущий или продолжить другой ingestion с тем же source. Один интеграционный тест с настоящими SQLite spool + PG: применить несколько native packets без checkpoint, потерять ACK одной последней операции, затем вызвать продолжение; до reconciliation новая операция не dispatch, после duplicate resolution продолжение успешно, и число чтений command BLOB не зависит от количества ранее применённых packets. Это единственный discriminating test: он одновременно сохраняет нужную границу и выявляет лишний scan.

**Минимальная правка:** вычесть цикл по всем историческим rows и повторный вызов из `_packet_progress`; admission основывать на уже сохранённом unresolved apply текущего source/ingestion и текущем writer. Если для такого решения не хватает существующего поля/индекса, не создавать новый proof ledger: сначала показать, какой существующий pending key/source binding его заменяет. Не удалять exact command bytes из неразрешённых операций. **Ожидаемый выигрыш:** два full-prefix прохода на этап → узкая indexed existence/current-operation проверка; n² historical decode → работа, пропорциональная новым операциям. Миллисекунды не оценивались.



### I2. Удалить бессрочное повторное хранение покрытого recovery payload

**Основные источники:** [control_spool.py:223–233](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/src/regional_knowledge/control_spool.py#L223-L233); [control_spool.py:598–621](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/src/regional_knowledge/control_spool.py#L598-L621); [dataset_recovery_store.py:91–107](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/src/regional_knowledge/dataset_recovery_store.py#L91-L107); [dataset_recovery_store.py:164–215](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/src/regional_knowledge/dataset_recovery_store.py#L164-L215).

**Вердикт:** ЗАМЕНИТЬ бессрочное хранение полных покрытых тел существующим snapshot boundary + compact receipts/active references; удалить мёртвый retention knob. Сама безопасная уборка требует одного согласованного автора и consumer inventory, не массового `DELETE WHERE covered_version IS NOT NULL`. Приоритет: доступность импорта/мутаций, размер checkpoint/restore; косвенно search shared runtime. Уверенность высокая в отсутствии найденного GC и lifetime budget, средняя в безопасной границе удаления.

**Где:** [src/regional_knowledge/control_spool.py:223–233,598–621](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/src/regional_knowledge/control_spool.py#L223); [src/regional_knowledge/dataset_recovery_store.py:91–107,164–170,201–215](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/src/regional_knowledge/dataset_recovery_store.py#L91); [src/regional_knowledge/kaggle_dataset_checkpoint.py:298–end](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/src/regional_knowledge/kaggle_dataset_checkpoint.py#L298).

1. **Ценность и пользователь.** Непотеря accepted/Saved диалогов, мутаций и effects — обязательна. Пользователь поиска/импорта не должен терять admission из-за полной копии уже сохранённой истории. Параметр `raw_retention_seconds=4*3600` обещает окно, но не выполняет работу.
2. **Достижимая цепочка.** Последовательно принять достаточно операций, успешно checkpoint каждую группу. `covered_version` только UPDATE; строки остаются. `_used_bytes` суммирует все control operations, `_put` суммирует все Dataset objects. После конечного объёма накопленного history следующий accept даёт `SpoolFull`/`JournalLimit`, несмотря на успешные checkpoints. При default 512MiB каждая известная операция продолжает занимать в budget как минимум 32768 bytes сверх тела: уже это даёт верхнюю границу менее 16384 сохранённых operations, до учёта всех настоящих command/outcome bytes и source heads. Это вычисленный предел default accounting, не утверждение о текущей production capacity. Параллельно `export_control` каждый раз base64-сериализует все non-snapshot objects в общий bytearray и затем bytes. Рост исторической базы увеличивает время export и чтения. Живой объём/дата исчерпания неизвестны.
3. **Имеющаяся гарантия.** Проверенная Dataset version, snapshot base_sequence и `applied_ops` уже хранят подтверждённые факты. Неопределённые accepted операции, актуальные head/manifest ancestors и receipts для replay/status могут оставаться в локальном рабочем наборе. Нельзя считать любой `covered_version` доказательством отсутствия ссылок.
4. **Хрупкость.** Все домены делят общий лимит. Успешный старый импорт может исчерпать бюджет для будущего невоспроизводимого диалога/мутации. Каждое новое `_put` также делает `sum(length(data))` по полной истории. В update-ветке budget сравнивает size + len(new), не вычитая длину предыдущего значения: дополнительный ложный отказ у границы, хотя отдельный порядок величины вторичен.
5. **Дублирование.** В Dataset mode exact command живёт в spool row, journal segment/object, checkpoint journal blob и PG applied_ops; receipt — spool apply/outcome/receipt и journal object + PG. Часть копий нужна до acknowledgement/rotation, но код сохраняет всё бессрочно. Это не основание удалять authoritative applied_ops.
6. **Копии/слои.** Repository search по `raw_retention_seconds` нашёл только constructor validation/store (`:223,228,231`). По production `DELETE FROM rkb_control_operations` и `DELETE FROM rkb_dataset_recovery_objects` удаления не найдено; дополнительный sweep всех DELETE/DROP/retention в этих owners и generic table-delete patterns не обнаружил скрытого GC. Единственный synthetic delete operations — [tests/test_kaggle_cases_backend.py:685](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/tests/test_kaggle_cases_backend.py#L685). `export_control` invoked из checkpoint `:121`. Dataset promotion `:168` только маркирует; spool `_record_outcome` `:850` только меняет статус; checkpoint `:366–388` только публикует/settles/marks verified. Ещё одна долговечная копия: [bge_queue.py:993–1003](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/src/regional_knowledge/bge_queue.py#L993) чистит done query и audit document jobs, но source_command/recovery_phase jobs там не удаляются; это дополнительный retained state, его replay/status consumers тоже нужно учитывать, а не удалять бездумно. Старые docs называют spool коротким и bounded; actual budget — lifetime.
7. **Что может сломаться и один тест.** Слепое удаление разорвёт журнал head → predecessor, historical receipt lookup/повторный request/status, source history coverage и restoration из старого snapshot. Один тест: принять mixed import + невоспроизводимую mutation, потерять ACK mutation, сделать подтверждённый полный snapshot, убрать только разрешённые покрытые тела и восстановиться из него с оставшимся хвостом; повторить обе operation_key. ### I4. Вычесть повторный SQL precondition внутри apply и per-command pg_proc проверку

**Основные источники:** [kaggle_apply.py:330–445](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/src/regional_knowledge/kaggle_apply.py#L330-L445); [026_source_batch_activation.sql:762–773](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/sql/kaggle/026_source_batch_activation.sql#L762-L773); [026_source_batch_activation.sql:862–882](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/sql/kaggle/026_source_batch_activation.sql#L862-L882).

**Где:** [src/regional_knowledge/kaggle_apply.py:330–340,383–445](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/src/regional_knowledge/kaggle_apply.py#L330); [sql/kaggle/026_source_batch_activation.sql:762–773,862–882](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/sql/kaggle/026_source_batch_activation.sql#L762); аналог inner check [sql/kaggle/034_source_catalog_corrections.sql:41–43](https://github.com/onedayonemasterpiece/regional-knowledge-base/blob/ad157b402eab4110a130bed3f2949a378f388d44/sql/kaggle/034_source_catalog_corrections.sql#L41); каталог отдельно рассматривает SQL-2.

1. **Ценность и пользователь.** Некорректный packet не должен попасть в поиск. Первая проверка trusted PG precondition + constraints даёт эту гарантию; повторная такая же проверка в той же transaction не улучшает ответ импортирующему пользователю.
2. **Достижимая цепочка.** `apply_accepted` держит recovery_state writer row lock; новый operation: два `_function_contract` SELECT, `handler.check` SELECT, затем `handler.apply`. `apply_source_batch_v1` снова берёт тот же recovery row lock и вызывает тот же `check_source_batch_v1`. Он заново парсит prepared command JSON, проверяет source conflicts, раскрывает embedding inputs и вычисляет sha256 текстов. Для text и semantic commands всё повторяется. Никакого другого writer между двумя checks при соблюдении установленного writer boundary нет.
3. **Уже имеющаяся гарантия.** Один PG transaction, recovery_state lock, constraints/UNIQUE, exact accepted bytes и trusted HandlerRegistry, ordered SQL migration ledger. Runtime функция не может самопроизвольно сменить форму между двумя calls без отдельного DDL writer, которому запрещён обход общего writer lock.
4. **Хрупкость.** Валидация формы deployment на каждой operation превращает проблему артефакта в operation failure внутри global sequence. Повторная тяжёлая проверка расходует timeout до effect и удлиняет writer lock. Удаление первой проверки вместо второй неправильно: код потеряет canonical rejected_precondition outcome для плохого ввода.
5. **Повторная проверка.** Обе PG функции получают один p/ids/expected/logical_time и читают одну committed/prepared state. `_function_contract` проверяет pg_proc return type/language/volatility/security, хотя registry/migration артефакт доверенный. Ограничения формы не следует заменять runtime hash pins.
6. **Копии/слои.** Dev validates source packet, materializer validates/prepare, apply_accepted outer precondition, SQL apply inner precondition. Exact `apply_source_batch_v1(` search в src/scripts не нашёл literal production direct caller; dynamic call построен apply_accepted. Tests SQL isolation переопределяют function; нужен осмотр privileges и динамических calls, а не признание тестового direct SQL продуктовым consumer. Tests `_function_contract` в `tests/test_kaggle_apply.py` закрепляют invoker/scalar contract; их переносить к existing deployment validation, не просто удалять safety assertions.
7. **Что может сломаться и один тест.** Если реальный production caller вызывает apply напрямую без common executor, удаление внутренней проверки уберёт единственную input boundary. Один PG integration regression через production executor: valid packet применяется один раз, invalid precondition создаёт rejected receipt без effects, повтор exact operation отдаёт duplicate; инструментированный check исполняется ровно один раз для нового accepted packet и ноль для duplicate. Добавить прямой вызов в этот же scenario допустимо лишь если такой caller реально найден; без него тест не оправдывает дублирование.

**Минимальная правка:** вычесть inner check из текущей function definition через новую ordered migration, не менять bytes уже применённой SQL026; вычесть два `_function_contract` calls из `apply_accepted` только при доказанном existing migration/startup enforcement. Не менять registry fingerprints вручную. **Выигрыш:** два pg_proc round trips + одна полная packet-precondition SQL execution на новую apply operation; меньше lock-held work. Не обещать p95 в ms.

### Что именно оператор должен проверить в живой конфигурации/базе

Это **задание оператору**, не команды, выполненные аудитором. Нужны существующие read-only данные и сохранённые логи; новые нагрузки — только в рамках отдельно разрешённой приёмки. Секреты, signed URLs и payload содержимого книг в отчёт не переносить.

1. **Фактический MCP путь:** профиль server, advertised schema tools, использует ли клиент evidence operation. Из существующих traces разделить ASGI/auth, tool call, backend, result-to-terminal и network send. Не складывать backend_elapsed и общий terminal как независимые интервалы. Проверить warm запрос отдельно и во время уже запланированных original/snapshot операций; target p95 считать по полной серии, не по нескольким удачным примерам.
2. **SQL план на действующей схеме:** versions всех установленных migrations; планы current scoped dense с узкой/широкой областью, `book_find` по исправленному названию, Story fragment view SQL026 и fetch passage второго пакета. Уточнить actual HNSW/GIN usage, buffers/rows, recall относительно exact reference. Старый fixture SQL001 или SQL018/019 не заменяет current-schema план.
3. **Spool и retained references:** число/байты rkb_control_operations по seal/apply/outcome, количество covered/uncovered Dataset objects, current verified base/cursor и все designated retained bases/unfinished consumers. Отдельно взять applied sequence maximum и длину обязательного tail. По этим данным определить безопасно удаляемые raw copies; в ходе проверки ничего не удалять.
4. **Legacy producer и decoder:** выполнить read-only count `rkb_native_source_intake_state` с `packet_mode=0 AND phase NOT IN ('finalized','failed')`; перечислить route/schema versions в сохранённых command bytes, old Dataset manifests, replay/status consumers. Ноль активных mode0 позволяет рассматривать removal producer, но не автоматический removal decoder.
5. **Dataset config/clock:** только имена активных config sections `dataset_checkpoints`/`dataset_seed`/`source_snapshot`/`source_restore`/`geo_bootstrap`, точные refs без credentials, timestamps последних dirty/control и full backups. Подтвердить, есть ли уже существующая сохраняемая first-dirty граница для control-only state. Отдельно проверить, что Saved действительно означает покрытие exact Dataset version.
6. **Originals/media:** kinds текущих и retained originals, доля S3-only refs, наличие настоящего Telegram locator/archive contract для каждого supported ingress. Проверить количество remembered original operations при допустимой большой книге и replay semantics pending-handle→snapshot_status. Без этого нельзя вычесть archive path одной настройкой.
7. **SQL writer boundary:** реальные роли/GRANT на check/apply functions и direct callers; допускается ли DDL writer в обход общей migration/lease границы. Если inner SQL apply публично вызывается без common executor, I4 требует оставить единственную input boundary на этом входе.
8. **Последняя штатная ротация:** из сохранённых API/controller/provider logs получить начало SIGINT, actual listener gap и ready successor; проверить live supervisor configuration. Успешный exit75 unit test не доказывает непрерывность MCP, а наличие terminal provider proof не следует заменять догадкой по heartbeat.

## 12. Вопросы к владельцу

**Новых вопросов о целевой политике нет.** Dataset primary/weekly backup, закрытое чтение книг, повторяемый однопоточный импорт, сохранность accepted effects,15/30/4ч и запрет12 fingerprint inputs уже заданы. Повторное подтверждение этих решений не требуется.

Оставшиеся неизвестные — факты production конфигурации, retained references, callers и длительность реальных границ. Они перечислены оператору выше. Если выбранное исправление требует изменения одного из12 protected files или новой подсистемы, оно остаётся отдельным BLOCKER; текущий аудит такого разрешения не запрашивает и не предполагает.

## 13. Критерий завершения следующего шага

RKB-Opus проверяет находки по указанным текущим caller/consumer, принимает или опровергает каждый минимальный пакет одним различающим сценарием и сохраняет полезные гарантии из §10. После этого оператор подтверждает сокращение **полного** пути text-search на существующей рабочей конфигурации. До такой проверки нельзя заявлять достижение p95 или устранение живого overlap только по числу удалённых проверок.

Аудит завершён послойно; полнота всего репозитория и live-результат не заявлены.
