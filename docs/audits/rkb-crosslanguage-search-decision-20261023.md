# RU→DE в RKB: выбор стратегии поиска без лишней задержки

**Дата:** 2026-10-23 · **Автор:** RKB-Межъязычный поиск · **Тип:** docs-only decision / research, **не** внедрение.  
**Статус данных:** source/papers reviewed; сравнение с реальным held-out корпусом Вихерта — **NOT RUN**.  
**Source checkpoint:** `main@9f24365f9ecce83327159ded97935bcfd96e77cf` (сверено 2026-10-23); нормативный контракт `bd138b2449f68cabb2cbfa3df552df8471f40c78`.

## 0. Решение в одном абзаце

**Сейчас:** сохранить обязательный dense BGE-M3 + текущий lexical hybrid; не объявлять RU→DE доказанным по одной странице и не добавлять синхронный перевод/реранкер на каждое обращение. При следующем *отдельно одобренном* изменении поискового пути первым дешёвым кандидатом являются нормализованные **aliases исторических имён/топонимов (§4.2)**; убедиться, что ветвь действительно включена в live fusion (сейчас в просмотренном `kaggle_search.py` видны только lexical+dense). **После полного источника и слепой оценки:** сравнить с baseline прежде всего *перевод на RU при однократном импорте* и индекс оригинал+перевод, не отбрасывая его из-за стоимости импорта. Двуязычный запрос клиента — конкурентная гипотеза, но измерять полную задержку модели, второго encode и поиска. Sparse BGE-M3 не переводит смысл между скриптами; ColBERT и cross-encoder — лишь условный top-K rerank при подтверждённом выигрыше и достаточном p95-бюджете. Ни один вариант пока не принят в production.

**Главный критерий владельца:** добавка к **сквозному p50 и p95 каждого запроса**; время/токены импорта на страницу и хранение — *отдельные вторичные измерения*. Для тёплого поиска защищённое требование `p95 ≤ 1000 ms`; для полного MCP пути в §14.1 также `p95 ≤ 1500 ms` при предусмотренной нагрузке. Это *целевые пороги*, не измеренные значения этой работы. Не создавать новые сервисы, не делать дополнительный hop через Dev и не заменять поиск скрытой backend-LLM.

## 2. Что именно считать задержкой

Единица наблюдения — **один исходный пользовательский запрос** с конечным исходом: evidence / empty-but-grounded / timeout / pending / failure. Не исключать неудачи из знаменателя. Параллельные этапы не складываются линейно: в текущем коде lexical исполняется, пока идёт encode; дополнительный DE encode и ветви могут быть последовательными либо параллельными, а конкуренция за GPU/PG может ухудшить p95.

- `T_user→evidence` — от исходного запроса до пригодного source-grounded ответа инструмента клиенту; **включает клиентскую модель**, если она генерирует DE query, её ожидание, обе encode, SQL, rerank, hydrate, serialization, admission/transport и проверку результата. Отдельно `T_tool` от входа MCP до usable evidence и `T_kaggle` внутри обработчика. Для голоса downstream ASR/TTS и первый *содержательный слышимый* ответ учитывать отдельно по §14.4.
- Для каждого кандидата и режима: `Δp50 = p50(T_user→evidence, candidate) − p50(T_user→evidence, baseline)`; аналогично `Δp95`. **Оба числа сейчас NOT MEASURED.** Дополнительно сохранять paired per-query differences и confidence intervals; *нельзя* вычислять общий p95 как сумму p95 стадий.
- Обозначения таблицы: `M` — дополнительная latency client LLM (в т.ч. удлинение имеющегося ответа); `E_DE` — второй encode или инкрементальный batch GPU; `Q_*` — дополнительные bounded SQL/index/scoring операции; `R_K` — инференс reranker по K парам; `F/H` — изменение fusion/hydrate; `I_*` — разовые операции при импорте. Знаки «+» ниже описывают *причины* изменения, **не миллисекунды и не складываемые процентили**.

### Условия реализации *при отдельном будущем решении*

**1. Baseline / control.** RRF ветвей lexical и dense должен оставаться двумя независимо работающими bounded retrieval ветвями. Проверять dense-only Hit@K и ANN vs exact, чтобы переводная lexical ветка не маскировала деградацию mandatory dense. Прямой GET страницы не является релевантностным тестом.

**2. Двуязычная формулировка.** Для честного сравнения клиент отдаёт два раздельных поля `ru_query` и `de_query` с указанием источника/времени DE формулировки; нельзя склеить оба языка в текущий single-string query и объявить поддержку без проверки. Один DE запрос должен действительно идти по немецкому FTS, а не запускать German stemming русского текста. Вариант 2a — только DE lexical рядом с RU dense; 2b — также DE dense. Модельная генерация, даже выполняемая до MCP, входит в *пользовательский* latency denominator. Не выдавать «без нагрузки backend» за нулевую стоимость Kaggle, если нужен второй encode и SQL. Exact original RU намерение/даты сохранять независимо от DE paraphrase.

**3. Aliases.** Предусмотреть identity disambiguation, исторический период, исходное написание, язык и provenance (пара «Кёнигсберг/Königsberg» не всегда тождественна современному городу в историческом смысле). Использовать существующие индексированные alias/entity projections из §4.2, без отдельного registry. Текущая `kaggle_search.py` fusion содержит две branches — **план ≠ уже включённый runtime**. В отличие от семантического перевода, эта ветка не решит абстрактный парафраз без распознанного имени.

**4a. BGE sparse.** Официальная формула BGE-M3 даёт score по **общим токенам** query и document. Разные RU/DE слова, не разделяющие tokenizer IDs, не начнут совпадать от sparse-весов; общие числа/латиница/names возможны. Отдельно проверять tokenizer/вызов shared forward, sparse retrieval indexability и O(N) отсутствие. Не строить всем 100k passages новый неиндексируемый Python scan. Dense BGE остаётся требуемым.

**4b. ColBERT.** BGE-M3 умеет late interaction token-level MaxSim, но официальные docs прямо предупреждают о тяжёлой multi-vector части и предлагают rerank на кандидатах. Замерять candidate count, length truncation, IO, query token vectors, batches и VRAM. Нельзя вычислять token similarity по всему корпусу в Python. Candidate recall остается верхней границей качества rerank.

**5. Cross-encoder.** Допустимый концептуальный пример — `BAAI/bge-reranker-v2-m3` (multilingual model card); это **второй loaded model**, не новый внешний API/сервис. Не начинать с top-100 вслепую: сравнить ограниченные `K=10/20/50` (только проектные параметры эксперимента), длину passage, shared GPU и concurrent import. Если кандидат не попал в top-K first-stage, reranker не поможет. Quality считать по оригиналу, не по красиво звучащему ответу LLM.

**6. Перевод при импорте.** Хранить `(original_source_id, accepted_revision, original_passage_id/page, translation_language, translation_text, translation_model_revision, alignment_status)` как *восстанавливаемую derived projection*, не новый accepted source/evidence и не подмену оригинала. Возвращать **оригинальный DE passage ID и страницу**; RU перевод — поисковый ключ/помощь для кандидатов, не доказательство и не «цитата из книги». Отдельно QA loss/alteration для дат, имён, диакритики, цитат, отрицания; ошибка перевода не должна отбрасывать допустимый оригинал. Invalidation при revision/withdrawal/reimport, текущие source/visibility fences и bounded hydrate сохраняются. Начальный вариант **RU FTS перевода + original dense** не требует второй online query encode. Решение о дополнительном RU dense translation embedding принимать отдельно после gain/cost/storage измерений. Дорогой *однократный* import никогда не является самостоятельным основанием исключить этот подход.

## 3. Качественная оценка / что может быть улучшено

- **Класс lexical gap:** RU семантика ↔ немецкие морфологические формы. Dense baseline потенциально умеет; bilingual DE query и русский indexed translation создают настоящую одноязычную lexical ветку. У sparse BGE без перевода такого гарантированного механизма нет.
- **Класс entity mismatch:** историческое и современное название, кириллица/латиница, немецкое ß/ö/ä, смешанная транслитерация. Exact verified alias лучше «переводить» моделью; логика identity/temporal scope обязательна.
- **Класс fact specificity:** точные годы, числа, редкие имена и отрицания могут сохраняться в FTS и потеряться в embeddings или машинном переводе. Перевод требует page-aligned original link и проверок.
- **Класс rank-only:** ColBERT/cross-encoder могут переместить золотой chunk из rank>10 в top-10, **если** он уже среди собранных кандидатов. Они не расширяют покрытие за пределами first-stage retrieval. Измерять `candidate recall@100`, а не только итоговый Hit@10.
- **Класс negative:** если факт отсутствует в корпусе, метод должен сохранять неопределённость, а не привлекать похожий перевод как новое историческое свидетельство.

## 4. Воспроизводимый замер, владелец runtime — только Шкипер

**Условия начала:** полный принятый Вихерт, фиксированные версии текстов/страниц и projection cursor, модель/токенизатор/PG indexes из одного точного checkpoint; baseline работает и наблюдаемы сквозные trace/статусы. Ни этого корпуса, ни новых замеров в настоящем docs-only задании нет. **Не запускать тесты на Kaggle, PG, provider или live нагрузку на основании этого документа без отдельного runtime решения.**

**Gold:** не менее **30 независимых held-out семейств фактов**, скрытых при выборе candidate modes и их весов. Рекомендуемый минимум — 5 имён/вариантов написания, 5 исторических топонимов, 5 дат/чисел, 5 семантических парафраз, 5 редких немецких терминов/словосочетаний, 5 межстраничных или неоднозначных фактов. Допускаются пересечения тегов, но идентичный факт считается одной family. Для каждой семьи — ≥2 естественных RU вопроса разной формы, gold accepted DE passage/revision/page и допустимые альтернативы; независимо review по оригинальному скану/источнику. Поиск по заглавию или двуязычному титулу не заменяет body test. Добавить отрицательные/unanswerable примеры **в отдельную diagnostic выборку** и явную ошибку переводного отрицания. Gold вручную зафиксировать *до* ранжирования гипотез. Другие книги/исторические слои и mixed RU/DE после Вихерта проверить дополнительно, но не выдавать за выполненную сейчас оценку.

**Метрики качества (для каждого метода и подгруппы):** Hit@5; Hit@10; MRR@10; candidate coverage@K до rerank; dense-only Hit@10/ANN-vs-exact; no-answer false-evidence rate и original passage/page correctness. Семейство считается hit только при eligible **оригинальном** evidence, а не похоже переведённом тексте. При ровно 30 families требование `≥85%` означает **не менее 26/30**, но 30 — минимум для gate, не достаточная мощность для доказательства малых улучшений: показать доверительный интервал/парные различия, при малых эффектах увеличить gold. Не подбирать веса по held-out; для tuning использовать отдельную dev выборку или фиксированные априорные параметры.

**Два слоя end-to-end latency:** (i) `T_user→evidence` и (ii) `T_tool` + `T_kaggle`; клиентскую генерацию DE/перевод RU→DE никогда не вычитать из (i). Один trace с input family, mode, source revision, allowed filters, actual output/status. Разложение: client model wait/generation; admission/queue; tokenize; pool acquire; RU и DE encode (batch/sequence, GPU contention); lexical RU/DE; alias lookup; sparse retrieval; dense ANN; ColBERT/cross-encoder K; fusion; hydrate/ACL; serialization; WSS/Dev relay; final client validation. ## 5. Decision gates после замеров (не автоматическая реализация)

1. **Fail** при отсутствии source-grounded и правильного original revision/page, нарушении authority/withdrawal, при просадке обязательного standalone dense quality, неиндексируемом full scan либо нарушении protected p95. Даже отличный ranking не оправдывает изменение этих инвариантов.
2. **Pass** только при RU→DE `Hit@10 ≥ 85%` на held-out и приемлемых Hit@5/MRR, без значимых regressions имён/дат/мест, при warm p95 ≤1000ms и applicable MCP/4-user p95 ≤1500ms; дать CI и source-pinned результаты, а не текст «быстрее». Если baseline проходит, online метод с дорогим inference можно вводить лишь при предварительно зарегистрированном, повторяемом gain, который действительно меняет пользовательский ответ.
3. **Предпочтение при сходном качестве:** минимальная *измеренная* добавка к каждому запросу. Поэтому index-time translation может выиграть у query-time translation/rerank **даже если import дорог**; но growth SQL/index/maintenance тоже должен быть измерен. Alias branch ограничить точными именами. Не устраивать cascade «всё и сразу»: проверять каждый метод отдельно и только затем наиболее удачные комбинации, чтобы видеть causality.
4. **Failure modes:** если dense@10 низок, сначала проверить качество accepted transcription/chunk boundary/source scope/ANN, не маскировать плохой BGE лексикой; если candidate@100 высок, но Hit@10 слабый, тогда rerank имеет основание. Если ошибки имён — aliases, если RU lexical misses DE body — пробовать import-translation vs bilingual-DE. При неубедительном приросте оставить baseline.
5. **Организация:** Шкипер — **единственный runtime оператор** и держатель измерений; Opus — source/PR review и merge; Продукт — decision по actual metric tradeoff. **Данный PR не выдаёт Шкиперу автоматического разрешения на live/import/provider вызовы.** После measured results **дополнить этот же документ**, не создавать второй decision report.

## 6. Что НЕ сделано этим исследованием

Никаких edits к `src/`, `sql/`, скриптам, конфигурации модели, backend, provider, Kaggle, PG, индексам или правам. Никакого импорта, generation DE query, GPU encode, SQL EXPLAIN или stress-run. Показатели качества всех кандидатов, стоимость перевода на реальной странице Вихерта и runtime p50/p95 — **NOT RUN**. Публикация paper benchmark не является RKB benchmark. Следующий эксперимент потребует уже завершённого accepted corpus и отдельного штатного runtime запуска Шкипера.

## 7. Риск-реестр / порядок проверок

| Риск | Проверка / защита |
|---|---|
| RU translated passage выдан как немецкое evidence | Возвращать только accepted original passage ID, revision и physical page; translated text — derived query index; compare negatives/quotes |
| Немецкий FTS по русскому тексту назван переводом | Требовать явный DE query/translated RU index; source `websearch_to_tsquery` — нормализация, не translation |
| Старое написание топонима слито с новым объектом | Language+period+entity ID/source evidence и explicit ambiguity; не превращать similarity в identity |
| Sparse/ColBERT добавляют постоянный GPU/SQL overhead без gain | Stage+end-to-end paired p95; candidate recall; отказ при неизвестной эффективности |
| Cross-encoder большой K вытесняет BGE/замедляет импорт | Тесты GPU/VRAM, 4 users+import, resource admission/deadline; не добавлять сервис |
| Перевод неправильно восстанавливает дату/отрицание | Held-out exact fact checks, original proof, language/projection revision invalidation |
| «100% Hit» с титула/одной страницы | Held-out ≥30 fact families по немецкому телу полной книги, negative controls |
| Выигрыш backend time скрывает client LLM time | T_user→evidence включает модель; T_tool отдельно; p95 per request, все завершения в denominator |
