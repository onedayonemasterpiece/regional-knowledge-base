## 1. Цель

Продуктовая цель владельца: **поиск быстрый и надёжный, импорт не вязнет.** Упрощение ради упрощения не нужно. Поэтому в отчёт попадает только то, что влияет хотя бы на одно из:
- **задержку или надёжность поиска/fetch** (тёплый backend p95 ≤ 1000 мс, MCP p95 ≤ 1500 мс, предел 2000 мс; отказы, зависания);
- **скорость импорта** (страниц/час) и **застревания импорта** (пакет нельзя повторить/исправить, переимпорт упирается в запрет, ожидание без выхода);
- **надёжность восстановления/ротации** (restore не проходит, replay упирается в проверку).

Аудитируется **слой PostgreSQL** проекта: хранимые функции, проверки предусловий, триггеры, версии функций и то, как Python их вызывает и проверяет. Для каждой находки сначала назови, какую из трёх целей она задевает и насколько (на каждый запрос / на каждый пакет / на каждую страницу / только при сбое). Находку без влияния на эти цели **не разбирай подробно** — одна строка в разделе «Сложность без влияния на продукт (не трогать сейчас)».

Код писала та же модель, что ты (Codex/GPT). Комментариям «защита», «proof», «must», «immutable» не доверяй — проверяй по коду и вызывающим.

## 4. Что искать (по каждой группе — только с влиянием на цели из §1)

**A. Проверка формы внутри SQL.** Функции `check_*` (и аналогичные проверки внутри `apply_*`), которые заново разбирают и проверяют форму JSON/полей, уже проверенную Python на входной границе (pydantic/валидаторы в `src/`). Для каждой: что именно проверяется в SQL, где та же проверка в Python (file:line), есть ли путь вызова SQL-функции **минуя** Python-проверку (прямые вызовы, роли/GRANT, другие executor'ы). Различай: проверку **формы** (кандидат на удаление) и проверку **предусловия состояния** (expected_revisions, существование строк, CAS — нужна, это работа БД).

**B. Проверка установленных функций на каждом применении.** `kaggle_apply._function_contract` (обращение к `pg_proc` перед каждой командой), fingerprint/хеши функций и обработчиков, сверки `schema_revision/function_revision/executor_revision`. Какой реальный сбой это ловит, который не ловят ordered migration + transaction? Стоимость на каждое применение.

**C. Триггеры неизменяемости** (`reject_revision_update`, `immutable_*` и подобные) на таблицах пакетов, манифестов, векторов, публикаций. Для каждого: какую реальную порчу он предотвращает и не делает ли он **невозможным исправление** (повтор пакета после частичного отказа, переимпорт книги, исправление каталога). Правило ревью: «one-shot immutability → лучше append-only с latest wins». Связь с решением владельца «переимпорт — нормальный путь».

**D. Версии функций и совместимость.** Функции `_v1…_v4`, `RENAME TO ..._before_*`, несколько `CREATE OR REPLACE` одной функции в разных миграциях, «переигрывать старые команды старыми функциями». Что из этого реально нужно для восстановления (база Dataset + хвост команд после базы) и что — обратная совместимость с данными, которые не переносятся и будут переимпортированы. Посчитай, какие версии функций вызываются из текущего кода и из команд текущего журнала (схемы `rkb-v4-sql001-011-v1` — GEO, `-014-v1` — книги), а какие — ни откуда.

**E. Работа на горячем пути.** Функции, которые выполняются на каждом поиске/fetch/применении и делают работу пропорционально размеру книги или всей истории (полные развороты JSON-манифестов, `jsonb_array_elements` по всей книге, перехеширование, `DISTINCT ON` по всем пакетам). Не повторяй уже исправленное (PR 488 — `source_passage_metadata_v1`); найди такие же места в других функциях.

**F. Дубли гарантий.** Constraints/CHECK, которые дублируют друг друга или Python; несколько независимых доказательств одного факта (CHECK + триггер + check_* + Python).

## 5. Метод (для каждого элемента)

1. Какую продуктовую ценность это даёт на критическом пути (поиск; страница → видна в поиске; импорт; ротация/восстановление)?
2. Какой **реальный** сбой предотвращает (наблюдавшийся или конкретно достижимый, с шагами)? «На всякий случай» — кандидат на удаление.
3. Какой существующий механизм уже покрывает (file:line)?
4. Повышает надёжность или хрупкость? Может ли помешать исправлению, повтору, переимпорту?
5. Копии того же условия во всех слоях (SQL, Python Dev, Python Kaggle, тесты).
6. Что сломается при удалении и каким **одним** тестом это доказать. Сомневаешься — пиши УДАЛИТЬ и назови тест, который докажет «оставить».
7. Требует ли изменение новой миграции и переустановки функций на живом Kaggle; влияет ли на восстановление из уже сохранённых версий Dataset (база содержит функции на момент сохранения; хвост команд переигрывается после восстановления).
