Аудитор: RKB-Opus. Для владельца, координатора (dot) и всех исполнителей; координатор переносит раздел «Исправления» в план.
Основа: ТЗ `docs/prompts/rkb-scalable-kaggle-implementation-20261019.md@bd138b2` (§0.1, §1, §3, §7, §14), решения владельца в треде C0C8RT9JB2P, `main@7c7a9b8`, события ночи 22→23.10. Базовая точка сравнения — рабочая версия до переноса (`main@215b3b7`, 20.10).

## 1. Вердикт

**Продуктовый результат хуже исходной точки.** До переноса (20.10) книги импортировались через MCP и находились поиском. После трёх суток работы и ~30 слитых PR за одну ночь **ни одна книга не находится поиском**: Гаузе (174 стр.) принят постранично, но не активирован. Цели переноса — много пользователей, низкая латентность, разгрузка DevCoveer — не проверены ни одной метрикой на реальном корпусе, потому что корпуса нет.

Причина не в отдельных багах, а в архитектурной инверсии: вместо «перенести работающий импорт/поиск на Kaggle и масштабировать» построена новая система доказательств, барьеров и состояний, через которую обычная операция проходит только после десятков проверок. Каждая из них по отдельности выглядит разумной; вместе они дают систему, где любая ошибка в любом месте останавливает всё.

## 2. Что соответствует требованиям

- PG + pgvector + BGE-M3 живут в Kaggle; поиск выполняется там, вектор запроса не ходит через Dev (§0.1, §1). Тёплый поиск на пустом корпусе ~0.3 с.
- Миграции схемы применяются к живой базе без нового запуска ноутбука (SQL021 горячо, v113), восстановление из Dataset старой версии с автоматическими миграциями (v114) — §1 «стоимость отладки», план упрощения PR-1a…PR4 выполнен.
- Хэши каталога/ACL, тройки ревизий, ручные переходы и пины удалены (−2212 строк, PR282/284).
- SQL и read-handler доставляются в работающий ноутбук по WSS без Dataset (PR294/300).
- Медиа без SHA-гейтов (SQL020, PR292) — §0.1 «без обязательного post-upload SHA comparison».
- Оригинал из Telegram читается ноутбуком напрямую через RKB1 (§0.1).

## 3. Крупные несоответствия (по убыванию ущерба)

### 3.1. Импорт: тяжёлый барьер «вся книга» вместо постраничного импорта
- **Требование.** Владелец: модель импортирует постранично, без тяжёлого импорта всей книги. ТЗ §3/§7: start → pages/stage → validate → finalize/status; «Активация source revision и continuation атомарны» — но не «вся книга одним доказательством».
- **Факт.** Принятые страницы лежат неактивными; поиск видит книгу только после `seal` всей книги → компиляции всего графа → токенизации → атомарной SQL-активации со сквозной проверкой цитат/фактов/иллюстраций/графа. Любая неточность на любой из 174 страниц отклоняет всё (ночью: whitespace в одной цитате, footnote span, SQL alias, два таймаута, fact evidence).
- **Сравнение с 20.10.** Там `finalize` тоже активировал, но был лёгким, а векторы догонялись асинхронно («including delayed vector readiness»). Тяжесть добавлена при переносе.
- **Ущерб.** Вся ночь ушла на этот один шаг; ни одной книги в поиске.

### 3.2. «Редкий холодный запуск» → 14 запусков за ночь
- **Требование.** §1: обычные SQL/app изменения — в уже поднятом Kaggle; холодный запуск редок.
- **Факт.** v110→v123 за ~10 часов. Причины: рестарт API убивал ноутбук (дважды, до PR309/310); ошибка одной SQL-команды (`AmbiguousColumn`, `QueryCanceled`) завершает весь воркер; после штатного drain ноутбук висит в Kaggle 15+ мин; часть правок требовала нового bootstrap.
- **Ущерб.** Каждая ошибка = 10–20 минут холодного старта и восстановления.

### 3.3. Глобальные гейты на несвязанных путях
Каждый из них блокировал запись книги, хотя к ней не относится:
- полная перепроверка всей истории источников при каждом продлении, с глобальным бюджетом 4 MiB (поднят до 16 MiB — хватит на 4–5 книг, затем снова встанет);
- классификатор истории отвергает любой новый вид команды и останавливает checkpoint всей системы;
- `imports_current=False` из-за режима GEO bootstrap блокировал импорт книги;
- обязательный `public_rights` при закрытой группе пользователей (владелец: «материалы легальны, не перепроверять»);
- writer-идентичность у сохранённых задач → `PermissionError` и шторм переподключений при восстановлении (PR315).

### 3.4. Приоритеты: инфраструктура раньше сквозного сценария
- **Требование.** §1: «Начать с одного writer и сквозного сценария. Добавлять readers только при измеренном недостатке ёмкости. Не вводить … машину истины».
- **Факт.** Параллельно с неработающим импортом строились телеметрия (PR303 +794, PR301 +845 с сэмплером /proc в ноутбуке), multi-reader (PR290), SQL-префильтр сущностей (PR302), revision2 (PR258/260), Quartz/Expert ветки. Пять–семь агентов меняли общие файлы, координация стыков (stacked PR, restack, merge-ref) съедала часы.

### 3.5. Контракт MCP и модельный клиент расходятся
- Клиент «Книги» не мог отправить `basic_variant.body` — устаревшая схема инструмента у клиента; обход через JSON-файл и ручную передачу «root».
- Ошибки инструментов возвращаются как «Error executing tool …» без причины — модель и оператор слепы.
- ТЗ §8 «История содержит сохранённый рассказ… при достаточном источнике создаётся при импорте»: первый проход дал 0 bodies; сейчас 10 bodies и 44 `needs_context` — качество не проверено на §14.1 Story gate.

### 3.6. Ни один §14.1 gate не измерен
Масштаб (100 книг), dense quality (Hit@5/10), warm p95 ≤1000 мс, MCP p95 ≤1500 мс, каналы/очередь с не-owner, Мира, Slack — не проверены. Цели переноса (много пользователей, латентность, разгрузка Dev) пока не подтверждены ничем.

### 3.7. Процесс ревью
Я (аудитор сложности) ночью одобрял ускорения финального барьера вместо того, чтобы поставить под сомнение сам барьер; один PR (309) влит при красном CI из-за ошибки моего скрипта. Критик был недоступен часами; merge шли по «CI зелёный» без проверки соответствия цели.

## 4. Исправления (в план, по порядку)

**P0 — первая книга в поиске штатным путём**
1. Попакетная активация: каждый принятый `stage` (≤8 стр.) сразу активируется (chunks → векторы → поиск) с проверкой только этого пакета; whole-book `seal`/`prepare_source_activation_*`/атомарная активация удаляются; `finalize` — отметка «дочитано». Continuation сохраняется в каждом пакете (§7 атомарность activation+continuation соблюдена на уровне пакета).
2. Гаузе **переимпортировать штатно постранично**, без backfill/ремонта старого ingestion. Это и есть приёмка процесса.
3. Ошибка одной команды → failed/rejected outcome этой команды + откат её транзакции; процесс воркера не завершается.
4. Ошибки MCP-инструментов возвращают класс и короткую причину.

**P1 — убрать гейты на несвязанных путях**
5. Проверка истории — только хвост от последнего verified Dataset checkpoint; глобального бюджета на всю историю нет.
6. Неизвестный вид команды не блокирует checkpoint (не public-source, учитывается, не стоп).
7. Импорт не зависит от состояния GEO bootstrap.
8. `public_rights` — необязательный, по умолчанию owner attestation; legal-валидатор убрать.
9. После штатного STOP ноутбук завершает процесс сам.

**P2 — подтвердить цели переноса (только после P0)**
10. Импорт 3–5 книг подряд штатным путём; затем §14.1: warm p95, MCP p95, Hit@K, рост истории/диска.
11. Сравнение с версией 20.10 на тех же запросах: латентность и полнота ответов.
12. Телеметрия (PR303 уже в main, PR301) выкатывать после P0; сэмплер ресурсов урезать до core.

**Процесс**
13. Пока P0 не закрыт — не открывать новые фичи (multi-reader, revision2, Quartz, префильтры, телеметрия): один сквозной сценарий.
14. Для каждого PR в ревью первый вопрос: «нужен ли этот шаг/гейт вообще для цели владельца», затем — правильность.
15. Merge только при непустом списке check-runs, все success, на точном HEAD.
