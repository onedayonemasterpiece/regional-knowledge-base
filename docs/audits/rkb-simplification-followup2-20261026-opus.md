## F4 (вместо P0-3). Предел журнала считает только то, что ещё не сохранено в Dataset

**Проблема.** `ControlSpool._used_bytes` (`control_spool.py` ~L599–606) и проверка размера в `DatasetRecoveryStore._put` (`dataset_recovery_store.py` ~L208–210) суммируют **всю** историю за всё время против 512 МиБ. По замеру Шкипера ≈ 70 КБ на операцию → предел через ≈ 7 300 операций (≈ 10 000 страниц), после чего любая запись получит отказ «spool full» и импорт встанет. Назначение бюджета по документам — ограничивать **ещё не сохранённый** хвост (backpressure, пока Dataset отстаёт), а не всю историю.

**Сделать (без удаления строк и объектов).**
1. `_used_bytes`: учитывать только операции, ещё не покрытые сохранённой версией Dataset — `outcome_state<>'DURABLE'` (DURABLE ставится только после `publish_outcome` по проверенной версии Dataset). Резерв для неизвестных исходов (`reserved_bytes` при `apply_bytes IS NULL`) и `rkb_control_source_heads` — как сейчас.
2. `DatasetRecoveryStore._put`: в сумме размера учитывать только объекты `covered_version IS NULL`.

**Нельзя.** Удалять строки/объекты; менять предел 512 МиБ, формат экспорта, `export_control`, ссылки импортёра; добавлять таблицы/колонки/статусы.

**Бюджет.** ≤ 4 изменённые строки SQL-предикатов в двух местах.

**Тест (один).** Реальный SQLite: при маленьком `max_bytes` 3 операции доходят до DURABLE → новая операция принимается; те же 3 операции в NOT_SENT → новая операция получает `SpoolFull`. `book_ingest status` по ранее сохранённому `pending_operation_key` продолжает работать (данные не удалены).

**Известное остающееся (не в этом задании).** Рост файла `journal-control.json` в каждой версии Dataset (≈ 80 МБ сейчас) и диска Dev. Вырезать историю из экспорта небезопасно по тем же причинам, что и удаление; решать отдельно, после замера времени checkpoint.

## F5 (SQL-аудит SQLA-01). Fetch не должен ломаться, когда в ту же книгу добавлен пакет

**Продукт.** Во время импорта книги ссылки из уже выданного поиска на фрагменты **этой же книги** перестают открываться (`evidence_withdrawn`), хотя сам фрагмент не менялся.

**Доказательство (проверено RKB-Opus).** `kaggle_query.py` ~L307–319: чтение точного пассажа требует `row[6] == locator.source.eligibility_revision` (через JOIN `source_visibility`). Триггер `bump_source_visibility` (`sql/kaggle/004_read_fences.sql` ~L54–76) увеличивает `eligibility_revision` книги на **каждую вставку** пассажа в её активную ревизию — то есть на каждый принятый пакет.

**Сделать.** В точном чтении пассажа (`kaggle_query.py`, ветка continuation/exact) удалить сравнение `row[6] != locator.source.eligibility_revision`, колонку `v.eligibility_revision` из SELECT и JOIN `source_visibility`. Оставить: точные `passage_id/source_id/revision`, активную ревизию, `s.accepted AND NOT s.withdrawn`, сравнение `database_generation`.

**Нельзя.** Менять формат локатора/ID, SQL-функции, write-путь снятия книги (там `expected eligibility` защищает настоящую мутацию), чтение Case.

**Бюджет.** Только удаление.

**Тест (один).** Реальный PG17: поиск выдаёт ID пассажа A; принимается новый текстовый пакет B той же книги; fetch A возвращает тот же текст. Существующие тесты на снятие книги/смену ревизии/другую генерацию БД должны продолжать отказывать.

**Живая установка** — Шкипер (обработчик чтения на Kaggle).
