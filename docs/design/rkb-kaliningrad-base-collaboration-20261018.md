**Целевой контракт 20.10.2026, не доказательство deployed runtime.** [Единый handoff](../prompts/rkb-scalable-kaggle-implementation-20261019.md), [архитектура](../designs/rkb-scalable-kaggle-architecture-20261019.md), [дела](rkb-disagreement-journal-design-20261018.md) и [Story](../story-registry.md) задают общую модель. Baseline main a8cf41b50b8ccb62409d046d009d53c09d74b1d7; PR151 adf78a50013e2d8a2fbbe425c61f4ac479eaa0c4 — reusable незавершённая ветка, не live PASS. Наличие fairness/dialog/ACK/checkpoint code в ветке требует проверки при интеграции.

Только GEO-слои переносятся в новый corpus. Старые книги, Stories, дела, ручные/личные drafts, contributions и old jobs не мигрируют. Fresh MCP imports создают facts/cases и достаточные actual narratives заново; следующие правила сохранности относятся к новым данным.

## 1. Продукт и пользователи

**Kaliningrad Base** — отдельное Slack-приложение, единственный видимый пользователю бот. В Slack-пространстве экспертов **не требуется устанавливать или добавлять dot**: событие обрабатывается во внутреннем MCP-контуре, а пользователь видит только Kaliningrad Base. Историк, эксперт или верификатор разговаривает с ним в DM либо упоминает его в разрешённом канале. Он ничего не должен знать о dot. Dot — сменяемый внутренний исследовательский исполнитель; автором экспертного вклада считается установленный человек, а не бот/модель.

Владелец также может тестировать поиск и работу с делами через **этого же Kaliningrad Base** в DM или разрешённом канале. Его подтверждённый Slack-аккаунт связывается с уже существующим RKB owner; это не новый владелец и не расширение полномочий бота. Точное сопоставление и границы: [участники, §3.4](rkb-participants-poi-fact-bridge-20261018.md#34-владелец-как-испытатель-slack-маршрута-19102026). Статус дополнения от 19.10.2026: проект, без live-grant.

Бот отвечает на вопросы, ищет дела, показывает доступные материалы и выделенные области оригиналов (только при отдельном праве), сохраняет личные аргументы и подписки, возвращает ссылки на VK-обсуждение, принимает запросы на включение дела в обычную или срочную очередь. Понятны состояние запроса, ID дела и что можно сделать следующим шагом.

**Импорт PDF/DjVu, reprocess и массовый проход доступен только владельцу**, напрямую через его ChatGPT/MCP или dot в явно владельческом контуре. Не только кнопка, но и серверная операция start/resume/reprocess/finish защищена от экспертов. Даже владелец в маршруте экспертного бота не получает функцию импорта: это отдельный ограниченный интерфейс. Предметный вес эксперта не даёт дополнительные полномочия.

## 2. Один RKB backend и существующий durable request protocol

**Согласованное решение владельца от 25.10.2026:** «Поиск и пробуждение исполнителя идут параллельно с корреляцией исходного запроса; итог — связный ответ с источниками, без ограничения тремя карточками».

Это целевой контракт, не утверждение о готовности RKB MCP Events и инструмента записи коррелированного ответа. Исходные `event_id`/`request_id`, подтверждённый Slack-инициатор и исходный thread/DM связывают поиск, пробуждение, результат и единственную отправку; служебная корреляция не становится частью поискового текста. Исполнитель отвечает от ограниченного RKB service route, не от имени владельца. До подтверждённой подписки dot и проверки полного Slack E2E связный ответ не считается работающим.

**Целевой путь принятого durable Slack-вопроса:**
1. Slack Events API / Socket Mode → небольшое приложение Kaliningrad Base проверяет происхождение события и извлекает team_id, user_id, thread/message ID.
2. РКБ атомарно сохраняет входной запрос, действительные полномочия, допустимый ответ и ключ дедупликации в существующем request journal/jobs/events на DevCoveer. Early local receipt означает pending; продуктовый accepted требует exact remote intake по handoff. Бот не ждёт модель для технического подтверждения получения.
3. MCP Events будит разрешённого исполнителя. Он получает запрос в экспертном профиле, использует существующие/расширенные MCP методы и сохраняет коррелированный результат; canonical записи делает один PG/Kaggle writer.
4. Kaliningrad Base доставляет ответ в исходный thread/DM своим именем; durable journal сохраняет result hash, provider receipt и native client ACK. Принятие, работа, сохранённый результат и доставка различаются; ACK другого request/hash не завершает этот запрос.
5. При сбое dot принятые задания остаются в очереди; любой разрешённый исполнитель может продолжить по ID без нового пользовательского сообщения.

Это **не уже работающая цепочка**. Подтверждён только [Projects Hub MCP Events MVP от 13.10.2026](https://github.com/onedayonemasterpiece/projects-hub/blob/7a45193661ca879deced51ee404c2b180d53c368/docs/reports/mcp-events-mvp0-20261013.md): один разрешённый owner-маршрут будил dot, сохранял ответ и доставлял его в Slack. Старый PH start_question_session_from_service действует от owner_actor_id, а отправителем был dot. Эти полномочия и отправителя переносить нельзя. Не основывать решение на непроверенном варианте «бот упомянул dot». Переиспользовать **протокол** сохранённого запроса/MCP-события/коррелированного результата, а не owner-only реализацию или дополнительный центральный шлюз.

Slack Socket Mode не требует публичного Request URL; HTTP-альтернатива требует проверки HMAC X-Slack-Signature по **сырому телу**, timestamp и защите от replay. Для обоих режимов обязательны доверенный источник и уникальность event ID. Параллельные задания разных акторов получают раздельный исполняемый контекст по trusted request ID и recipient scope: dot не должен подмешивать ответ/свидетельства из собственного предыдущего запроса или постоянной личной памяти другого эксперта. `get_request`, `record_result`, `status` и `claim_delivery` проверяют связку actor+request+route+generation на сервере; запоздалый/чужой `record_result` отклоняется. Перед выдачей и отправкой повторно проверяются эффективные разрешения и принадлежность результата исходному запросу. HTTP Events API требует acknowledgement до 3 секунд и делает повторные доставки. Его transport ACK после защищённого локального intake не равен продуктовым accepted/Saved: они требуют exact remote intake/outcome соответственно; cloud RTT не обещается уложить в transport deadline. Не считать сообщение «принято» готовым ответом. В Slack по ответам учитывать 429/Retry-After и состояние канала.

### 2.1. Общий контур нагрузки и Kaggle

Корпус, facts, Stories, cases и evidence живут в одном PostgreSQL/pgvector на Kaggle. Исходящий WSS notebook → existing DevCoveer ASGI использует одну admission/BgeQueue/controller authority и один fenced writer. Durable_question/request и mutation/provider-effect сохраняют exact remote intake/outcome, ACK/RESUME, receipts и UNKNOWN. Обычный read_query использует RAM permit и QUERY/QUERY_RESULT/CANCEL_QUERY без durable row, fsync, seal, RESUME или resultSaved. Nested read принятого вопроса не создаёт новый human request. BGE-only, без E5/Supabase target, локального encoder, новой очереди Slack и отдельного research scheduler. Сеть/модель не удерживают write transaction; pending durable-вопроса не означает потерю принятой работы.

Один canonical person имеет одну fair admission identity во всех подтверждённых каналах. У durable-вопросов dialog sequence сохраняет порядок ближайших вопросов человека; ссылка вне этого контекста требует explicit request ID. Арифметический ETA≤10s не порождает notices; >10s и значимые изменения дают durable coalesced notice только для ближайшего вопроса этого человека. Final result имеет приоритет и подавляет устаревшие notices. Обычная нагрузка не тратит outage retry budget. Перезапуск/replay не создаёт новые requests или второй ответ; unknown delivery сначала сверяется по receipt. Ephemeral read имеет исходный deadline/generation и min_data_seq, не обещает отложенный ответ. Existing control index проверяет unresolved mutations по canonical person и typed resource/scope dependencies во всех Dot/Mira/MCP routes на старте/выдаче read: пересечение даёт prior_write_pending с известной freshness. Общие ресурсы затрагивают всех соответствующих читателей; unrelated private-draft UNKNOWN не блокирует accepted-book search, недоказанную независимость считать зависимостью. Это отдельно от per-dialog порядка и не создаёт новый журнал/очередь; см. [handoff §§5.2, 10.2](../prompts/rkb-scalable-kaggle-implementation-20261019.md).

## 3. Атрибуция, полномочия и конфиденциальность

Канонический request envelope, заполняемый **сервером**: реальный инициатор (подтверждённый workspace/enterprise/team + Slack user ID и, при связке, платформенный UUID), технический service principal, модель-исполнитель, исходные channel/thread/message/event ID и версия, task/request ID, action и ресурсы/ревизии, дедупликационный ключ, разрешённый объём ответа, destination, время и статусы.

**Никакой actor_id, роль, owner=true или «владелец разрешил» из пользовательского текста не даёт прав.** РКБ проверяет пересечение прав подтверждённого инициатора, разрешённой категории expert-обслуживания, сервисного профиля и действующих ограничений ресурса/аудитории. Accepted active book text/bibliography ищутся без per-book owner ACL, illustrations публичны; source withdrawal, private drafts и непубличные participant data проверяются. Dot не вправе выполнять экспертный запрос с owner-правами своего другого подключения. Для экспертного исполнения нужен ограниченный RKB service route с привязкой к сохранённому request ID; права импортировать по нему отсутствуют. Проверять разрешения при приёме, чтении, записи, перед асинхронной доставкой и после их отзыва; кешированный proof не может обойти отзыв.

Автор исходного высказывания, человек, отправивший запрос, сервис и модельный пересказ — разные поля. Исправления и удаления сообщений версиями, не заменяя бесследно историческую запись. Личное одобрение относится к **точной** версии заключения; мнение не возникает автоматически из слов модели. Связь Slack/VK/platform идентичности подтверждается отдельно, не совпадением имени.

**Назначение proof по политике владельца:** категория demo/expert/local_historian, подтверждённая как owner_attested или independently_verified, атомарно материализует **существующий scan_proof_read grant** вместе с audit и source category revision; для demo фиксируется expiry. Claimed категория прав не создаёт. Render/read проверяет текущую capability и scope/expiry, без второго category bypass. Независимый revoke действует немедленно и не отменяется чтением или повтором прежнего события. Удаление категории отзывает только policy-derived grant/его основание; отдельные explicit grants не переписываются и не выдаются за категорийные. Повторное назначение после revoke требует нового разрешённого owner-policy действия. Это назначение существующего права, без нового IAM, pixel registry или ручного одобрения каждого изображения.

Профессиональный proof возвращает document/revision/page/region и выделение **на оригинале**, плюс отдельные метки area_located, model_visually_checked, human_verified. Совпадение OCR или изображённое выделение не равны независимой человеческой верификации. Если изображение не отрисовано/нет прав — честно отдать текст и статус, а не изображение чужой страницы. **Любой групповой маршрут** — публичный канал, закрытый/private канал и group DM — потенциально содержит участников с несовпадающими ACL. Даже если H имеет scan_proof_read, group thread может раскрыть полосу/страницу участнику V без этого права. Публичные accepted text и illustrations при этом не становятся частными из-за uploader. По умолчанию групповой ответ использует только разрешённую для всей аудитории публичную проекцию; для непубличного доказательства бот предлагает личный проверенный DM/авторизованный viewer. Индивидуальную персональную проекцию в группе можно отправить только при отдельно доказанных правах **всех** доступных получателей (включая позднее добавленных — необходима повторная проверка при доставке). Page/stripe proof — только в разрешённое персональное пространство либо за авторизованной ссылкой, которая повторно проверяет доступ (без бессрочной публичной URL).

## 4. Пользовательский маршрут

**Владелец-испытатель:** проверенный ключ Slack `T0C82495TK5/U0C8C1QKWAG` разрешается в существующий owner UUID, после чего действует тот же путь bot → внутренний dot → РКБ → bot, без ручной пересылки от owner-подключения dot. Владелец ищет материалы/дела, открывает актуальную карточку и разрешённый proof, сохраняет личный черновик, явно вносит аргумент или поддерживает точную версию, подписывается и продолжает по case/operation ID. Каждая операция остаётся в пределах server-side capability, route и ACL; в группе даже запрос владельца получает только безопасную общую проекцию, частные материалы выдаются в проверенном личном DM/авторизованном viewer. Отзыв mapping или прав блокирует следующие действия и отложенную доставку. Этот маршрут не включает импорт или новое администрирование; ПМИ KB-41…45/E2E-8 ещё предстоит выполнить.

**Автотестирование владельцем:** этот маршрут предназначен и для автоматизированного E2E-8, не только для ручного smoke. Harness отправляет запрос через поддерживаемый коннектор/transport, аутентифицированный именно как O, и читает реальный ответ Kaliningrad Base плюс RKB operation readback. Техническое сообщение бота, подставленный user ID или искусственный event не заменяют сообщение владельца. Пока не подтверждён поддерживаемый owner-authored transport, именно Slack E2E имеет BLOCKED/implementation gap; это не блокирует component/integration автотесты предметных операций и отката. Используются только разрешённые тестовые case/operation IDs и идемпотентный повтор; новые grants и импорт через бота не появляются.

**Вопрос:** короткий ответ с текстовыми ссылками, оговорками и доступными источниками; отдельное действие «показать на скане», если есть право. Бот не сваливает на пользователя все документы и не изображает проверенной историю, если скан не прочитан.

**Рассказ:** запрос «расскажи» получает сохранённый existing Variant.body и exact default_variant_ref, отдельно от title/summary/rating/bibliography. Search даёт actual excerpt с меткой и ref либо полный короткий body; get/voice/read-export читают exact saved text без LLM-композиции на чтении. Достаточный импортный эпизод автоматически сохраняется базовым читаемым рассказом; drafting не скрывает shared body от Story readers и не даёт publish_ready. Личный черновик остаётся личным. None/needs_context не маскируются описанием потенциала.

**Подбор разногласий:** естественный вопрос, точное слово или фильтры (период/объект/место/автор/документ/тип/статус, требует сверки/открытое), курсор и упорядоченная выдача без скрытых дел. «Мои дела» имеет различимые режимы authored/contributed, assigned, following. Карточка: нейтральный вопрос, доступное краткое положение, ID, что осталось проверить, своё следующее действие и состояние VK.

**Собственное исследование:** выбор case ID → актуальные варианты и changes_since → личный анализ/черновик, видимый только автору → явное «внести аргумент в общее дело» → receipt с contribution ID и ревизией. Личный рабочий текст не становится автоматически общей позицией, выводом дела или публикацией VK. Частные черновики можно хранить как ограниченные автору вклады существующей таблицы contributions (private draft, publish/withdraw), без нового реестра. Дословный подтверждённый аргумент человека и интерпретация dot сохраняются отдельно; другой эксперт не видит чужих черновиков. Неясное намерение «поддерживаю» требует уточнения точной версии; независимые вклады не блокируют друг друга.

**Общее обсуждение:** готовая ссылка на *действительно опубликованный* зарегистрированный VK-пост или заявка «следующий свободный день», «ближайший слот» либо «срочно». Запрос не публикует ничего сам и не выдаёт будущую ссылку за существующую. Если пост уже есть, возвращать ту же ссылку; новый пост на ту же тему только отдельным явно разрешённым продолжением.

**Страница дела для всех:** Kaliningrad Base и владелец через MCP могут запросить `public_page` и получить **постоянную прямую ссылку** на опубликованную публичную Astro-страницу дела на `kenigevents.ru`; URL возвращается только после readback статического HTML. Ссылка доступна любому, у кого она есть: **для просмотра страницы не нужны вход, роль, бот, регистрация или отдельная авторизация**. Страница адаптивна для мобильного и десктопа и показывает только материалы, предназначенные для публикации: версии, книги с обложками и авторами, рецензии, аргументы сообщества, статус и предварительные выводы. Отозванные/непринятые источники, private participant data, full PDF, page/stripe proof без права публичного раскрытия и личные drafts не входят в public export. Accepted text/bibliography и illustrations не скрываются по owner ACL. Slug постоянный, но не является секретом/ACL. См. [требование к Astro](../requirements/disagreement-case-static-pages-20261019.md).

### 4.1. Безопасный откат автоматизированных проверок

**Обратимость автотеста на реальных книгах:** один `test_run_id` связывает baseline, case/revision, operation keys, собственные эффекты и receipts в существующих jobs/events/contributions. Отдельный test-service, база или реестр не нужны. Предпочтителен изолированный тестовый case/рабочая копия с ссылками на настоящие source revisions: выполняются те же domain operations, но PDF/DjVu, OCR, provenance и реальные экспертные данные неизменны. Тестовые аргументы, веса, поддержки и заключения не становятся действительными экспертными оценками, не меняют live search/сводки и не порождают реальные уведомления либо VK-очередь/публикацию.

Если без изменения канонического дела не обойтись, до запуска фиксируются исходные значения/ревизии и разрешённый набор изменений. Откат — узкая транзакционная CAS-компенсация **только эффектов данного run** через существующий авторизованный контур, с operation receipt и идемпотентным readback; допустима адресная очистка производных тестовых данных, но не общий DELETE, восстановление всей БД, удаление источников/аудита или чужих вкладов. Реальный поздний вклад эксперта сохраняется. Конфликт ревизий помечается `rollback_conflict` и требует сверки, не принудительной перезаписи. Повтор rollback безопасен; завершённый run получает state/generation fence, чтобы crash/resume, старый worker и поздний callback не создали эффект заново.

После компенсации отдельно проверяются дело, вклады/веса/поддержки/заключения, search/projections, подписки/уведомления и pending outbox/VK jobs: не осталось действующего тестового мнения или отложенной отправки. Дело возвращается к исходному ожиданию реальных экспертов, если таков baseline; независимое реальное экспертное действие/решение не отменяется. Только проверенные receipts и readback дают `rolled_back`; при сбое — видимый pending/conflict и безопасное продолжение, не ложная «чистота». Наличие отдельного Slack user-sender transport не требуется для component/integration автотестов этих domain operations; реальный Slack E2E проверяется отдельно.

## 5. VK-публикации: последовательный редакционный поток

Единица ограничения — **одно VK-сообщество + серия дел РКБ** (не все прочие рубрики сообщества), день по **Europe/Kaliningrad**. Начальная регулируемая политика: **до одного обычного нового поста/день**, при пустой очереди — ни одного; **до двух дополнительных срочных постов/день** с явным подтверждением владельца/назначенного редактора. Это предлагаемая настройка, не подтверждённый технический лимит VK. Приоритет «завтра» — перенос в следующий ещё свободный ordinary-slot с объяснением перестановки; не обход срочного ограничения. Конкурентные запросы сериализуются атомарно, включая in-flight.

Состояния одной публикации: proposed → prepared_public_pack → approved → regular/urgent slot_reserved → provider_scheduled → published с сохранёнными provider ID/URL; ошибки/cancelled/unknown_outcome отдельно. РКБ владеет выбором дел, очередью *редакционных решений*, правами, квотой и связью case/revision→VK post. **VibePublish** владеет нативной публикацией/переносом/отменой/чтением/ответами/удалением и receipt. Не строить второй VK-клиент, дублирующий календарный worker или таблицу фактически отправленных постов. Для обычной очереди передавать VibePublish требуемые будущие даты в нативное расписание провайдера. Поддержку и ограничения VK native scheduling подтвердить живым тестом — не предполагать по документации дизайна.

Подготовка и передача в расписание разрешены только из отдельного **публично допустимого пакета**: включая источник цитаты, выделение, подпись и все пересказы. Смена прав после планирования запускает отмену у провайдера и предупреждение владельцу при невозможности подтвердить отмену. **Слот нельзя освобождать при непроверенном исходе отмены или переноса**: статус `cancellation_unknown` сохраняет занятую reservation, provider operation ID и исходный день; следующий case B не получает этот regular-day до receipt, подтверждающего реальную отмену/перенос поста A. После timeout проводится reconcile фактического provider schedule; отсутствие ответа само по себе не является подтверждённой отменой. При необходимости день блокируется и оператор видит причину, а не выпускаются два поста. Нельзя обещать проверку «непосредственно перед VK publish», если автономный провайдер публикует уже запланированный пост. При неизвестном исходе **сначала** reconciliation с VibePublish/VK, а не новый send: двойная публикация хуже задержки.

Пакет связывает опубликованный фиксированный текст и изображения с ревизией дела. Существенное обновление объясняется новым комментарием/сводкой, а не молчаливой заменой прошлого поста. Бот возвращает VK-ссылку по receipt с точным post ID; публикация в очереди ещё без ссылки.

Whitelist-модерация касается лишь зарегистрированных case-постов. Проверить реальные права токена на тестовом посте, все ветви, комментарии от имени сообщества, режим ответов и удаление родителя с ответами экспертов. После простоя перечитать доступный срез, но не обещать восстановить неизвестные удалённые сообщения. Просроченный whitelist не является основанием удалять наугад.

## 6. Уведомления и брифинги

При завершённом импорте владелец получает source/revision, research coverage, новые/обновлённые cases, saved narratives и gaps/errors. Source accepted, retrieval ready, research pending/completed, narrative readback и downstream POI delivery различаются. Эксперты получают active accepted bibliography/текст и публичные illustrations, доступные дела/подписки, приглашения по специализации и подтверждённую VK-ссылку. Отозванные/непринятые источники, private drafts/participants и proof без grant не раскрываются через titles/counters/уведомления.

У сообщения есть event/revision, recipient/route, разрешённая проекция, dedup key, статус/receipt и время. Подписки и периодический digest — по выбору участника, без обязательного спама. Перед отправкой повторная проверка прав, роли, маршрута и публичного содержимого. Slack ephemeral может помогать в интерактивности, но **не является** долговременной записью (его доставка не гарантируется).

## 7. Достаточность MCP-инструментов

**Не создавать отдельный MCP tool на каждую кнопку.** К группам §8 v3 добавляются конкретные параметры и один небольшой интерфейс для сохранённых запросов:

| Группа | Требуемое уточнение |
|---|---|
| disagreement_search/get | Семантические представления, устойчивые фильтры/курсоры, мои contributed/assigned/following, changes_since, ACL |
| disagreement_contribute/conclusion | Дословный личный вклад, actor/provenance, действие подтвердить точную версию, expected_revision, operation_status |
| source_proof | Original revision, locator/region, уровни сверки, авторизованный private viewer/рендер |
| disagreement_discussion | propose/priority_request/approve/reserve/prepare/bind/status/sync/cancel, regular/urgent слот и внешний receipt |
| disagreement_participants | Связь реальных идентичностей, предметные веса, индивидуальные подписки/предпочтения |
| disagreement_export | Разрешённый для конкретного адресата/public пакет; last_supported/current и proof warnings |
| **expert_request_delivery** (маленькая группа на базе существующих jobs/events) | accept/get/claim/record_result/status/claim_delivery/receipt; trusted route/actor, correlation и dedup |

Вся запись проходит серверную проверку прав, не только подсказку модели. Длинный результат содержит cursor/has_more. Незавершённая доставка не считается успешно завершённой обработкой пользователя. Операция публикации и экспертиза не превращаются в единый неотменяемый вызов.

## 8. Projects Hub/Mira/mobile — тот же RKB контракт

Slack — заменяемый клиентский адаптер; Mira остаётся клиентом Projects Hub, а не отдельным RKB помощником. **Dot→tools и Mira→tools — независимые умные маршруты**: Dot сохраняется, но не вставляется в обычный запрос Миры. PH typed provider обращается к existing Dev auth/admission и WSS, который инициировал notebook. Existing Knowledge adapter в baseline search-only: v2 расширяет status/freshness/min-cursor/continuation, Stories/cases/proof и exact revision/readback; durable pending/request/result/native ACK относится только к соответствующему принятому вопросу/эффекту. Наличие PH owner-only доступа не доказывает готовую multi-user интеграцию.

Same-host service calls используют loopback machine identity и verified delegated actor/request context; нельзя создавать OAuth-flow между собственными локальными сервисами или подставлять owner-token. Внешний клиент получает действительный resource-bound grant. PH actor usr_… и RKB UUID связываются подтверждённым mapping, не строковой подстановкой. PH не дублирует cases/weights, не становится новым IdP и не создаёт второго dot.

Live read_query получает компактный реальный body/excerpt+ref и явные status/freshness, без durable ACK/RESUME. Профессиональное исследование использует полный типизированный профиль; принятый durable вопрос/эффект сохраняет pending/result/native hash ACK. Short display не скрывает незавершённость или exact version. Строгий v1 evidence/mode adapter выдаёт success лишь для полностью представимого результата, иначе existing unavailable/error, не empty hybrid. Canonical person и fair admission общие; durable dialog order и ACK с проверкой route/hash сохраняются. Cancel/закрытие read не отменяет и не повторяет accepted effect; stale generation/current revoke/withdrawal исключают позднюю выдачу.

Перед выдачей policy delta проверяется по полным source/variant/grant dependencies item, включая cross-book текст и bibliography. Исключается весь affected item с display/continuation; оставшийся ответ — degraded/evidence_withdrawn даже при нуле items, не empty ok. Незатронутые reads продолжаются, но неполный provenance/compacted delta/недоказанный scope требуют fail closed; cursor один не доказывает права. Remote-durable barrier подтверждает блокировку новой RKB-выдачи без ожидания Kaggle, а PG withdrawal/public purge остаются pending до собственных commit/readback по [handoff §§6, 10.1](../prompts/rkb-scalable-kaggle-implementation-20261019.md).

PH асинхронно сохраняет exact ordered evidence/context refs в existing private tool/utterance store по `(session, turn_generation, tool_call_id)`, с committed-turn binding/disposition. Ephemeral ответ checkpoint не ждёт; crash до записи даёт явный context_gap/evidence_context_unavailable, а не новый поиск под видом источников старого ответа. Continuation/context ref не capability и повторно проверяет права. Это recovery диалога, не disposable telemetry и не гарантия durable RKB read; см. [handoff §10.4](../prompts/rkb-scalable-kaggle-implementation-20261019.md).

После реального PH provider выполнить [handoff §14.4](../prompts/rkb-scalable-kaggle-implementation-20261019.md): отдельно сравнить Mira/Dot на одинаковом тексте запросов, corpus/revisions, правах и common tool profile/budget; отдельно — реальные пути с ASR/voice/Slack и их фактическими tool различиями. Качество, полнота и source grounding оцениваются вместе с временем первого полезного и полного ответа. Возможная команда «Мира, хорошо подумай»/делегирование Dot — future option после показанной пользы, не часть base implementation. Отсутствующий provider/pilot — NOT RUN, не предполагаемое преимущество модели.

## 8.1. Создание участника и объединение его внешних аккаунтов

Владелец управляет профилем человека через свой MCP: категория demo/student/research_staff/expert/guide/local_historian, регалии (claimed/verified), предметные веса, права на text/proof/вклады/общие заключения, expiry и отдельные grants. Категория не равна разрешению: научная степень не даёт scan_proof_read, доступ к full PDF или чужому private draft, а статус гида не означает нулевой профессиональный вес. Используется существующий контракт rkb_users UUID и авторизации, не новый центр аккаунтов; это не требование перенести прежние книги, drafts, cases или contributions.

Связка external provider account — отдельно подтверждённая принадлежность: Slack workspace+user, VK конкретный положительный user ID, Projects Hub usr_… через подтверждённую сессию/делегацию, а не одинаковое отображаемое имя. Один человек имеет один RKB UUID и несколько verified mappings; отозванный канал перестаёт давать новые права, старые вклады сохраняют происхождение. Библиографический автор книги и участник — разные реестровые роли, их можно связать только явно.

Точный контракт и owner-only операции: [участники и POI-факты](rkb-participants-poi-fact-bridge-20261018.md). В ПМИ добавлены проверки owner provision, verified multi-account, expiry и ошибочной идентичности. Baseline PH actor и RKB UUID несовместимы напрямую; existing owner invite не является multi-user доступом. Same-host adapter использует доверенный service route с verified actor, внешний клиент — действительный resource grant.
