# Kaliningrad Base — экспертная коллаборация, Slack и VK

**Дополнение к проекту РКБ v3.1, 18.10.2026. Статус: проект, не внедрение.** Связанные документы: [журнал разногласий](rkb-disagreement-journal-design-20261018.md) и [программа и методика испытаний](../testing/rkb-disagreement-pmi-20261018.md).

## 1. Продукт и пользователи

**Kaliningrad Base** — отдельное Slack-приложение, единственный видимый пользователю бот. Историк, эксперт или верификатор разговаривает с ним в DM либо упоминает его в разрешённом канале. Он ничего не должен знать о dot. Dot — сменяемый внутренний исследовательский исполнитель; автором экспертного вклада считается установленный человек, а не бот/модель.

Бот отвечает на вопросы, ищет дела, показывает доступные материалы и выделенные области оригиналов (только при отдельном праве), сохраняет личные аргументы и подписки, возвращает ссылки на VK-обсуждение, принимает запросы на включение дела в обычную или срочную очередь. Понятны состояние запроса, ID дела и что можно сделать следующим шагом.

**Импорт PDF/DjVu, reprocess и массовый проход доступен только владельцу**, напрямую через его ChatGPT/MCP или dot в явно владельческом контуре. Не только кнопка, но и серверная операция start/resume/reprocess/finish защищена от экспертов. Даже владелец в маршруте экспертного бота не получает функцию импорта: это отдельный ограниченный интерфейс. Предметный вес эксперта не даёт дополнительные полномочия.

## 2. Архитектура — один backend РКБ, один процесс данных

**Целевой путь:**
1. Slack Events API / Socket Mode → небольшое приложение Kaliningrad Base проверяет происхождение события и извлекает team_id, user_id, thread/message ID.
2. РКБ атомарно сохраняет входной запрос, действительные полномочия, допустимый ответ и ключ дедупликации в существующем SQLite/jobs/events. Бот подтверждает приём, не ждёт модель.
3. MCP Events будит dot. Dot получает только разрешённый запрос в экспертном профиле, вызывает имеющиеся/новые инструменты РКБ и сохраняет коррелированный ответ.
4. Только Kaliningrad Base (не dot) доставляет ответ в исходный тред/DM своим именем; РКБ хранит delivery receipt. Стадии приёма, работы, результата и доставки различаются.
5. При сбое dot принятые задания остаются в очереди; любой разрешённый исполнитель может продолжить по ID без нового пользовательского сообщения.

Это **не уже работающая цепочка**. Подтверждён только [Projects Hub MCP Events MVP от 13.10.2026](https://github.com/onedayonemasterpiece/projects-hub/blob/7a45193661ca879deced51ee404c2b180d53c368/docs/reports/mcp-events-mvp0-20261013.md): один разрешённый owner-маршрут будил dot, сохранял ответ и доставлял его в Slack. Старый PH start_question_session_from_service действует от owner_actor_id, а отправителем был dot. Эти полномочия и отправителя переносить нельзя. Не основывать решение на непроверенном варианте «бот упомянул dot». Переиспользовать **протокол** сохранённого запроса/MCP-события/коррелированного результата, а не owner-only реализацию или дополнительный центральный шлюз.

Slack Socket Mode не требует публичного Request URL; HTTP-альтернатива требует проверки HMAC X-Slack-Signature по **сырому телу**, timestamp и защите от replay. Для обоих режимов обязательны доверенный источник и уникальность event ID. HTTP Events API требует acknowledgement до 3 секунд и делает повторные доставки; durable accept предшествует подтверждению. Не считать сообщение «принято» готовым ответом. В Slack по ответам учитывать 429/Retry-After и состояние канала.

## 3. Атрибуция, полномочия и конфиденциальность

Канонический request envelope, заполняемый **сервером**: реальный инициатор (подтверждённый workspace/enterprise/team + Slack user ID и, при связке, платформенный UUID), технический service principal, модель-исполнитель, исходные channel/thread/message/event ID и версия, task/request ID, action и ресурсы/ревизии, дедупликационный ключ, разрешённый объём ответа, destination, время и статусы.

**Никакой actor_id, роль, owner=true или «владелец разрешил» из пользовательского текста не даёт прав.** РКБ проверяет пересечение прав подтверждённого инициатора, разрешённой категории expert-обслуживания, сервисного профиля и ACL каждого источника. Dot не вправе выполнять экспертный запрос с owner-правами своего другого подключения. Для экспертного исполнения нужен ограниченный RKB service route с привязкой к сохранённому request ID; права импортировать по нему отсутствуют. Проверять разрешения при приёме, чтении, записи, перед асинхронной доставкой и после их отзыва; кешированный proof не может обойти отзыв.

Автор исходного высказывания, человек, отправивший запрос, сервис и модельный пересказ — разные поля. Исправления и удаления сообщений версиями, не заменяя бесследно историческую запись. Личное одобрение относится к **точной** версии заключения; мнение не возникает автоматически из слов модели. Связь Slack/VK/platform идентичности подтверждается отдельно, не совпадением имени.

| Действие | Читатель | Эксперт | Ведущий/верификатор | Владелец |
|---|:---:|:---:|:---:|:---:|
| Доступный текстовый поиск/дела | Да | Да | Да | Да |
| Собственные аргументы/подписки | По явному праву | Да | Да | Да |
| Оригинальный скан с выделением | По отдельному **can_read_scan_proof** + ACL | То же | То же | По ACL |
| Поддержать точную версию заключения | По отдельному праву | По предметному допуску | Да | По допуску |
| Общая сводка, веса и роли | Нет | Нет | По явно назначенной компетенции | Да |
| Запросить ближайший слот/срочный пост | Нет | Да | Да | Да |
| Разрешить фактический срочный выпуск | Нет | Нет | Только роль редактора | Да |
| Импорт и массовая обработка | Нет | Нет | Нет | Только личный владельческий маршрут |

Профессиональный proof возвращает document/revision/page/region и выделение **на оригинале**, плюс отдельные метки area_located, model_visually_checked, human_verified. Совпадение OCR или изображённое выделение не равны независимой человеческой верификации. Если изображение не отрисовано/нет прав — честно отдать текст и статус, а не изображение чужой страницы. В публичный Slack-канал/общее уведомление отправлять лишь отдельную разрешённую проекцию; закрытые сканы — только в персональное пространство либо за авторизованной ссылкой, которая повторно проверяет доступ (без бессрочной публичной URL).

## 4. Пользовательский маршрут

**Вопрос:** короткий ответ с текстовыми ссылками, оговорками и доступными источниками; отдельное действие «показать на скане», если есть право. Бот не сваливает на пользователя все документы и не изображает проверенной историю, если скан не прочитан.

**Подбор разногласий:** естественный вопрос, точное слово или фильтры (период/объект/место/автор/документ/тип/статус, требует сверки/открытое), курсор и упорядоченная выдача без скрытых дел. «Мои дела» имеет различимые режимы authored/contributed, assigned, following. Карточка: нейтральный вопрос, доступное краткое положение, ID, что осталось проверить, своё следующее действие и состояние VK.

**Собственное исследование:** выбор case ID → актуальные варианты и changes_since → добавить аргумент/источник/личное заключение → receipt с contribution ID и ревизией. Дословный аргумент человека и интерпретация dot сохраняются отдельно. Неясное намерение «поддерживаю» требует уточнения версии; независимые вклады не блокируют друг друга.

**Общее обсуждение:** готовая ссылка на *действительно опубликованный* зарегистрированный VK-пост или заявка «следующий свободный день», «ближайший слот» либо «срочно». Запрос не публикует ничего сам и не выдаёт будущую ссылку за существующую. Если пост уже есть, возвращать ту же ссылку; новый пост на ту же тему только отдельным явно разрешённым продолжением.

## 5. VK-публикации: последовательный редакционный поток

Единица ограничения — **одно VK-сообщество + серия дел РКБ** (не все прочие рубрики сообщества), день по **Europe/Kaliningrad**. Начальная регулируемая политика: **до одного обычного нового поста/день**, при пустой очереди — ни одного; **до двух дополнительных срочных постов/день** с явным подтверждением владельца/назначенного редактора. Это предлагаемая настройка, не подтверждённый технический лимит VK. Приоритет «завтра» — перенос в следующий ещё свободный ordinary-slot с объяснением перестановки; не обход срочного ограничения. Конкурентные запросы сериализуются атомарно, включая in-flight.

Состояния одной публикации: proposed → prepared_public_pack → approved → regular/urgent slot_reserved → provider_scheduled → published с сохранёнными provider ID/URL; ошибки/cancelled/unknown_outcome отдельно. РКБ владеет выбором дел, очередью *редакционных решений*, правами, квотой и связью case/revision→VK post. **VibePublish** владеет нативной публикацией/переносом/отменой/чтением/ответами/удалением и receipt. Не строить второй VK-клиент, дублирующий календарный worker или таблицу фактически отправленных постов. Для обычной очереди передавать VibePublish требуемые будущие даты в нативное расписание провайдера. Поддержку и ограничения VK native scheduling подтвердить живым тестом — не предполагать по документации дизайна.

Подготовка и передача в расписание разрешены только из отдельного **публично допустимого пакета**: включая источник цитаты, выделение, подпись и все пересказы. Смена прав после планирования запускает отмену у провайдера и предупреждение владельцу при невозможности подтвердить отмену. Нельзя обещать проверку «непосредственно перед VK publish», если автономный провайдер публикует уже запланированный пост. При неизвестном исходе **сначала** reconciliation с VibePublish/VK, а не новый send: двойная публикация хуже задержки.

Пакет связывает опубликованный фиксированный текст и изображения с ревизией дела. Существенное обновление объясняется новым комментарием/сводкой, а не молчаливой заменой прошлого поста. Бот возвращает VK-ссылку по receipt с точным post ID; публикация в очереди ещё без ссылки.

Whitelist-модерация касается лишь зарегистрированных case-постов. Проверить реальные права токена на тестовом посте, все ветви, комментарии от имени сообщества, режим ответов и удаление родителя с ответами экспертов. После простоя перечитать доступный срез, но не обещать восстановить неизвестные удалённые сообщения. Просроченный whitelist не является основанием удалять наугад.

## 6. Уведомления и брифинги

При завершённом импорте владелец получает источник/ревизию, покрытие, число **новых и обновлённых** дел и ошибки. Отличать состояние «текст активен, scan pending» от «полный импорт завершён». Эксперты получают только разрешённые им новые книги/дела, изменения подписок, приглашения по специализации и подтверждённую VK-ссылку. Не объявлять счётчик скрытых дел или название закрытой книги в общем канале.

У сообщения есть event/revision, recipient/route, разрешённая проекция, dedup key, статус/receipt и время. Подписки и периодический digest — по выбору участника, без обязательного спама. Перед отправкой повторная проверка прав, роли, маршрута и публичного содержимого. Slack ephemeral может помогать в интерактивности, но **не является** долговременной записью (его доставка не гарантируется).

## 7. Достаточность MCP-инструментов

**Не создавать отдельный MCP tool на каждую кнопку.** К группам §8 v3 добавляются конкретные параметры и один небольшой интерфейс для сохранённых запросов:

| Группа | Требуемое уточнение |
|---|---|
| disagreement_search/get | Семантические представления, устойчивые фильтры/курсоры, мои contributed/assigned/following, changes_since, ACL |
| disagreement_contribute/conclusion | Дословный личный вклад, actor/provenance, действие подтвердить точную версию, expected_revision, operation_status |
| source_proof | Original revision, locator/region, уровни сверки, авторизованный private viewer/рендер |
| disagreement_discussion | propose/priority_request/approve/reserve/prepare/bind/status/sync/cancel, regular/urgent слот и внешний receipt |
| disagreement_participants | Связь реальных идентичностей, предметные веса, индивидуальные подписки/предпочтения |
| disagreement_export | Разрешённый для конкретного адресата/public пакет; last_supported/current и proof warnings |
| **expert_request_delivery** (маленькая группа на базе существующих jobs/events) | accept/get/claim/record_result/status/claim_delivery/receipt; trusted route/actor, correlation и dedup |

Вся запись проходит серверную проверку прав, не только подсказку модели. Длинный результат содержит cursor/has_more. Незавершённая доставка не считается успешно завершённой обработкой пользователя. Операция публикации и экспертиза не превращаются в единый неотменяемый вызов.

## 8. Будущее Projects Hub/Mira/mobile

UI-адаптер Slack заменяем. Профиль исследования, ACL, case ID, версии, источники и события принадлежат РКБ. В Projects Hub проектом становится «База знаний региона», пользователь получает *тот же* Knowledge MCP/API через одобренную для ресурса платформенную OAuth-делегацию с собственным actor UUID. Slack team/user ID — внешний идентификатор, связанный с платформенным только после подтверждения; не универсальный аккаунт. Projects Hub не дублирует дела/веса, не превращается в IdP и не требует отдельного «второго dot». Для Live-коротких ответов допустим компактный профиль, для профессионального исследования — полный с explicit actions и подтверждением.
