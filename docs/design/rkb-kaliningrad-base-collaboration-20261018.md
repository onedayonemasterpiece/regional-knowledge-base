# Kaliningrad Base — экспертная коллаборация, Slack и VK

## Применение в переработке 19.10.2026

Нормативный целевой контракт: [единый файл агенту](../prompts/rkb-scalable-kaggle-implementation-20261019.md) и [архитектура](../designs/rkb-scalable-kaggle-architecture-20261019.md). Текущий runtime ещё не перенесён этой документационной задачей.

- Один PostgreSQL/pgvector corpus в Kaggle, BGE-only (1024 FP32 baseline, exact pinned BGE input≤512); небольшой durable control journal на DevCoveer.
- Прямой исходящий WSS notebook→existing DevCoveer ASGI с двусторонними заданиями/результатами, durable ACK/RESUME и одной BgeQueue authority. Старые polling/локальный E5/Supabase инструкции не целевой deployment.
- Fresh MCP import книг; перенос только historical/cartographic layers и согласованных зависимостей, со stable IDs/provenance и проверенным reanchor. Ручная работа не уничтожается из-за отказа от старого corpus.
- Source-bound facts/dates/observations сохраняются без обязательной Story; эпизод/досье/Variant/private draft/independent case различаются. Один persisted research workflow, bounded compose, без квот и выдуманной драматургии.
- Поиск accepted active book text и bibliography без per-book owner ACL; current withdrawal/revision, pixels/original/private draft grants и delivery audience остаются обязательными.
- One canonical person/request/dialog, fair admission и confirmed result/hash ACK; Мира в PH расширяет existing typed adapter, не создаёт отдельный voice/IAM/queue.

Численные protected gates сохранены: backend p95≤1000ms, MCP p95≤1500ms/hard2000ms, BGE Hit@5≥85%/@10≥90%, RU→DE@10≥85%, ≥30 held-out families, ≥100 sources/100000 chunks, storage≤80% steady/≤90% peak. Документ не является доказательством PASS.

## 1. Продукт и пользователи

**Kaliningrad Base** — отдельное Slack-приложение, единственный видимый пользователю бот. В Slack-пространстве экспертов **не требуется устанавливать или добавлять dot**: событие обрабатывается во внутреннем MCP-контуре, а пользователь видит только Kaliningrad Base. Историк, эксперт или верификатор разговаривает с ним в DM либо упоминает его в разрешённом канале. Он ничего не должен знать о dot. Dot — сменяемый внутренний исследовательский исполнитель; автором экспертного вклада считается установленный человек, а не бот/модель.

Владелец также может тестировать поиск и работу с делами через **этого же Kaliningrad Base** в DM или разрешённом канале. Его подтверждённый Slack-аккаунт связывается с уже существующим RKB owner; это не новый владелец и не расширение полномочий бота. Точное сопоставление и границы: [участники, §3.4](rkb-participants-poi-fact-bridge-20261018.md#34-владелец-как-испытатель-slack-маршрута-19102026). Статус дополнения от 19.10.2026: проект, без live-grant.

Бот отвечает на вопросы, ищет дела, показывает доступные материалы и выделенные области оригиналов (только при отдельном праве), сохраняет личные аргументы и подписки, возвращает ссылки на VK-обсуждение, принимает запросы на включение дела в обычную или срочную очередь. Понятны состояние запроса, ID дела и что можно сделать следующим шагом.

**Импорт PDF/DjVu, reprocess и массовый проход доступен только владельцу**, напрямую через его ChatGPT/MCP или dot в явно владельческом контуре. Не только кнопка, но и серверная операция start/resume/reprocess/finish защищена от экспертов. Даже владелец в маршруте экспертного бота не получает функцию импорта: это отдельный ограниченный интерфейс. Предметный вес эксперта не даёт дополнительные полномочия.

## 2. Архитектура — один backend РКБ, один процесс данных

**Целевой путь:**
1. Slack Events API / Socket Mode → небольшое приложение Kaliningrad Base проверяет происхождение события и извлекает team_id, user_id, thread/message ID.
2. РКБ атомарно сохраняет входной запрос, действительные полномочия, допустимый ответ и ключ дедупликации в существующем SQLite/jobs/events. Бот подтверждает приём, не ждёт модель.
3. MCP Events будит dot. Dot получает только разрешённый запрос в экспертном профиле, вызывает имеющиеся/новые инструменты РКБ и сохраняет коррелированный ответ.
4. Только Kaliningrad Base (не dot) доставляет ответ в исходный тред/DM своим именем; РКБ хранит delivery receipt. Стадии приёма, работы, результата и доставки различаются.
5. При сбое dot принятые задания остаются в очереди; любой разрешённый исполнитель может продолжить по ID без нового пользовательского сообщения.

Это **не уже работающая цепочка**. Подтверждён только [Projects Hub MCP Events MVP от 13.10.2026](https://github.com/onedayonemasterpiece/projects-hub/blob/7a45193661ca879deced51ee404c2b180d53c368/docs/reports/mcp-events-mvp0-20261013.md): один разрешённый owner-маршрут будил dot, сохранял ответ и доставлял его в Slack. Старый PH start_question_session_from_service действует от owner_actor_id, а отправителем был dot. Эти полномочия и отправителя переносить нельзя. Не основывать решение на непроверенном варианте «бот упомянул dot». Переиспользовать **протокол** сохранённого запроса/MCP-события/коррелированного результата, а не owner-only реализацию или дополнительный центральный шлюз.

Slack Socket Mode не требует публичного Request URL; HTTP-альтернатива требует проверки HMAC X-Slack-Signature по **сырому телу**, timestamp и защите от replay. Для обоих режимов обязательны доверенный источник и уникальность event ID. Параллельные задания разных акторов получают раздельный исполняемый контекст по trusted request ID и recipient scope: dot не должен подмешивать ответ/свидетельства из собственного предыдущего запроса или постоянной личной памяти другого эксперта. `get_request`, `record_result`, `status` и `claim_delivery` проверяют связку actor+request+route+generation на сервере; запоздалый/чужой `record_result` отклоняется. Перед выдачей и отправкой повторно проверяются эффективные разрешения и принадлежность результата исходному запросу. HTTP Events API требует acknowledgement до 3 секунд и делает повторные доставки; durable accept предшествует подтверждению. Не считать сообщение «принято» готовым ответом. В Slack по ответам учитывать 429/Retry-After и состояние канала.

## 3. Атрибуция, полномочия и конфиденциальность

Канонический request envelope, заполняемый **сервером**: реальный инициатор (подтверждённый workspace/enterprise/team + Slack user ID и, при связке, платформенный UUID), технический service principal, модель-исполнитель, исходные channel/thread/message/event ID и версия, task/request ID, action и ресурсы/ревизии, дедупликационный ключ, разрешённый объём ответа, destination, время и статусы.

**Никакой actor_id, роль, owner=true или «владелец разрешил» из пользовательского текста не даёт прав.** РКБ проверяет пересечение прав подтверждённого инициатора, разрешённой категории expert-обслуживания, сервисного профиля и ACL каждого источника. Dot не вправе выполнять экспертный запрос с owner-правами своего другого подключения. Для экспертного исполнения нужен ограниченный RKB service route с привязкой к сохранённому request ID; права импортировать по нему отсутствуют. Проверять разрешения при приёме, чтении, записи, перед асинхронной доставкой и после их отзыва; кешированный proof не может обойти отзыв.

Автор исходного высказывания, человек, отправивший запрос, сервис и модельный пересказ — разные поля. Исправления и удаления сообщений версиями, не заменяя бесследно историческую запись. Личное одобрение относится к **точной** версии заключения; мнение не возникает автоматически из слов модели. Связь Slack/VK/platform идентичности подтверждается отдельно, не совпадением имени.

| Действие | Читатель | Эксперт | Ведущий/верификатор | Владелец |
|---|:---:|:---:|:---:|:---:|
| Доступный текстовый поиск/дела | Да | Да | Да | Да |
| Собственные аргументы/подписки | По явному праву | Да | Да | Да |
| Оригинальный скан с выделением | По отдельному **can_read_scan_proof** + ACL | То же | То же | По ACL |
| Поддержать точную версию заключения | По отдельному праву | По предметному допуску | Да | По допуску |
| Общая сводка, веса и роли | Нет | Нет | По явно назначенной компетенции | Да |
| Запросить ближайший слот/срочный пост | Нет | Да | Да | Да |
| Разрешить фактический срочный выпуск | Нет | Нет | Только роль редактора | Да |
| Импорт и массовая обработка | Нет | Нет | Нет | Только личный владельческий маршрут |

Профессиональный proof возвращает document/revision/page/region и выделение **на оригинале**, плюс отдельные метки area_located, model_visually_checked, human_verified. Совпадение OCR или изображённое выделение не равны независимой человеческой верификации. Если изображение не отрисовано/нет прав — честно отдать текст и статус, а не изображение чужой страницы. **Любой групповой маршрут** — публичный канал, закрытый/private канал и group DM — потенциально содержит участников с несовпадающими ACL. Даже если инициатор H вправе читать закрытый источник, ответ в исходный групповой тред может раскрыть его V. По умолчанию групповой ответ использует только разрешённую для всей аудитории публичную проекцию; для непубличного доказательства бот предлагает личный проверенный DM/авторизованный viewer. Индивидуальную персональную проекцию в группе можно отправить только при отдельно доказанных правах **всех** доступных получателей (включая позднее добавленных — необходима повторная проверка при доставке). Закрытые сканы — только в персональное пространство либо за авторизованной ссылкой, которая повторно проверяет доступ (без бессрочной публичной URL).

## 4. Пользовательский маршрут

**Владелец-испытатель:** проверенный ключ Slack `T0C82495TK5/U0C8C1QKWAG` разрешается в существующий owner UUID, после чего действует тот же путь bot → внутренний dot → РКБ → bot, без ручной пересылки от owner-подключения dot. Владелец ищет материалы/дела, открывает актуальную карточку и разрешённый proof, сохраняет личный черновик, явно вносит аргумент или поддерживает точную версию, подписывается и продолжает по case/operation ID. Каждая операция остаётся в пределах server-side capability, route и ACL; в группе даже запрос владельца получает только безопасную общую проекцию, частные материалы выдаются в проверенном личном DM/авторизованном viewer. Отзыв mapping или прав блокирует следующие действия и отложенную доставку. Этот маршрут не включает импорт или новое администрирование; ПМИ KB-41…45/E2E-8 ещё предстоит выполнить.

**Автотестирование владельцем:** этот маршрут предназначен и для автоматизированного E2E-8, не только для ручного smoke. Harness отправляет запрос через поддерживаемый коннектор/transport, аутентифицированный именно как O, и читает реальный ответ Kaliningrad Base плюс RKB operation readback. Техническое сообщение бота, подставленный user ID или искусственный event не заменяют сообщение владельца. Пока не подтверждён поддерживаемый owner-authored transport, именно Slack E2E имеет BLOCKED/implementation gap; это не блокирует component/integration автотесты предметных операций и отката. Используются только разрешённые тестовые case/operation IDs и идемпотентный повтор; новые grants и импорт через бота не появляются.

**Вопрос:** короткий ответ с текстовыми ссылками, оговорками и доступными источниками; отдельное действие «показать на скане», если есть право. Бот не сваливает на пользователя все документы и не изображает проверенной историю, если скан не прочитан.

**Подбор разногласий:** естественный вопрос, точное слово или фильтры (период/объект/место/автор/документ/тип/статус, требует сверки/открытое), курсор и упорядоченная выдача без скрытых дел. «Мои дела» имеет различимые режимы authored/contributed, assigned, following. Карточка: нейтральный вопрос, доступное краткое положение, ID, что осталось проверить, своё следующее действие и состояние VK.

**Собственное исследование:** выбор case ID → актуальные варианты и changes_since → личный анализ/черновик, видимый только автору → явное «внести аргумент в общее дело» → receipt с contribution ID и ревизией. Личный рабочий текст не становится автоматически общей позицией, выводом дела или публикацией VK. Частные черновики можно хранить как ограниченные автору вклады существующей таблицы contributions (private draft, publish/withdraw), без нового реестра. Дословный подтверждённый аргумент человека и интерпретация dot сохраняются отдельно; другой эксперт не видит чужих черновиков. Неясное намерение «поддерживаю» требует уточнения точной версии; независимые вклады не блокируют друг друга.

**Общее обсуждение:** готовая ссылка на *действительно опубликованный* зарегистрированный VK-пост или заявка «следующий свободный день», «ближайший слот» либо «срочно». Запрос не публикует ничего сам и не выдаёт будущую ссылку за существующую. Если пост уже есть, возвращать ту же ссылку; новый пост на ту же тему только отдельным явно разрешённым продолжением.

**Страница дела для всех:** Kaliningrad Base и владелец через MCP могут запросить `public_page` и получить **постоянную прямую ссылку** на опубликованную публичную Astro-страницу дела на `kenigevents.ru`; URL возвращается только после readback статического HTML. Ссылка доступна любому, у кого она есть: **для просмотра страницы не нужны вход, роль, бот, регистрация или отдельная авторизация**. Страница адаптивна для мобильного и десктопа и показывает только материалы, предназначенные для публикации: версии, книги с обложками и авторами, рецензии, аргументы сообщества, статус и предварительные выводы. Закрытые источники и личные черновики не попадают в публичный экспорт. Slug постоянный, но не является секретом/ACL. См. [требование к Astro](../requirements/disagreement-case-static-pages-20261019.md).

### 4.1. Безопасный откат автоматизированных проверок

**Обратимость автотеста на реальных книгах:** один `test_run_id` связывает baseline, case/revision, operation keys, собственные эффекты и receipts в существующих jobs/events/contributions. Отдельный test-service, база или реестр не нужны. Предпочтителен изолированный тестовый case/рабочая копия с ссылками на настоящие source revisions: выполняются те же domain operations, но PDF/DjVu, OCR, provenance и реальные экспертные данные неизменны. Тестовые аргументы, веса, поддержки и заключения не становятся действительными экспертными оценками, не меняют live search/сводки и не порождают реальные уведомления либо VK-очередь/публикацию.

Если без изменения канонического дела не обойтись, до запуска фиксируются исходные значения/ревизии и разрешённый набор изменений. Откат — узкая транзакционная CAS-компенсация **только эффектов данного run** через существующий авторизованный контур, с operation receipt и идемпотентным readback; допустима адресная очистка производных тестовых данных, но не общий DELETE, восстановление всей БД, удаление источников/аудита или чужих вкладов. Реальный поздний вклад эксперта сохраняется. Конфликт ревизий помечается `rollback_conflict` и требует сверки, не принудительной перезаписи. Повтор rollback безопасен; завершённый run получает state/generation fence, чтобы crash/resume, старый worker и поздний callback не создали эффект заново.

После компенсации отдельно проверяются дело, вклады/веса/поддержки/заключения, search/projections, подписки/уведомления и pending outbox/VK jobs: не осталось действующего тестового мнения или отложенной отправки. Дело возвращается к исходному ожиданию реальных экспертов, если таков baseline; независимое реальное экспертное действие/решение не отменяется. Только проверенные receipts и readback дают `rolled_back`; при сбое — видимый pending/conflict и безопасное продолжение, не ложная «чистота». Наличие отдельного Slack user-sender transport не требуется для component/integration автотестов этих domain operations; реальный Slack E2E проверяется отдельно.

## 5. VK-публикации: последовательный редакционный поток

Единица ограничения — **одно VK-сообщество + серия дел РКБ** (не все прочие рубрики сообщества), день по **Europe/Kaliningrad**. Начальная регулируемая политика: **до одного обычного нового поста/день**, при пустой очереди — ни одного; **до двух дополнительных срочных постов/день** с явным подтверждением владельца/назначенного редактора. Это предлагаемая настройка, не подтверждённый технический лимит VK. Приоритет «завтра» — перенос в следующий ещё свободный ordinary-slot с объяснением перестановки; не обход срочного ограничения. Конкурентные запросы сериализуются атомарно, включая in-flight.

Состояния одной публикации: proposed → prepared_public_pack → approved → regular/urgent slot_reserved → provider_scheduled → published с сохранёнными provider ID/URL; ошибки/cancelled/unknown_outcome отдельно. РКБ владеет выбором дел, очередью *редакционных решений*, правами, квотой и связью case/revision→VK post. **VibePublish** владеет нативной публикацией/переносом/отменой/чтением/ответами/удалением и receipt. Не строить второй VK-клиент, дублирующий календарный worker или таблицу фактически отправленных постов. Для обычной очереди передавать VibePublish требуемые будущие даты в нативное расписание провайдера. Поддержку и ограничения VK native scheduling подтвердить живым тестом — не предполагать по документации дизайна.

Подготовка и передача в расписание разрешены только из отдельного **публично допустимого пакета**: включая источник цитаты, выделение, подпись и все пересказы. Смена прав после планирования запускает отмену у провайдера и предупреждение владельцу при невозможности подтвердить отмену. **Слот нельзя освобождать при непроверенном исходе отмены или переноса**: статус `cancellation_unknown` сохраняет занятую reservation, provider operation ID и исходный день; следующий case B не получает этот regular-day до receipt, подтверждающего реальную отмену/перенос поста A. После timeout проводится reconcile фактического provider schedule; отсутствие ответа само по себе не является подтверждённой отменой. При необходимости день блокируется и оператор видит причину, а не выпускаются два поста. Нельзя обещать проверку «непосредственно перед VK publish», если автономный провайдер публикует уже запланированный пост. При неизвестном исходе **сначала** reconciliation с VibePublish/VK, а не новый send: двойная публикация хуже задержки.

Пакет связывает опубликованный фиксированный текст и изображения с ревизией дела. Существенное обновление объясняется новым комментарием/сводкой, а не молчаливой заменой прошлого поста. Бот возвращает VK-ссылку по receipt с точным post ID; публикация в очереди ещё без ссылки.

Whitelist-модерация касается лишь зарегистрированных case-постов. Проверить реальные права токена на тестовом посте, все ветви, комментарии от имени сообщества, режим ответов и удаление родителя с ответами экспертов. После простоя перечитать доступный срез, но не обещать восстановить неизвестные удалённые сообщения. Просроченный whitelist не является основанием удалять наугад.

## 6. Уведомления и брифинги

При завершённом импорте владелец получает источник/ревизию, покрытие, число **новых и обновлённых** дел и ошибки. Отличать состояние «текст активен, scan pending» от «полный импорт завершён». Эксперты получают только разрешённые им новые книги/дела, изменения подписок, приглашения по специализации и подтверждённую VK-ссылку. Не объявлять счётчик скрытых дел или название закрытой книги в общем канале.

У сообщения есть event/revision, recipient/route, разрешённая проекция, dedup key, статус/receipt и время. Подписки и периодический digest — по выбору участника, без обязательного спама. Перед отправкой повторная проверка прав, роли, маршрута и публичного содержимого. Slack ephemeral может помогать в интерактивности, но **не является** долговременной записью (его доставка не гарантируется).

## 7. Достаточность MCP-инструментов

**Не создавать отдельный MCP tool на каждую кнопку.** К группам §8 v3 добавляются конкретные параметры и один небольшой интерфейс для сохранённых запросов:

| Группа | Требуемое уточнение |
|---|---|
| disagreement_search/get | Семантические представления, устойчивые фильтры/курсоры, мои contributed/assigned/following, changes_since, ACL |
| disagreement_contribute/conclusion | Дословный личный вклад, actor/provenance, действие подтвердить точную версию, expected_revision, operation_status |
| source_proof | Original revision, locator/region, уровни сверки, авторизованный private viewer/рендер |
| disagreement_discussion | propose/priority_request/approve/reserve/prepare/bind/status/sync/cancel, regular/urgent слот и внешний receipt |
| disagreement_participants | Связь реальных идентичностей, предметные веса, индивидуальные подписки/предпочтения |
| disagreement_export | Разрешённый для конкретного адресата/public пакет; last_supported/current и proof warnings |
| **expert_request_delivery** (маленькая группа на базе существующих jobs/events) | accept/get/claim/record_result/status/claim_delivery/receipt; trusted route/actor, correlation и dedup |

Вся запись проходит серверную проверку прав, не только подсказку модели. Длинный результат содержит cursor/has_more. Незавершённая доставка не считается успешно завершённой обработкой пользователя. Операция публикации и экспертиза не превращаются в единый неотменяемый вызов.

## 8. Будущее Projects Hub/Mira/mobile

UI-адаптер Slack заменяем. Профиль исследования, ACL, case ID, версии, источники и события принадлежат РКБ. В Projects Hub проектом становится «База знаний региона», пользователь получает *тот же* Knowledge MCP/API через одобренную для ресурса платформенную OAuth-делегацию с собственным actor UUID. Slack team/user ID — внешний идентификатор, связанный с платформенным только после подтверждения; не универсальный аккаунт. Projects Hub не дублирует дела/веса, не превращается в IdP и не требует отдельного «второго dot». Для Live-коротких ответов допустим компактный профиль, для профессионального исследования — полный с explicit actions и подтверждением.

## 8.1. Создание участника и объединение его внешних аккаунтов

Владелец управляет профилем человека через свой MCP: категория demo/student/research_staff/expert/guide/local_historian, регалии (claimed/verified), предметные веса, права на text/proof/вклады/общие заключения, expiry и отдельные grants. Категория не равна разрешению: научная степень не даёт право на чужую книгу, а статус гида не означает нулевой профессиональный вес. Существующие rkb_users UUID и ACL сохраняются, не нужен новый центр аккаунтов.

Связка external provider account — отдельно подтверждённая принадлежность: Slack workspace+user, VK конкретный положительный user ID, Projects Hub usr_… через подтверждённую сессию/делегацию, а не одинаковое отображаемое имя. Один человек имеет один RKB UUID и несколько verified mappings; отозванный канал перестаёт давать новые права, старые вклады сохраняют происхождение. Библиографический автор книги и участник — разные реестровые роли, их можно связать только явно.

Точный контракт и owner-only операции: [участники и POI-факты](rkb-participants-poi-fact-bridge-20261018.md). В ПМИ добавлены проверки owner provision, verified multi-account, expiry и ошибочной идентичности. В текущем Projects Hub actor и RKB UUID ещё несовместимы напрямую, а существующий PH invite/Knowledge OAuth не следует выдавать за готовый multi-user доступ.
