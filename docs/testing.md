# ПМИ: импорт, поиск и извлечение

Версия плана: 2026-10-16. База сверки кода: `aaac18305619d3bd8ea32a2b215eddade89ddcdc` (main после PR #120). Это программа и методика испытаний, **не отчёт о выполнении**. Результаты и повторные проверки ведутся в [журнале](testing-journal.md).

## Границы и условия старта

- Контракт: [MCP](mcp.md), [импорт](ingestion.md), [реестр историй](story-registry.md), [места](location-registry.md); защищённые пороги: [readiness](mass-ingestion-readiness.md) и [requirements.json](../.devcoveer/requirements.json). ПМИ не ослабляет их.
- Семантическое чтение, выделение историй, идентичности и оценку свидетельств выполняет вызывающая модель через MCP. Бэкенд хранит, проверяет права/ссылки/версии, индексирует и обеспечивает идемпотентность; совпадение цитаты не доказывает историческую истинность.
- История представляет эпизод/утверждения со своими свидетельствами, не механическую копию одного чанка. Чанки заменяемы. RKB places могут быть без координат; это не физические POI Street Story. Одноимённость не разрешает автоматическое слияние.
- До запуска записать run ID, UTC, точные deployed SHA MCP/indexer/BGE controller, MCP profile/tools schema, конфигурацию моделей/векторных пространств/индекса, actor scope, IDs и active revisions источников, private fixture version/hash и ограничения запуска. Main SHA не подтверждает deployed SHA; несовпадающие runtime SHA блокируют приёмку развёртывания.
- Подготовка документов не разрешает новый импорт, reprocess/rechunk, нагрузку или вызовы модельного провайдера. Для будущего прогона заранее определить разрешённый тестовый источник/стенд, объём, бюджет и rollback. Не изменять принятые книги ради подготовки ПМИ. Source proof для сканов может вызвать отдельного провайдера: такой тест запускать только в явно разрешённом режиме; иначе BLOCKED/NOT RUN, а не PASS.
- Исходники, страницы, цитаты, private IDs, raw traces и тестовые вопросы хранить в owner-restricted хранилище, **не в GitHub**. Публичный журнал содержит агрегаты и обезличенные ссылки на код/отчёты; закрытые артефакты обозначать непрозрачным ID без bearer/signed URLs.

Для первого ограниченного теста одной книги выбираются только относящиеся к нему случаи. Полный holdout, проверки чужих principals и масштабный CAP-01 не являются предварительным условием самого bounded-теста; они нужны для соответствующих заявлений о качестве, безопасности и массовой готовности. Не строить новый harness/реестр: использовать существующие MCP и runners, а этот журнал — для связи наблюдений с исправлениями.

## Проверка смыслового качества и решение

До запуска заморозить gold evidence, family split и ожидаемые оценки extraction. Перефразы одного факта и языковые варианты остаются в одной family: их нельзя раскидывать между tuning и holdout. Исторические 16 held-out families из отчёта 08.10 не удовлетворяют новому полному минимуму ≥30 held-out families, даже при 32 вопросах.

Для каждого extraction candidate независимый от генерации просмотр оригинала проверяет: точность цитаты/locators, соответствие proposition своей цитате, атрибуцию, отсутствие чужих свидетельств и дублей. Записывать число проверенных/поддержанных/неподдержанных/пропущенных эпизодов и дефекты; не называть structural `story_validate` проверкой исторической истины. Полноту оценивать только относительно заранее размеченной выборки, не всего непросмотренного корпуса.

Статусы: PASS — критерий выполнен с артефактом; FAIL — измеренное нарушение; BLOCKED — нет обязательной зависимости/разрешения; NOT RUN — не выполнялось; INCONCLUSIVE — запуск/выборка не дают заключения. Отрицательный кейс PASS означает корректный отказ, а не успешную мутацию. Общая приёмка не получается усреднением: незакрытый критический FAIL/BLOCKED/NOT RUN запрещает объявлять mass-ingestion-ready.

После исправления связать defect → PR/commit → новые run/case IDs; старые результаты не переписывать. Перед rollout изменений chunking/model/index/fusion/lexical/scope/storage повторить применимые quality/capacity/latency gates. Сначала разрешённый bounded import, затем per-book retrieval/extraction acceptance, затем отдельная масштабная приёмка; готовность документации не равна готовности массового заполнения.
