# RKB — режимы ответов на вопросы (продуктовое решение)

**24.10.2026 · исследование, docs-only; не утверждение о внедрении.** Владелец: «Мы не цитатник строим, а систему». Цель: человек задаёт обычный вопрос и получает **один проверяемый ответ**, а не ранжированный список текстов. Страницы, цитаты и служебные ID доступны по просьбе, но не подменяют ответ.

## 1. Что уже существует и чего нет

В E2E Slack Kaliningrad Base [№1–3](https://mira-projects.slack.com/archives/C0C8RT9JB2P/p1792794564600049) доставка 3/3 работает, но [PR383](https://github.com/onedayonemasterpiece/regional-knowledge-base/pull/383)/[PR387](https://github.com/onedayonemasterpiece/regional-knowledge-base/pull/387) ведут `mention → ACL → search_adapter(limit=3) → answer_from_evidence → chat.postMessage`. `answer_from_evidence()` в `expert_slack_search_reply.py` печатает до трёх цитат. Синтеза и проверки достаточности свидетельства **нет**. На вопрос о температуре у восточных ворот замка 17.02.1256 в 14:23 выданы три нерелевантных места Гаузе (`pages 38/5/94`); на русский вопрос по Вихерту — немецкие фрагменты, но нет русского ответа. `urn:rkb:passage:…` в `kaggle_public_backend.py` — внутренний локатор, **не публичный HTTPS deep link**. Пять заведомо внебазовых запросов в замере 24.10 также вернули по три кандидата каждый: ненулевой top-K не означает релевантность.

Целевые [collaboration §2](../design/rkb-kaliningrad-base-collaboration-20261018.md) и [handoff §§2, 4](../prompts/rkb-scalable-kaggle-implementation-20261019.md) уже предусматривают **dot как сменяемую вызывающую модель**, самостоятельные MCP-маршруты Dot/Mira и отсутствие скрытой LLM внутри RKB backend. Но `expert_executor_*` — защищённый приём/доставка результатов внешнего исполнителя, **не вызов dot**. Текущий Slack short-path этот контур минует; не заявлять, что dot уже «под капотом».

## 2. Контракт ответа для пользователя

| Естественный запрос | Один результат; источники всегда в конце |
|---|---|
| По умолчанию: «Когда основали Кёнигсберг?» | **Короткий:** 1–4 содержательных предложения по-русски, с указанием границ знания; затем «Источники: 1. Автор. Название. Год [ISBN, если подтверждён]». Объединить согласующиеся документы; не повторять общие цитаты и UUID. |
| «Подробно», «покажи страницы», «дословно», «дай первоисточник», «почему?» | **Развёрнутый** ответ к тому же вопросу/треду: привязка каждого проверяемого утверждения к документу и его ревизии, **печатная страница или номер скана** (различать), короткая точная цитата с языком оригинала, разрешённая ссылка на конкретный фрагмент; если HTTPS-viewer ещё нет — честный текстовый локатор, не псевдоссылка. |
| «Какая была температура… 17.02.1256 в 14:23?» | **Отрицательный:** «В доступной региональной базе подтверждений точной температуры для этого места и момента не найдено. Назвать значение и страницу источника нельзя». Никаких соседних тематических цитат, UUID или фиктивной библиографии. Это *ограничение базы*, не утверждение, что измерения в принципе не существовало. |
| «Источники расходятся?», «Что пишут разные авторы?», «Сравни версии» | **Расхождение:** сначала суть несогласия, затем по каждой позиции кто, что и на каком конкретном основании утверждает; различить факт, оценку, перевод, эпоху и чужую атрибуцию; указать, есть ли вывод и что осталось непроверенным. Не создавать искусственный консенсус. |

Пользователь **ничего не переключает в настройках**: обычная речь выбирает детализацию; «кратко» возвращает короткий формат. Продолжение в Slack — текущий тред и исходный request ID; в ChatGPT — контекст диалога. Отдельная кнопка или команда необязательна. Для текста по-немецки синтез **на языке вопроса**; немецкая цитата появляется только в раскрытом доказательстве. Для «расскажи историю» отдавать сохранённый `Variant.body`, а не генерировать несуществующий рассказ из сниппетов.

**Библиография:** читать текущие `title/authors/publication_year` + `CatalogMetadata.identifiers`/edition/kind/parent из [каталога PR378](https://github.com/onedayonemasterpiece/regional-knowledge-base/pull/378); ISBN только если тип и значение действительно установлены. Дедуплицировать одно издание, не считать его чанки независимыми источниками. При неизвестном годе/ISBN пропускать поле, не договаривать по OCR титульного листа. Страницы и подтверждения — по активной ревизии/конкретному пассажу; private/proof материалы только по соответствующим grants, а в общем Slack-треде — только общедоступная проекция.

## 3. Когда отвечать, а когда воздержаться

Слой **answerability / evidence sufficiency** нужен *после* поиска и *до* формулировки. `status=ok`, три результата, RRF-ранг и близость embedding **не являются доказательством**; текущий `EvidenceSearchOutput` вообще не отдаёт калиброванной вероятности истинности. Нельзя задавать произвольный абсолютный порог cosine/RRF и называть его гарантией. Предлагаемая семантика:

1. **Доступность:** `hybrid`, актуальные source/ACL/revision, `context_gap=false`, достаточный `observed_projection_seq`, без `prior_write_pending`. При `pending/unavailable/timeout/revoked` говорить **«Не удалось проверить базу сейчас»**, а не «не найдено».
2. **Полнота попадания:** из 3–5 кандидатов в допустимом времени проверить совпадение *сущности, требуемого свойства, места, временного интервала, единиц и атрибуции*. Для точного показания температуры доказательство должно содержать само измерение, а не просто слова «замок», «градусы» или чужую дату. Семантический перефраз допустим; ответ не опирается на заполнение моделью пробелов из общей памяти.
3. **Вердикт:** `supported` — все ключевые утверждения следуют из одного или нескольких доступных оригиналов; `partial` — явно сказать, какую часть установить удалось; `conflicting` — показать несовместимые версии; `no_support` — «в доступных источниках подтверждений не найдено»; `unavailable` — технический отказ. Модель обязана указывать точные source/passage refs для каждого утверждения, а сервер перед выдачей повторно проверяет current scope. Не доказано ≠ доказано неверным.
4. **Дела:** если есть тематическое `disagreement_*`, использовать его `positions/evidence/current_conclusion`, версию и `based_on_seq` как *контекст*, не как машинный арбитраж. Отделять модельный вывод, экспертно поддержанную версию и личное мнение по [журналу расхождений](../design/rkb-disagreement-journal-design-20261018.md). Если доказательства в деле устарели/недоступны — не приписывать делу окончательную истину.

**Критерий приёмки (предложение, не достигнутый KPI):** отдельные positive/negative/partial/conflict/RU→DE/rights/time-location наборы ≥30 разных случаев; для критических negative (включая E2E №3 и фантастические запросы) **0 ложных фактических ответов и 0 нерелевантных ссылок**; для positive — каждый существенный тезис связан с поддерживающим активным пассажем. Измерять отдельно coverage, ложные отказы и фактическую точность, не подменяя их Hit@K. Не ослаблять [§14.1 retrieval gates](../testing/rkb-scalable-kaggle-acceptance-20261019.md).

## 4. Кто формулирует ответ

**Рекомендация — модель на стороне вызывающего клиента, RKB — trusted evidence.** В ChatGPT-коннекторе **сама ChatGPT-модель** формирует ответ из результатов обычных `search/fetch`; это уже соответствует архитектуре Dot/Mira без нового процесса или скрытого LLM-вызова внутри Kaggle. Сервер должен отдавать ей не только ранжированные `text/title`, но проверяемую проекцию: статус/причину и freshness, актуальные source ID/revision/ACL, текст и язык, `kind`, однозначные author/title/year/ISBN, `printed_page_number` vs physical index, `passage_id`/URL с возможностью повторного fetch, `source_continuation`, а для дела — атрибуции/ревизию позиции/заключения. Эти поля не заменяют проверку моделью; `metadata.citation` и `urn:` без public resolver недостаточны для кликабельной страницы. **Одни и те же правила ответа** задаются вызывающей модели и Slack-исполнителю; не делать два конкурирующих алгоритма истины.

**Slack:** подключать **существующий** ограниченный expert request → claim/result/delivery маршрут к уполномоченному dot/другому MCP-клиенту, когда есть *реально установленный исполнитель*, с сохранением actor/source gate/destination/correlation/UNKNOWN-no-resend. Dot должен получать **только полномочия проверенного Slack-пользователя и аудитории**, не собственные owner-права. **Сегодня нет доказанного автоматического вызова dot** из `ExpertSlackSearchReply`; одной привязки сокета недостаточно. Добавить «LLM внутри бота» означало бы новую модельную зависимость, расходящуюся с базовым handoff; не рекомендовано. Если исполнитель пока не подключён, нельзя объявлять Slack полноценной системой ответов: допустим временный строго подтверждённый extractive ответ/честное воздержание, но **не сырой top-3**.

**Латентность — предлагаемый отдельный UX-SLO, ещё не измеренный:** существующий поиск public MCP p95 ≤1,5 с / hard ≤2 с; синтез p95 ≤4 с; проверка и Slack-доставка p95 ≤1 с; ориентир **весь short answer p95 ≤7 с**, без уверенного обещания до E2E с dot. Для глубокого исследования: быстрый транспортный ACK, затем асинхронный результат в том же треде с существующей durable pending/notice-механикой при >10 с; не выдавать ACK за ответ. Показывать p50/p95 и timeout/error denominator по search/synthesis/send; не усреднять только успешные запросы.

## 5. Практики и минимальный первый срез

- [Perplexity](https://www.perplexity.ai/help-center/en/articles/10352903-what-is-pro-search): синтез многих источников с возможностью открыть первоисточник и продолжить вопрос. **Берём:** answer-first + проверяемые sources; **не берём:** многопоисковый веб-каскад и длинный процесс по умолчанию.
- [Consensus](https://help.consensus.app/en/articles/9922673-how-consensus-works) / [Elicit](https://support.elicit.com/en/articles/14757979-elicit-s-reliability-does-elicit-run-the-same-risk-of-hallucination-as-other-ai-tools): сначала релевантный корпус, потом синтез, прослеживаемые выдержки и явные разногласия. **Не берём** Consensus Meter/проценты согласия для единичных исторических книг: число чанков и вторичных пересказов не равно независимым свидетельствам.
- [Google AI Overviews](https://developers.google.com/search/docs/appearance/ai-features) и [разбор ошибок](https://blog.google/products-and-platforms/products/search/ai-overviews-update-may-2024/): краткий вывод с углублением в ссылки, но опасность «пустоты данных» и неправильно понятой сатиры. **Берём:** явное воздержание, а не правдоподобный ответ на нерелевантный результат.
- [RUSA, справочная служба](https://www.ala.org/rusa/clone-guidelines-behavioral-performance-reference-and-information-service-providers): установить действительный вопрос, выбирать уместные источники, проверить и при необходимости уточнить; **не берём** требование обучать каждого пользователя поиску или заставлять самостоятельно читать всё найденное.

**Минимальный вариант (без новых сервисов, предложение Product/Opus):** (а) прекратить выдавать три сырых совпадения как ответ; ввести проверку достаточности и раздельные `no_support/unavailable`; (б) для ChatGPT-клиента немедленно описать answer-first контракт над текущим guarded MCP evidence, каталог/точные страницы/links добавить в существующую выдачу по мере готовности; (в) для Slack использовать тот же формат только через реально подключённый **существующий** expert executor с dot и измеренным E2E; пока его нет — явный ограниченный режим, а не фиктивный синтез; (г) принять 3 E2E (Гаузе, RU→DE Вихерт, отрицательный) и новые holdout с проверкой ссылок, ревизий, прав, ошибок и латентности. **Этот документ ничего не внедряет и не меняет действующие protected gates.**
