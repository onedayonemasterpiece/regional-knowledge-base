## 1. Цель и предмет

Доказать **продуктовый цикл**, а не только работающий процесс:
- владелец fresh-imports документ через MCP; один research workflow сохраняет факты, атрибуцию, даты/measurements, cases и actual basic narratives достаточных эпизодов, без второго полного чтения;
- владелец как испытатель через **того же Kaliningrad Base** ищет материалы и работает с делами от собственного подтверждённого actor, без обхода ограничений expert route;
- эксперт, не знающий о dot, **через отдельного Slack-бота Kaliningrad Base** находит вопрос, получает разрешённый ответ и proof, сохраняет личный аргумент и продолжает после потери чата;
- два независимых специалиста могут разойтись во мнениях и вернуться к делу; ни один вклад не пропадает и вывод не получает чужого подтверждения;
- нужное дело попадает в ограниченную обычную очередь VK, либо получает отдельно подтверждённый срочный слот; бот возвращает реальную VK-ссылку после публикации, а комментарии возвращаются в то же дело;
- разрешённые адресаты получают осмысленный briefing без раскрытия чужих материалов;
- PH/Mira использует expanded typed v2 adapter: ephemeral read со status/freshness и отдельно durable question/effect с request/result/native ACK; Story/case/proof права общие, get/search/read-export/voice читают saved body, не summary.

Тесты должны отдельно доказывать: **доставлено Slack → принято РКБ → обработано dot → записано в дело → возвращено Kaliningrad Base → прочитано из Slack**, а не делать вывод о продукте по одному успешному HTTP 200/файлу/поставленной в очередь задаче.

## 3. Среда, допуски и контрольный материал

**Стенд:** точный source commit/installed SHA и health РКБ, работоспособный service-only expert route, отдельно заведённый и разрешённый Slack app (предпочтительно Socket Mode), тестовый разрешённый DM и закрытый канал, при необходимости один публичный канал. Тестовое VK-сообщество/пост с разрешением владельца; VibePublish с реально настроенными в тесте правами. Не выполнять destructive VK-модерацию или массовые публикации в производственном сообществе. Состояние native scheduled VK читать отдельно от внутренней очереди.

**Роли/аккаунты:** O — реальный владелец; V — только текстовый читатель; E1 и E2 — два разных реальных эксперта; H — expert/local_historian с действующим existing scan_proof_read и отдельным правом ведущего/редактора; D — demo с тем же proof grant и expiry; X — чужой пользователь либо иной team/workspace. Предусмотреть claimed/owner_attested/independently_verified категории, category-policy grant с audit/source revision, отдельный explicit grant, demo expiry и независимый revoke в ходе операции. Не считать тестом авторства два сообщения владельца через разные каналы.

**Owner Slack fixture (дополнение 19.10.2026):** O — подтверждённый по исходному поручению `provider=slack, team_id=T0C82495TK5, user_id=U0C8C1QKWAG`. `U0C8A9GM76D` — упоминание dot, не инициатор. До живого теста требуется verified mapping на **существующий** canonical owner `rkb_users.id`, подтверждённый readback; значение UUID получают из доверенной RKB identity, не из текста запроса. Подготовить контролируемые отрицательные fixtures: другой user в этом team, тот же user ID в другом team, поддельный actor/owner payload, pending и revoked mapping. Чужой действительный участник сохраняет только свои права, а не становится O. Сама ПМИ не создаёт этот mapping, grants, Slack app или реальные тестовые сообщения.

**Автоматизированный owner harness:** E2E-8 и связанные KB-41…45 проектируются как автопроверки. Положительный путь отправляет реальное сообщение через поддерживаемый connector/transport, аутентифицированный как O; зафиксировать способ доказательства фактического user-sender. Не подставлять owner user ID в payload и не отправлять техническое bot-сообщение вместо человеческого инициатора. Нужны реальный event → Kaliningrad Base → внутренний исполнитель → RKB → ответ бота и независимый Slack/RKB readback. Отсутствие подтверждённого user-sender transport — implementation gap и BLOCKED только реального Slack E2E, не разрешение заменить её ручным smoke или выдумать работающий коннектор. Отрицательные spoof-события допускаются только как контролируемые fixtures в изолированном тестовом контуре, не как способ инициировать положительный owner-запрос. Протокол хранит run ID, namespace тестовых case/operation IDs, точные ревизии, reused idempotency keys при rerun и cleanup только явно разрешённых тестовых сущностей; реальные дела и ACL не менять ради прогона.

**Обратимые component/integration автотесты дел:** независимо от Slack-транспорта harness вызывает те же авторизованные domain operations на разрешённом стенде. Один test_run_id в существующих jobs/events/contributions связывает baseline, case/revision, operation keys, эффекты и receipts. По умолчанию тестовый case/копия с ссылками на неизменные реальные source revisions; test-only вклады/веса/поддержки/заключения изолированы от live проекций, уведомлений и VK. Если нужен canonical-case тест, допускается лишь заранее ограниченная CAS-компенсация своих изменений, сохраняющая реальные поздние вклады; не общий DELETE/whole-DB restore. Подробный контракт: [Kaliningrad Base §4.1](../design/rkb-kaliningrad-base-collaboration-20261018.md#41-безопасный-откат-автоматизированных-проверок). Независимые проверки KB-46…48 можно выполнить без user-sender Slack; если нет самих test-scope/rollback операций, они BLOCKED по этой конкретной причине, не по транспорту.

**Источники и фикстуры:** A — PDF/DjVu с заранее известным фактическим или интерпретационным расхождением и исходным сканом, B — действительный альтернативный источник/рецензия, C — похожий по словам, но непротиворечивый материал, P — частный full original/page-proof при публичном active accepted text; W — отозванный/непринятый источник; L — private author draft с синтетическим проверочным маркером; Q — ещё не импортированная статья, запрошенная в деле. Не использовать «книгу другого владельца» как отрицательный text-search fixture. Желательно использовать разрешённые специально созданные тестовые материалы; accepted text/bibliography и illustrations публичны; page/stripe proof требует scan_proof_read owner/demo/expert/local_historian, full PDF остаётся private. Отзыв W и private L проверяются отдельно. Для каждого известны document_id, active source_revision, page/region locator, expected cases/gaps и видимость.

**Перед тестом:** зафиксировать входную ревизию, часы Europe/Kaliningrad, роли, Slack install/scopes, профиль ограниченного dot, native VK capabilities, состояние outbox/публикаций и способ восстановления. Не переносить PH owner_actor_id в expert route. Не запускать тест на реальных приватных книгах, если тестовый канал/адресат не имеет соответствующих прав.

## 4. Как выполняется каждый тест

1. Оператор фиксирует ID проверки, actor/role, preconditions, точный SHA и среду; сбрасывает **только тестовые** данные/сообщения, не очищая реальные чужие задачи.
2. Прогоняет конкретные действия с реальным Slack UI/событием, а не только вызывает backend напрямую; для негативного и аварийного случая использует контролируемую имитацию сбоя или разрешённый тестовый рестарт.
3. Собирает **независимые доказательства**: Slack event и ответ от Kaliningrad Base в том же DM/thread; RKB request ID, actor/ACL decision и result revision; вызовы MCP и operation receipt; source proof locator/render; VibePublish/provider ID/план/внешний URL и комментарий; delivery receipt. В логах только ID, статусы, время, проверенная версия и причина отказа, без токенов, содержимого приватных цитат и полных личных данных.
4. Сверяет, что один запрос не записан дважды, а отказ прав не содержит скрытых названий, счётчиков, изображений или производных пересказов. Для asynchronous разнести accepted, processing, result_saved, delivery_confirmed.
5. Ставит PASS / FAIL / BLOCKED / NOT_RUN. Любой FAIL требует повторного теста **на новой проверяемой ревизии** после исправления; прежний receipt не переписывать. Сбой внешнего провайдера — BLOCKED при подтверждённой инфраструктурной причине, но не PASS. Не повторять бездумно запрос с неизвестным результатом.

| KB-71 / P0 A/B | O подтверждает demo/expert/local_historian как owner_attested/independently_verified; сравнить claimed. Повторить event, истечь demo, независимо revoke grant, открыть proof, удалить category при наличии отдельного explicit grant | Verified category атомарно создаёт existing scan_proof_read с audit/source category revision и demo expiry; claimed не grant. Render проверяет current capability/scope. Retry/read не восстанавливает revoked grant. Category removal отзывает только policy-derived basis; independent explicit grant не подделан/не стёрт, per-image approval и новый IAM отсутствуют |
| KB-72 / P0 G | Слепой пилот 15–20 одинаковых fresh originals: pinned retired baseline prompt/contract и новый, actual saved body либо честное «body отсутствует» | Владелец/назначенный human оценивает связность, точность, атрибуцию, title и пригодность к рассказу без знания реализации. Self-model praise не PASS. До человеческого ответа human pilot NOT_RUN; результат отдельно от persistence tests, не per-book approval gate |

## 6. Десять обязательных сквозных маршрутов

### E2E-1: эксперт, публичный текст и ограниченный proof, bot→dot без владельца (этап A, P0)

**Действия:** E1 в разрешённом DM задаёт вопрос об A; фиксируем Slack event_id. После durable-ack с task ID владелец не вмешивается. MCP-событие пробуждает dot; dot читает сохранённый запрос и обращается к ограниченному профилю РКБ. Bot возвращает ответ в исходный DM. Далее V просит proof P и получает безопасный отказ, H получает оригинал по correct revision и region. H также спрашивает в private channel, где присутствует V, и получает только безопасную общую проекцию, закрытое предлагается в DM. Затем H и V **одновременно** делают запрос разрешённого proof/private draft и публичного текста на одном исполнителе; проверяется отсутствие пересечения результатов. E1 запрашивает импорт — отказ.

**PASS:** разные actor/worker/service principal, нет owner's authorisation, RKB receipts связаны с единственным Slack event, ответ пришёл от Kaliningrad Base, нет private leakage и импортных side effects. Предыдущая приёмка PH не заменяет этот тест.

### E2E-2: два независимых исследователя и потеря ответа (этап B, P0)

**Действия:** E1 выбирает C1 из смысловой выдачи; вносит аргумент с цитатой и теряет транспортный ответ. E2 параллельно добавляет иное объяснение. E1 читает operation_status и восстанавливает ход; H синтезирует по срезу, во время работы E2 добавляет позднее возражение. После обновления OCR документа запрашиваем обычный поиск.

**PASS:** вклад E1 в единственном экземпляре, E2 не перезаписан, поддержка относится к точной версии, поздний аргумент виден как нерассмотренный, прежняя оговорка в новом поиске не исчезла. Сканы/источники имеют locator и уровень проверки.

### E2E-3: VK очередь, завтра и срочно, без двойных публикаций (этап C, P0)

**Действия:** на тестовом сообществе две независимые regular-заявки конкурируют за следующий день; редактор приоритизирует одну. В VibePublish получаем provider_scheduled receipt, бот в Slack показывает статус **без фиктивного URL**. Затем проверяем actual published ID/URL и одно обсуждение case. Два urgent запроса одобрены; третий и запрос без роли отклонены. Имитируем lost send response, сверяем provider state. Отдельно отменяем/переносим уже scheduled A, **теряем подтверждение отмены**, пока B претендует на день A: слот должен оставаться занятым до проверенного provider receipt. Проверяем смену ACL до запланированной отправки.

**PASS:** regular ≤1/календарный день/серию и urgent ≤2 доп. по выбранной политике; ни второго поста при повторе, ни ссылки до publish, ни скрытого материала. Если native scheduling или удаление недоступно текущему токену — BLOCKED, а не обещание готовности.

### E2E-4: комментарии VK, мнение специалиста, брифинг (этап C, P0/P1)

**Действия:** два проверенных VK участника пишут и отвечают, один редактирует. Посторонний пишет в ветку, пока whitelist доступен, и повторяет во время простоя. После restart синхронизация фиксирует доступное. H через Slack открывает дело и добавляет новый аргумент; bot подтверждает contribution ID. Затем новый итог импорта A создаёт briefing для O и доступный digest E1; V не имеет scan_proof_read для P и не читает private draft L; accepted text P остаётся публичным.

**PASS:** авторство и ревизии VK не подменены; модерация не трогает чужие посты, не удаляет неизвестные ветви при ошибке whitelist; пользователь может вернуться к делу из VK-ссылки. Уведомления не выдают withdrawn W/private L/proof bytes или private participant данные; accepted text/bibliography и illustrations P не скрываются по uploader. Неутверждённая историческая оценка не называется общим консенсусом.

### E2E-5: PH/Mira через existing adapter (этап D)

**Действия:** PH/Mira v2 adapter с verified platform→RKB actor выполняет ephemeral read C1/Story body и получает explicit status/freshness/body ref. Проверить deadline/barge-in/reconnect без durable RESUME, late-generation drop и отсутствие per-read fsync/seal/ACK. Отдельно принять durable research/contribution и resumable proof, проверить exact pending/result/native hash ACK после reconnect; чужой route/hash не завершает request. Same-host route использует machine identity+verified actor через existing Dev auth/admission/outbound notebook WSS; external client — действительный resource grant. Выполняем те же разрешённые read/proof/contribute операции, что доступны E1 через Slack; меняем actor на V и отзываем grant. Read вслед за UNKNOWN записью того же dialog возвращает prior_write_pending с known freshness, не latest/not-found.

**PASS:** одинаковые ID и версии, единый RKB policy decision и запрет приватного; после отзыва grant доступ не сохраняется, включая cache/late output. V1 выдаёт success только для полностью представимого ответа, иначе existing unavailable/error, не empty hybrid. PH utterance checkpoints и durable effect order сохраняются; cancel read не отменяет effect. Этот backend/adapter сценарий не требует нового мобильного интерфейса и не заменяет отдельную настоящую phone/voice приёмку канала.

**Сравнение Mira/Dot — [handoff §14.4](../prompts/rkb-scalable-kaggle-implementation-20261019.md).** Оба smart routes сохраняются независимо. После actual PH provider сначала дать одинаковые текстовые queries, corpus/revisions, права и сопоставимый common tool profile/budget, оценить качество/полноту/source grounding без приписывания преимуществ профиля или cache модели. Отдельно измерить реальные пользовательские пути, включая ASR/voice/Slack, tool_lock_wait, конец высказывания→первый полезный слышимый ответ и полный ответ; ошибки ASR и barge-in не смешивают generations. Эти результаты не подменяют друг друга. До actual wiring/pilot — NOT RUN. «Мира, хорошо подумай»/делегирование Dot не реализуется в base: future option допустима лишь после показанной пользы.

### E2E-6: один человек через несколько подтверждённых каналов (этапы A/D, P0)

**Действия:** владелец через собственный MCP заводит RKB person UUID с категориями «краевед» и «научный сотрудник», добавляет непроверенное научное звание, отдельно назначает вес по региону и ограниченный grant. Привязывает подтверждённый Slack user, затем по независимому proof — VK и PH actor. Выполняем read/contribute из каждого доступного канала, затем проверяем попытку другого человека с таким же именем воспользоваться привязкой, чужую подпись и отзыв одной связи.

**PASS:** одна карточка и один персональный вес, но разные provider identifiers и route grants; одинаковое имя не объединяет людей; неподтверждённая регалия не становится verified; публикация/импорт не разрешены из признака «научный сотрудник». Отозванный Slack или VK link блокирует новое действие, сохраняя исторический вклад. PH без verified mapping/delegation и нужного grant честно возвращает blocked/denied; same-host service не подставляет owner, внешний клиент имеет resource grant.

### E2E-7: импорт книги → сохранённый POI-факт → новый источник (этап E, P0)

**Действия:** владелец принимает книгу A с известным фактом об уже существующем физическом POI и точной оригинальной страницей. Модель явно выбирает POI, записывает атомарный факт и source evidence; RKB подтверждает outbox. При авторизованной доставке Street Story принимает его как кандидат, выдаёт native claim/evidence receipt. Проверяем сохранённый book/article author и source revision, открыть выделение на оригинале. Повторяем outbox event. Затем из Street Story ищем по poi_id в RKB вторую книгу B и добавляем подтверждающее/противоположное evidence; проверяем, что не создан новый POI. Меняем OCR ревизию и отзываем один источник через withdrawal, отдельно проверяя отзыв proof grant.

**PASS:** раздельные наблюдаемые состояния source accepted, outbox pending/delivered, owner POI identity linked, claim candidate/reviewed; из POI видны читаемые книга/автор/страница и проверяемая цитата. Повтор не удваивает claim/evidence, неразрешённый alias не становится verified POI, противоречие не исчезает от численного score, прежняя редакция не продолжает считаться действительным public proof, но независимое evidence сохраняется. При отключённом Street Story — pending/retry, не фиктивная успешная доставка.

### E2E-8: автоматизированный owner Slack research route (этапы A/B, P0/P1)

**Предусловие:** verified binding точного Slack-ключа O к существующему RKB owner UUID по [§3.4 участников](../design/rkb-participants-poi-fact-bridge-20261018.md#34-владелец-как-испытатель-slack-маршрута-19102026), настроенный Kaliningrad Base, подтверждённый поддерживаемый owner-authored connector/transport и разрешённые тестовые материалы/case IDs. Это будущая автоматизированная приёмка, не утверждение, что привязка или transport уже существуют. Если реальная автоматическая отправка от O недоступна, зафиксировать BLOCKED и конкретный implementation gap; ручной прогон отдельно, без зачёта этого E2E.

**Действия harness:** через аутентифицированный owner-sender connector отправляет от O реальный запрос Kaliningrad Base, находит источник A и тестовое дело C1, открывает текущую карточку/changes_since и разрешённый proof. Сохраняет личный анализ, явно вносит один аргумент, поддерживает указанную версию и подписывается. После потери ответа продолжает через case/operation ID, проверяет сохранённый результат. В группе с V просит ограниченный proof P, затем получает допустимый proof в личном DM. Проверяет запрет импорта через бота (KB-02), отрицательные identity fixtures KB-43 и отзыв тестового mapping/grant в незавершённом запросе (KB-44). Повторяет run с теми же test-scoped operation keys, независимо читает эффекты/точные ревизии в RKB и ответы в Slack, проверяет locator/ACL и доступный proof. Изменения прав для отрицательного прогона допустимы только на разрешённом тестовом стенде, не в production. В конце выполняет scoped rollback данного test_run_id по KB-46…48 и отдельно читает дело, search/projections и outbox; исходные книги не меняются, тестовые оценки не остаются вместо рассмотрения реальными экспертами.

**PASS:** автоматизированный запрос от подтверждённого O проходит реальный Slack event → bot → внутренний dot → RKB → bot reply/readback; подтверждены реальные Slack event/request/operation/delivery receipts, неизменный canonical owner actor и отдельные service/executor. Нет нового owner, ручного проксирования через личные полномочия dot, лишних grants, дублирующих вкладов и приватной утечки; импорт через expert route denied. Scoped rollback подтверждён readback, реальные вклады сохранены и старые callbacks не восстанавливают эффекты. Поддельный event/actor, сообщение service-бота вместо O, backend-only вызов или ручной smoke не дают PASS именно Slack E2E; domain/integration результаты KB-46…48 учитываются отдельно. Owner-сценарий **не заменяет E2E-1 и минимум одного реального не-owner**; успешная проверка O не означает готовую многопользовательскую авторизацию.

### E2E-9: публичная страница дела на Astro без авторизации (этап F, P0)

**Действия:** в разрешённом тестовом деле создать две версии с источниками и материалами профессионального сообщества; часть данных пометить как не предназначенную для публикации. РКБ формирует публичный экспорт. Existing events-bot-new/site SSG build получает один versioned RKB export bundle и публикует HTML по стабильному slug. Через независимый браузер с пустым профилем открыть страницу на desktop/mobile и без JavaScript, проверить автора, обложки, аргументы и provisional conclusion; получить URL через MCP только после HTTP readback published URL с exact revision marker. Добавить общественный аргумент, обновить страницу по той же ссылке, смоделировать неудачную сборку и снятие контента с публикации.

**PASS:** контент совпадает с разрешённой ревизией и ничего закрытого нет ни в HTML, ни в статических assets/meta; чтение без входа и без JS, адаптивный макет не скрывает аргументы и книги; ссылки и статус соответствуют фактической публикации; URL не меняется, ошибка обновления сохраняет разрешённый last-good; withdrawal запрещает его сохранение и требует safe replacement/removal с HTTP readback published URL/revision marker/assets; отсутствие purge API не доказывает purge, старая фактическая выдача оставляет revocation BLOCKED; stale build не откатывает текущую версию. Наличие случайного slug не считается правовой/технической защитой просмотра.

### E2E-10: fresh import → настоящий сохранённый рассказ (этап G, P0)

**Действия:** выбрать разрешённые контрольные фрагменты: достаточный связный эпизод/практику, sparse facts и конкурирующие версии. Через MCP принять источник в новом corpus, пройти тот же research workflow для facts/cases/POI/dates и compose. Потерять ответ после сохранения basic Variant, продолжить в новом чате по operation/checkpoint. Прочитать default get, search excerpt+ref, reader export и Mira/voice; перезапустить reader. Отдельно проверить private draft, редакторскую правку, отсутствие publish_ready и source withdrawal.

**PASS:** sufficient episode имеет readable saved Variant.body, exact default ref и readback hash; реальные текст и provenance совпадают во всех чтениях, summary/rating/bibliography не подставлены. Sparse facts сохранены без fake Story/body, dates/people/roles/measurements/cases не потеряны. Нет выдуманных причин/героя/финала, «как» в title отвечает body либо retitle. Basic shared draft читается в Story scope, private draft не promoted, публикация требует отдельного approval. Retry/restart не создаёт новые варианты, CAS защищает ручную редакцию, withdrawal блокирует current/cache/late delivery. Проверка не требует постоянного judge или второго полного чтения книги. Разовый слепой human pilot KB-72 на 15–20 примерах оценивается отдельно; без ответа владельца/назначенного человека он NOT_RUN, а не PASS по оценке модели.

## 7. Условия приёмки / no-go

**Scope всего проекта не сокращается этапами.** Core cutover не является PASS новых Mira, VK и Astro. Для каждого обязательного feature gate нужен собственный реальный adapter/provider/site E2E и readback; выключенный feature flag, временная отсрочка или PASS ядра оставляют этот gate NOT_RUN/BLOCKED, а общий проект незавершённым.

- **Этап A:** все KB-01…08, KB-07A, KB-41 и KB-43…45 P0 должны быть PASS на **минимум двух реальных участниках с разными правами** (из них как минимум один не owner) и установленном Kaliningrad Base; KB-08 выполняется также в private channel/group DM смешанного состава. Нельзя заменить их unit mock или вручную отправленным dot сообщением.
- **Этап B:** P0 KB-10…13, KB-15, KB-27, KB-46…48 и функциональные KB-09/14/42; E2E-8 подтверждает автоматизированный owner research route вместе с этапом A, не подменяя проверки экспертов; открытый pilot только после проверки знаний и цитат по основному §14 РКБ. Пропуски известных противоречий измерены, необоснованные «0» не выдаются за полноту.
- **Этап C:** до реальной VK-публикации все относящиеся P0 KB-16…20, KB-19A и 22, 24 — PASS **на разрешённом сообществе** с provider receipts. Регулярные и срочные бюджет/approve должны быть enforced сервером, не инструкцией модели. Результаты нативной отмены, токена и веток VK нельзя предполагать по прошлым публикациям.
- **Этап D:** KB-26/30 и KB-67…68 PASS на отдельном клиенте/отозванном grant. Это не условие выпуска Slack-варианта. Текущий owner-only PH invite не считается multi-user связью.
- **Этап E:** KB-34…KB-40 с учётом P0/P1 и E2E-7; перед заявлением «POI обогащён» требуется реальный native Street Story claim/evidence receipt и resolver для выделенного оригинала. Отключение fact-intake из-за инфраструктуры → BLOCKED, а не PASS. Этап E обязателен перед объявлением полного межпродуктового накопления фактов, но не препятствует отдельному MVP экспертного Slack-поиска.
- **Этап F — публичная демонстрационная страница:** KB-49…53 (P0), KB-54…55 (P1) и E2E-9. Отдельная HTML-страница разрешённого дела реально прочитана на kenigevents.ru в десктопном/мобильном браузере без входа; MCP подтверждает фактический published URL; статический экспорт не включает частные материалы. Это не условие готовности исторического поискового ядра, но обязательно перед объявлением публичных страниц работающим продуктом.
- **Этап G:** KB-56…66, KB-69 и E2E-10 PASS до объявления настоящих историй при импорте. Baseline карточки с summary/0 variants не проходят. KB-71 дополняет proof/participant gate, KB-72 — обязательный human story pilot с исходным NOT_RUN до ответа. KB-70 входит в приёмку Astro; KB-67…68 — общего request/ACK протокола.
- **Общее блокирование:** остаточный тестовый вывод/вес/поддержка в live деле или проекции, тестовое уведомление/VK side effect, разрушение чужого вклада при rollback либо восстановление эффекта поздним callback — no-go для автотестирования на реальных книгах; также любой найденный обход owner-only импорта, ложная атрибуция, обход withdrawal/private draft/proof/full-PDF границы, дублирующий необратимый post, потеря человеческого вклада или неподтверждённое удаление являются no-go до исправления. Никакой косметический дефект не приравнивается к этим рискам.

**Проверяемый итог протокола испытаний** (заполняется исполнителем позже, НЕ в этом проектном файле): дата, среда, HEAD/installed SHA, роли, список выполненных ID с PASS/FAIL/BLOCKED/NOT_RUN, для каждого связка event/request/operation/provider IDs, ссылки на безопасно сохранённые receipts, известных дефектов и вердикт владельца по каждому этапу. Структуру отчёта можно вести одной таблицей; отдельная система тест-менеджмента не нужна.

## 8. Что не строить ради ПМИ

Не создавать отдельный IAM, вторую базу POI-фактов, новый планировщик VK, новый «центральный Slack→LLM gateway», рейтинг специалистов или самостоятельную БД для Projects Hub. Не запускать дорогую модель на каждую доставку уведомления. Не ждать готового Android-приложения. Не делать одну фиктивную «зелёную E2E», состоящую только из mocked Slack и API 200. Сначала обеспечить один реальный маршрут A; потом расширить сценарии на той же базе.

Сохранённый readable body, полнота исторического поиска и публикационное одобрение — разные измеряемые результаты; математически точные векторы не заменяют проверку того, что модель действительно нашла и рассмотрела смысловые альтернативы.
