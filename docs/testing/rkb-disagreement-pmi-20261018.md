## 1. Цель и предмет

Доказать **продуктовый цикл**, а не только работающий процесс:
- владелец через собственный канал импортирует документ, обязательный scan создаёт/пополняет корректно атрибутированные дела;
- эксперт, не знающий о dot, **через отдельного Slack-бота Kaliningrad Base** находит вопрос, получает разрешённый ответ и proof, сохраняет личный аргумент и продолжает после потери чата;
- два независимых специалиста могут разойтись во мнениях и вернуться к делу; ни один вклад не пропадает и вывод не получает чужого подтверждения;
- нужное дело попадает в ограниченную обычную очередь VK, либо получает отдельно подтверждённый срочный слот; бот возвращает реальную VK-ссылку после публикации, а комментарии возвращаются в то же дело;
- разрешённые адресаты получают осмысленный briefing без раскрытия чужих материалов;
- новый транспорт Projects Hub/mobile использует тот же ресурсный контракт РКБ.

Тесты должны отдельно доказывать: **доставлено Slack → принято РКБ → обработано dot → записано в дело → возвращено Kaliningrad Base → прочитано из Slack**, а не делать вывод о продукте по одному успешному HTTP 200/файлу/поставленной в очередь задаче.

## 2. Границы и этапы

| Этап | Что принимается | Не объявлять готовым раньше |
|---|---|---|
| A — первый работающий вертикальный срез | Slack другого реального пользователя → ограниченный dot → Kaliningrad Base; текст + разрешённый proof; отказ импорта и повтора | Установку бота по сборке; вызов dot только от owner; «принято» вместо «доставлено» |
| B — исследовательская коллаборация | Поиск, вклад, точная ревизия, два эксперта, source request, сохранённое продолжение | Кнопки без реальных server receipts |
| C — реальное VK-обсуждение и уведомления | Очередь regular/urgent, VibePublish provider-scheduled/published, ссылка, чтение/модерация/ответы; digest по ACL | Плановую дату вместо VK receipt; фиктивную возможность deleteComment |
| D — переносимость | Проверка того же API/ACL на тестовом клиенте PH/Mira/mobile | Готовое мобильное приложение; переписанную БД |

Один этап можно внедрить без последующих, но нельзя маркировать весь продукт «готов» по этапу A. Не блокировать A перфекционистскими проверками стадий C/D. Защищённые требования к импорту, поиску и данным из действующего RKB остаются применимы независимо от этой ПМИ.

## 3. Среда, допуски и контрольный материал

**Стенд:** точный source commit/installed SHA и health РКБ, работоспособный service-only expert route, отдельно заведённый и разрешённый Slack app (предпочтительно Socket Mode), тестовый разрешённый DM и закрытый канал, при необходимости один публичный канал. Тестовое VK-сообщество/пост с разрешением владельца; VibePublish с реально настроенными в тесте правами. Не выполнять destructive VK-модерацию или массовые публикации в производственном сообществе. Состояние native scheduled VK читать отдельно от внутренней очереди.

**Роли/аккаунты:** O — реальный владелец; V — только текстовый читатель; E1 и E2 — два разных реальных эксперта; H — верификатор/ведущий с отдельным can_read_scan_proof и, при необходимости, редакторским правом; X — чужой пользователь либо иной team/workspace. Предусмотреть переключение ACL в ходе незавершённой операции. Не считать тестом авторства два сообщения владельца через разные каналы.

**Источники и фикстуры:** A — PDF/DjVu с заранее известным фактическим или интерпретационным расхождением и исходным сканом, B — действительный альтернативный источник/рецензия, C — похожий по словам, но непротиворечивый материал, P — закрытая книга с уникальным проверочным маркером, Q — ещё не импортированная статья, запрошенная в деле. Желательно использовать разрешённые специально созданные тестовые материалы; оригинальные изображения и метаданные допускаются только по ACL. Для каждого известны document_id, active source_revision, page/region locator, expected cases/gaps и видимость.

**Перед тестом:** зафиксировать входную ревизию, часы Europe/Kaliningrad, роли, Slack install/scopes, профиль ограниченного dot, native VK capabilities, состояние outbox/публикаций и способ восстановления. Не переносить PH owner_actor_id в expert route. Не запускать тест на реальных приватных книгах, если тестовый канал/адресат не имеет соответствующих прав.

## 4. Как выполняется каждый тест

1. Оператор фиксирует ID проверки, actor/role, preconditions, точный SHA и среду; сбрасывает **только тестовые** данные/сообщения, не очищая реальные чужие задачи.
2. Прогоняет конкретные действия с реальным Slack UI/событием, а не только вызывает backend напрямую; для негативного и аварийного случая использует контролируемую имитацию сбоя или разрешённый тестовый рестарт.
3. Собирает **независимые доказательства**: Slack event и ответ от Kaliningrad Base в том же DM/thread; RKB request ID, actor/ACL decision и result revision; вызовы MCP и operation receipt; source proof locator/render; VibePublish/provider ID/план/внешний URL и комментарий; delivery receipt. В логах только ID, статусы, время, проверенная версия и причина отказа, без токенов, содержимого приватных цитат и полных личных данных.
4. Сверяет, что один запрос не записан дважды, а отказ прав не содержит скрытых названий, счётчиков, изображений или производных пересказов. Для asynchronous разнести accepted, processing, result_saved, delivery_confirmed.
5. Ставит PASS / FAIL / BLOCKED / NOT_RUN. Любой FAIL требует повторного теста **на новой проверяемой ревизии** после исправления; прежний receipt не переписывать. Сбой внешнего провайдера — BLOCKED при подтверждённой инфраструктурной причине, но не PASS. Не повторять бездумно запрос с неизвестным результатом.

## 6. Пять обязательных сквозных маршрутов

### E2E-1: чужой эксперт, публичное/закрытое, bot→dot без владельца (этап A, P0)

**Действия:** E1 в разрешённом DM задаёт вопрос об A; фиксируем Slack event_id. После durable-ack с task ID владелец не вмешивается. MCP-событие пробуждает dot; dot читает сохранённый запрос и обращается к ограниченному профилю РКБ. Bot возвращает ответ в исходный DM. Далее V просит proof P и получает безопасный отказ, H получает оригинал по correct revision и region. H также спрашивает в private channel, где присутствует V, и получает только безопасную общую проекцию, закрытое предлагается в DM. Затем H и V **одновременно** делают приватный и публичный запрос на одном исполнителе; проверяется отсутствие пересечения результатов. E1 запрашивает импорт — отказ.

**PASS:** разные actor/worker/service principal, нет owner's authorisation, RKB receipts связаны с единственным Slack event, ответ пришёл от Kaliningrad Base, нет private leakage и импортных side effects. Предыдущая приёмка PH не заменяет этот тест.

### E2E-2: два независимых исследователя и потеря ответа (этап B, P0)

**Действия:** E1 выбирает C1 из смысловой выдачи; вносит аргумент с цитатой и теряет транспортный ответ. E2 параллельно добавляет иное объяснение. E1 читает operation_status и восстанавливает ход; H синтезирует по срезу, во время работы E2 добавляет позднее возражение. После обновления OCR документа запрашиваем обычный поиск.

**PASS:** вклад E1 в единственном экземпляре, E2 не перезаписан, поддержка относится к точной версии, поздний аргумент виден как нерассмотренный, прежняя оговорка в новом поиске не исчезла. Сканы/источники имеют locator и уровень проверки.

### E2E-3: VK очередь, завтра и срочно, без двойных публикаций (этап C, P0)

**Действия:** на тестовом сообществе две независимые regular-заявки конкурируют за следующий день; редактор приоритизирует одну. В VibePublish получаем provider_scheduled receipt, бот в Slack показывает статус **без фиктивного URL**. Затем проверяем actual published ID/URL и одно обсуждение case. Два urgent запроса одобрены; третий и запрос без роли отклонены. Имитируем lost send response, сверяем provider state. Отдельно отменяем/переносим уже scheduled A, **теряем подтверждение отмены**, пока B претендует на день A: слот должен оставаться занятым до проверенного provider receipt. Проверяем смену ACL до запланированной отправки.

**PASS:** regular ≤1/календарный день/серию и urgent ≤2 доп. по выбранной политике; ни второго поста при повторе, ни ссылки до publish, ни скрытого материала. Если native scheduling или удаление недоступно текущему токену — BLOCKED, а не обещание готовности.

### E2E-4: комментарии VK, мнение специалиста, брифинг (этап C, P0/P1)

**Действия:** два проверенных VK участника пишут и отвечают, один редактирует. Посторонний пишет в ветку, пока whitelist доступен, и повторяет во время простоя. После restart синхронизация фиксирует доступное. H через Slack открывает дело и добавляет новый аргумент; bot подтверждает contribution ID. Затем новый итог импорта A создаёт briefing для O и доступный digest E1; V не имеет доступа к P.

**PASS:** авторство и ревизии VK не подменены; модерация не трогает чужие посты, не удаляет неизвестные ветви при ошибке whitelist; пользователь может вернуться к делу из VK-ссылки. Уведомления не выдают название, счётчик и текст P. Неутверждённая историческая оценка не называется общим консенсусом.

### E2E-5: будущий клиент без повторной реализации (этап D)

**Действия:** тестовый PH-клиент с подтверждённым platform actor, ресурсной OAuth-делегацией запрашивает C1, потом отзываем grant. Выполняем те же read/proof/contribute операции, что доступные E1 через Slack; меняем actor на V.

**PASS:** одинаковые ID и версии, единый RKB policy decision и запрет приватного; после отзыва grant доступ не сохраняется. Реализация мобильного интерфейса не требуется для этого контракта.

## 7. Условия приёмки / no-go

- **Этап A:** все KB-01…08 и KB-07A P0 должны быть PASS на **минимум двух реальных участниках с разными правами** (из них как минимум один не owner) и установленном Kaliningrad Base; KB-08 выполняется также в private channel/group DM смешанного состава. Нельзя заменить их unit mock или вручную отправленным dot сообщением.
- **Этап B:** P0 KB-10…13, KB-15, KB-27 и функциональные KB-09/14; открытый pilot только после проверки знаний и цитат по основному §14 РКБ. Пропуски известных противоречий измерены, необоснованные «0» не выдаются за полноту.
- **Этап C:** до реальной VK-публикации все относящиеся P0 KB-16…20, KB-19A и 22, 24 — PASS **на разрешённом сообществе** с provider receipts. Регулярные и срочные бюджет/approve должны быть enforced сервером, не инструкцией модели. Результаты нативной отмены, токена и веток VK нельзя предполагать по прошлым публикациям.
- **Этап D:** KB-26 PASS на отдельном клиенте/отозванном grant. Это не условие выпуска Slack-варианта.
- **Общее блокирование:** любой найденный обход owner-only импорта, ложная атрибуция, доступ к закрытому исходнику, дублирующий необратимый post, потеря человеческого вклада или неподтверждённое удаление являются no-go до исправления. Никакой косметический дефект не приравнивается к этим рискам.

**Проверяемый итог протокола испытаний** (заполняется исполнителем позже, НЕ в этом проектном файле): дата, среда, HEAD/installed SHA, роли, список выполненных ID с PASS/FAIL/BLOCKED/NOT_RUN, для каждого связка event/request/operation/provider IDs, ссылки на безопасно сохранённые receipts, известных дефектов и вердикт владельца по каждому этапу. Структуру отчёта можно вести одной таблицей; отдельная система тест-менеджмента не нужна.

## 8. Что не строить ради ПМИ

Не создавать отдельный IAM, новый планировщик VK, новый «центральный Slack→LLM gateway», рейтинг специалистов или самостоятельную БД для Projects Hub. Не запускать дорогую модель на каждую доставку уведомления. Не ждать готового Android-приложения. Не делать одну фиктивную «зелёную E2E», состоящую только из mocked Slack и API 200. Сначала обеспечить один реальный маршрут A; потом расширить сценарии на той же базе.

Полнота исторического поиска — отдельный измеряемый результат; математически точные векторы не заменяют проверку того, что модель действительно нашла и рассмотрела смысловые альтернативы.
